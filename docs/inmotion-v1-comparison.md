# InMotion V1: сверка с первоисточником (`ezcan`)

Сверка нашего декодера InMotion V1 (CAN-подобный диалект, [`InMotionDecoder.cs`](../WheelTalk.Core/Decoding/InMotionDecoder.cs) —
порт `InMotionAdapter.java`) с семейством протоколов производителя `ezcan`
(`C:\Work\repos\loeuc\artifacts\blutter-inmotion-protocol\ezcan\`, восстановлено дизассемблером
`blutter` из официального приложения InMotion 8.1.34). Соседние разборы не повторяются: телеметрия
P6 и семейство `lorin` — [`inmotion-loeuc-comparison.md`](inmotion-loeuc-comparison.md); слой связи,
обрамление кадра и контрольная сумма `lorin` — [`inmotion-link-layer.md`](inmotion-link-layer.md);
словарь сущностей — `C:\Work\repos\loeuc\inmotion-official-app-dictionary.md`.

**Метод.** `ezcan` — аннотированный дизассемблер ARM64, не исходник Dart: порядок инструкций не
совпадает с порядком исходного кода, регистры переиспользуются, значения проходят через боксинг/
разбоксинг Dart-рантайма (Mint/Double/SMI), что превращает даже простое чтение байта в 30–80 строк
асма. Смещения ниже добыты прослеживанием курсора и явных числовых констант (иммедиатов), а не
догадкой по имени поля — по возможности. Там, где цепочка вычислений оказалась длиннее, чем можно
надёжно распутать за разумное время, это сказано прямо, а не выдано за факт.

**Капкан 3 (сверка с фикстурой) применён.** Наши фикстуры `RAW_inmotion_V5F.csv`/`RAW_inmotion_V8S.csv`
и приколоченные к ним тесты ([`InMotionDecoderTests.cs`](../WheelTalk.Tests/Decoding/InMotionDecoderTests.cs))
— это реальные байты с реальных колёс, декодированные в правдоподобные числа (скорость 3.82 км/ч,
напряжение 82.13 В, ток −0.2 А, температура 26 °C и т. д.). Везде, где вывод из дизассемблера
противоречил бы этому, побеждает фикстура: она сильнее прочитанного в асме.

## 0. Премиса задания подтверждена буквально, не только по имени

Словарь `inmotion-official-app-dictionary.md` (§1) называет соответствие `ezcan` ↔ наш V1 лишь
**гипотезой по имени**: «прямого доказательства байт нет — соответствие не установлено». Эта сессия
его закрывает: `EzcanFactory` (`ezcan/factory/ezcan_factory.dart`) собирает исходящие кадры с
CAN-идентификаторами, зашитыми **литеральными шестнадцатеричными константами** (`movk x_, #0xf55,
lsl #16` поверх младшего слова) — и они дословно совпадают с нашим `InMotionCanMessage.IdValue`
([`InMotionCanMessage.cs:24-38`](../WheelTalk.Core/Decoding/InMotionCanMessage.cs)):

| Id (hex) | `ezcan_factory.dart` (генератор, строка) | Наш `IdValue` |
|---|---|---|
| `0x0F550113` | `genRequestFastInfoMsg` (:1727-1729) | `GetFastInfo` |
| `0x0F550114` | `genRequestSlowInfoMsg` (:617-619), Data = `[0xFF×8]` | `GetSlowInfo` (`GetSlowData()`) — **байт в байт**, включая тело запроса |
| `0x0F550115` | (:1012-1014) | `RideMode` |
| `0x0F550116` | (:921-923) | `RemoteControl` |
| `0x0F550119` | (:1121-1123) | `Calibration` |
| `0x0F550307` | `genVerifyPwdMsg` (:3446-3448) | `PinCode` |
| `0x0F55012E` | (:1564-1566) | `HandleButton` |
| `0x0F55060A` | (:1518-1520) | `SpeakerVolume` |
| `0x0F550609` | (:805-807) | `PlaySound` |

Девять из десяти небуквенных идентификаторов нашего enum (кроме `Light` и `NoOp`) совпали дословно
с независимо восстановленными константами текущего официального приложения. `Alert` (`0x0F780101`)
живёт в другом старшем слове (`0x0F78`, не `0x0F55`) и этим конкретным поиском не проверялся —
не встречено ни подтверждения, ни противоречия. `Light` (`0x0F55010D`) тоже не встретился в
выборке — рядом нашёлся `0x0F55010E` (`genSoundPackOnOffMsg`, звук, не свет, :1367-1418), то есть
это **соседний, другой** идентификатор, не конфликт с нашим.

`genVerifyPwdMsg` (:3377-3457) вдобавок строит **6 ASCII-цифр**, дополняя буфер нулями — то же
самое, что делает `InMotionCanMessage.GetPassword(string)`
([`InMotionCanMessage.cs:282-288`](../WheelTalk.Core/Decoding/InMotionCanMessage.cs)).

**Вывод:** `ezcan` — не «похоже по имени», а подтверждённая тем же самым кодом (с точностью до
байта id и тела запроса) текущая реализация протокола, который наш V1 портирует из старого
`InMotionAdapter.java`. Дальнейшие расхождения (раздел 2) — это расхождения **внутри одного и того
же протокола**, не путаница с чужим диалектом.

## 1. Раскладка кадра: что подтверждено дословно, что — нет

### 1.1 Обрамление и контрольная сумма — структура подтверждена, алгоритм суммы — нет

`EzcanEncoder.escape` (`ezcan/codec.dart:349-628`) построчно сравнивает байты тела кадра с `0x55`,
`0xAA`, `0xA5` (`cmp x7,#0x55` / `#0xaa` / `#0xa5`, :438-458) — тот же **набор из трёх байт**, что
эскейпит наш `InMotionCanMessage.Escape`
([`InMotionCanMessage.cs:145-154`](../WheelTalk.Core/Decoding/InMotionCanMessage.cs)). Первые два
байта тела (заголовок `0xAA 0xAA`, восстановлен как константа `EzcanMessage.field_7` — SMI-тегированные
`340,340` = `170,170` = `0xAA,0xAA` в конструкторе, `ezcan_message.dart:37-56`) копируются в вывод
**без экранирования** — ровно как наш код пишет header отдельно, до вызова `Escape()`. Восьмиполевая
структура `EzcanMessage` (`id`/`data`/`length`/`channel`/`format`/`type`/`extra`/`check`, подтверждено
именами полей в `toString()`, `ezcan_message.dart:641-843`) совпадает один в один с нашими
`Id`/`Data`/`Len`/`Ch`/`Format`/`Type`/`ExData`/чек-байтом.

**Не установлено.** Алгоритм самой контрольной суммы (`EzcanMessage.genCheck`, `ezcan_message.dart:237-582`)
не удалось надёжно распутать за разумное время: код проходит через боксинг/разбоксинг SMI/Mint и
динамическую диспетчеризацию по class-id, и на нескольких прочтениях давал разные правдоподобные
интерпретации (то ли побайтовая сумма по модулю 256 — как наш `ComputeCheck`
([`InMotionCanMessage.cs:157-162`](../WheelTalk.Core/Decoding/InMotionCanMessage.cs)), — то ли
что-то, что сперва считает суммарную длину полей и отдельно домешивает `extra`). Уверенно можно
сказать одно: чек — **один байт** (не многобайтовый CRC), это видно из `toString()`. Само равенство
алгоритма нашей побайтовой сумме — **требует проверки** отдельной сессией с более щедрым бюджетом
на трассировку, не факт этого документа. Аналогично не найдено место, где `ezcan` дописывает
финальный `0x55 0x55` — за пределами `msgToBytes`/`escape` (за что отвечает, вероятно, код выше по
стеку вызовов, не разобранный здесь).

**Важно и достоверно:** это в любом случае **не** XOR-«чётность» `lorin` (`Util.calculateEvenParity`,
см. [`inmotion-link-layer.md`](inmotion-link-layer.md) §1) — за это отвечает другой класс,
`EzcanEncoder`, а не `LorinEncoder`. Капкан 2 задания (не путать семейства) соблюдён: даже не зная
точной формулы, видно, что она **устроена иначе**, чем у `lorin`.

### 1.2 Семейства моделей — деление совпадает буквально

`ezcan/bean/euc/real_time_data.dart` делит модели ровно так же, как наш `InMotionDecoder.DecodeFastInfo`
и `BatteryFromVoltage`:

- `V5RealTimeInfo` (:2152) — база;
- `V8RealTimeInfo extends V5RealTimeInfo` (:2550) — без собственных полей, чистое наследование;
- `V10LikeRealTimeInfo extends AbsRealTimeInfo` (:1383) — отдельная от V5/V8 ветка.

У нас — та же группировка: `model.BelongToInputType("5") || model is V8 or Glide3 or V8F or V8S`
против `model is V10 or V10F or V10S or V10SF or V10T or V10FT`
([`InMotionDecoder.cs:370-391`](../WheelTalk.Core/Decoding/InMotionDecoder.cs)). Совпадение не по
названию класса, а по **набору моделей внутри группы** — ровно то соответствие «по смыслу», которого
требует капкан 3 разбора P6.

### 1.3 Формула заряда от напряжения (V5/V8) — подтверждена побайтово

`V5RealTimeInfo.fromBytes` (`real_time_data.dart:2154-2546`) считает уровень заряда из напряжения
через сравнение с **иммедиатными** double-константами (не через цепочку боксинга — эту часть можно
читать с высокой уверенностью):

```
volts×100 >= 8250            → 1.0   (100 %)
volts×100 >  6800            → (raw − 6800) / 1450       // raw = напряжение×100
иначе                        → 0.0
```

Это дословно (с точностью до записи через центы вольта) наша ветка **без** `UseBetterPercents`:

```csharp
// InMotionDecoder.cs:370-376, BelongToInputType("5") || V8/Glide3/V8F/V8S
batt = volts > 82.50 ? 1.0 : volts > 68.0 ? (volts - 68.0) / 14.5 : 0.0;
```

`8250/100 = 82.50`, `6800/100 = 68.00`, `1450/100 = 14.50` — три константы, три совпадения.
**Найдено попутно, не в задании, но стоит записать**: альтернативная ветка при
`UseBetterPercents = true` (`volts > 84.00`/`68.5`/`15.5`,
[`InMotionDecoder.cs:373-375`](../WheelTalk.Core/Decoding/InMotionDecoder.cs)) — это собственное
изобретение WheelLog (или порта), не то, что показывает официальное приложение: в `ezcan` только
**одна** формула на V5/V8, и это ровно ветка без «лучших процентов». Не разбор задания, но полезная
находка для владельца конфигурации `UseBetterPercents`.

Ветка V10-семейства (`V10LikeRealTimeInfo`/аналог `AbsRealTimeState`) за пределами бюджета сессии не
дочитана — **требует проверки** отдельно, если понадобится столь же строгое подтверждение для
V10/V10F/V10S/V10SF/V10T/V10FT.

### 1.4 Абсолютные смещения телеметрии — роль полей видна, точные номера байт — нет

`AbsRealTimeInfo.fromBytes` (`ezcan/bean/real_time_info.dart:176-470`, общий код для V5/V8/V10-семейств)
читает из массива, который передаётся вызывающей стороной как **`EzcanMessage.field_23`, то есть
поле `extra`** (подтверждено на месте вызова, `protocol.dart:9741-9750`: `V5RealTimeInfo.fromBytes(...)`
получает второй аргумент из `message.field_23`) — **это тот же самый массив, что наш `ExData`/`ex`**
([`InMotionCanMessage.cs:96-105`](../WheelTalk.Core/Decoding/InMotionCanMessage.cs),
[`InMotionDecoder.cs:211`](../WheelTalk.Core/Decoding/InMotionDecoder.cs)), не другой уровень
обёртки. Внутри неё видно (константы `24`, `40`, `48`, `88`, `32`/`33` — иммедиаты в вызовах
`bytes2IntLe`/`toInt8`):

- три поля по 3 байта LE, `/10`, `toInt16` — одно из них по роли явно **«speed»** (сохраняется в
  поле, которое печатается как `speed` в `AbsRealTimeInfo.toString`, :90-101), два других участвуют
  в вычислении **`power = a × b × 0.01`** (:337-354) — то есть, как и у нас, мощность **не читается
  с провода отдельным полем, а считается** из пары «напряжение × ток» ([`WheelState.CalculatePower`],
  вызывается из [`InMotionDecoder.cs:273`](../WheelTalk.Core/Decoding/InMotionDecoder.cs));
- пара соседних байт, из которых берётся **минимум** (не среднее, не первый — именно худший из двух
  показаний), затем `toInt8` (знаковый байт) — сохраняется как **`mosTemp`**;
- 4 байта LE `uint32`, `/10` — **`totalMileage`** (одометр).

**Что не сходится и потому не заявляется фактом.** Прямая проверка этих смещений против нашей
фикстуры (капкан 3) не прошла: при подстановке чисел «24/40/48» в нашу же декодированную запись
`RAW_inmotion_V5F.csv` они не дают правдоподобных значений speed/voltage — то есть **либо** извлечённые
из асма числа 24/40/48/88 — не абсолютные смещения от начала `ex[]` (мог быть неверно прочитан
регистр-аргумент где-то в длинной цепочке боксинга), **либо** сам протокол `ezcan` на текущей
прошивке для V5/V8 действительно использует **другую раскладку тех же полей**, чем зафиксированный в
`InMotionAdapter.java` (и работающий на наших дампах) вариант — вполне возможный сценарий: порт идёт
из старого, замороженного класса WheelLog, а `ezcan` в приложении 8.1.34 — код живого, обновляемого
протокола, который вполне мог сдвинуть байты телеметрии за прошедшие годы без изменения id кадров и
общей архитектуры (ровно то, что подтвердилось выше в §0 — id и рукопожатие не изменились).

**Что можно утверждать с уверенностью капкана 3 (фикстура сильнее асма):** наши собственные смещения
(`ex[12]`+`ex[16]` → скорость, `ex[20]` → ток, `ex[24]` → напряжение, `ex[32]`/`ex[34]` → температуры,
`ex[44]`/`ex[48]` → пробег/дистанция, `ex[60]` → режим, `ex[72]` → крен —
[`InMotionDecoder.cs:214-247`](../WheelTalk.Core/Decoding/InMotionDecoder.cs)) **доказанно верны**:
они декодируют реальные байты с реальных колёс (V5F, V8S) в физически правдоподобные числа, что
сильнее любого прочтения дизассемблера. Расхождение с числами из `ezcan`, если оно реально —
вопрос **не к нашему коду**, а к вопросу «какая ревизия протокола» — задание прямо предупреждало не
чинить код по этому документу, так что вывод здесь один: **точная построчная сверка смещений не
достигнута в этой сессии, называть её найденной было бы грехом «имя/число вместо доказательства»**.
Открытый вопрос — ниже, в разделе «Спорное».

### 1.5 Ошибки/аварии как часть телеметрии — другая архитектура, не бесполезная

`V5RealTimeError.fromBytes` (`real_time_data.dart:264-734`) — **не 45-битная маска**, как у `lorin`
(см. `docs/inmotion-loeuc-comparison.md` §1.5), а **один код** (`bytes2Uint32Le`, смещение 0 своего
под-сообщения): если код `== 0xFF` — «ошибок нет» (ранний `return null`); если код в диапазоне
`0x11..0x27` (17…39 десятичных) — таблица переходов (`_Int32List` с 23 смещениями, :373-403) на
конкретный обработчик конкретной ошибки. Это **архитектурно ближе к нашему `DecodeAlert`**
(один `alertId`, `switch` по конкретным значениям — 0x05/0x06/0x19/0x1d/0x20/0x21/0x26,
[`InMotionDecoder.cs:279-314`](../WheelTalk.Core/Decoding/InMotionDecoder.cs)), чем к плоской битовой
маске `lorin`/P6. Само число диапазона (23 значения) больше, чем наши 7 распознанных `alertId` — см.
раздел 5.

**Опасных расхождений (неверная цифра в рабочем диапазоне, которая может ввести в заблуждение о
реальной угрозе) в этой сессии не найдено.** Всё, что найдено, — либо не установлено окончательно
(№1), либо снижает точность/полноту, но не искажает знак или порядок величины показанного числа
(№2, №3, №4).

## 3. Аварии и ошибки: доходят ли до райдера

**Да, доходят — в отличие от P6.** `InMotionDecoder.Decode` явно разбирает выделенный CAN-id `Alert`
(`0x0F780101`) отдельной веткой (`case InMotionCanMessage.IdValue.Alert: return DecodeAlert(message);`,
[`InMotionDecoder.cs:194`](../WheelTalk.Core/Decoding/InMotionDecoder.cs)), и `DecodeAlert`
**безусловно** вызывает `_state.SetAlert(fullText)`
([`InMotionDecoder.cs:279-314`](../WheelTalk.Core/Decoding/InMotionDecoder.cs)) для любого значения
`alertId`, включая нераспознанные (ветка `_ => "Unknown Alert ..., please contact palachzzz"` — тоже
уходит в `SetAlert`, не отбрасывается). Это прямо противоположно находке по P6
(`docs/inmotion-loeuc-comparison.md` §1.5: «владелец P6 сейчас не получит ни одной аварии колеса от
приложения») — там `InMotionP6RealTime.Apply` вообще не зовёт `SetAlert`, а V2 отбрасывает suphcmd 3
без разбора. У V1 архитектура другая: авария — **отдельный, всегда обрабатываемый** кадр, а не
suphcmd, который можно молча пропустить в `switch`.

**Что не доходит:** `ezcan`-код (§1.5) хранит **до 23** различимых кодов ошибок в своей встроенной
таблице переходов; наш `switch` по `alertId` знает **7** конкретных значений (`0x05, 0x06, 0x19, 0x1d,
0x20, 0x21, 0x26`) плюс общий текст для всего остального. Если это один и тот же провод (не
установлено, см. §5) — 16 кодов ошибок дойдут до райдера **как текст**, но без конкретного описания
(«Unknown Alert…»), не молча. Это существенно мягче ситуации P6 (там — молчание вовсе), но не
идеально: тревога будет неспецифична там, где могла бы называть причину.

## 4. Формула температуры: у V1 нет болезни «−256 °C», формула буквально совпадает

Дефект из `docs/archive`/AGENTS.md §8 (`(b & 0xff) + 80 - 256`, ошибка на 256 при перегреве) — **это
дефект семейства V2/P6**, порт `InmotionAdapterV2.java`. У **V1** формула другая с самого начала:

```csharp
// InMotionDecoder.cs:221-222
int temperature = (sbyte)ex[32];
int imuTemp = (sbyte)ex[34];
```

Это просто **интерпретация байта как знакового** (`sbyte`), без прибавления `80` и без сдвига на
`256` вообще. У производителя, в `AbsRealTimeInfo.fromBytes` (`real_time_info.dart:384-399`), то же
самое: `min(bytes[a], bytes[a+1])` передаётся напрямую в `ByteUtil.toInt8()` — **без `+80`**. Формула
`lorin` (`signed + 0x50`, см. `inmotion-loeuc-comparison.md`, раздел «Формула температуры») здесь
попросту не используется: `ezcan` для этих полей не прибавляет ничего, только переинтерпретирует
байт со знаком.

**Вывод: болезнь V2/P6 (расхождение на 256° в диапазоне перегрева) у V1 отсутствует — ни в нашем
коде, ни (насколько прослежено) у производителя.** Диапазон знакового байта (`-128…127 °C`) с запасом
покрывает любую реальную температуру колеса без переполнения, в отличие от битой формулы V2.
Единственная найденная разница — производитель берёт **худшее** из двух соседних байт (см. №2 в
разделе 2), а мы читаем один; это не про знак/переполнение, а про охват датчиков.

## 6. Расшифровка 23 кодов ошибок (`ezcan`, семейство V5/V8)

Продолжение §1.5/§3/§5: раньше диапазон `0x11`–`0x27` был назван, сами коды — нет. Здесь —
построчная расшифровка того, что делает `V5RealTimeError.fromBytes`
(`ezcan/bean/euc/real_time_data.dart:264-734`) с каждым значением из диапазона, и сверка с нашими
семью `alertId`.

### 6.1 Метод и капкан 2 (не поверить удвоенному числу)

Код читает `errorCode = bytes2Uint32Le(bytes, 0)` (:324, `bytes` — то же самое `extra`/`ExData`,
что и в §1.4), затем:

```
если errorCode == 0xFF           → возврат null («ошибок нет»)
если errorCode вне [0x11, 0x27]  → возврат null (после return: молчаливый выход, :1340dec)
иначе: index = errorCode - 0x11 (0..22)
       переход по таблице из 23 адресов (`_Int32List(23)`, :374, значения — смещения от начала функции)
```

Таблица переходов лежит в **типизированном** `_Int32List` (сырые 32-битные числа, не список
объектов Dart) — типизированные массивы в этом дампе хранят значения как есть, без SMI-упаковки
(удвоения). Проверка капкана 2 сделана иначе: пороги `0x11`/`0x27` в самом коде сравнения (`cmp
x3,#0x11`/`cmp x3,#0x27`, :988-994) читаются из **уже распакованного** (`LoadField r3=r1->field_b`
на боксе `Mint`, :937) целого — та же самая цепочка распаковки, что дала верные (не удвоенные)
пороги напряжения в §1.3, где совпадение подтвердилось независимо по формуле заряда. Отсюда —
доверие к диапазону `[0x11, 0x27]` и к самим 23 адресам таблицы.

Каждый адрес из таблицы либо ведёт к одному и тому же коду выхода (`:1340dec` — «код распознан
диапазоном, но ничего не делает», 4 таких случая), либо к короткому блоку `bool2Uint4(true) →
StoreField` — записи `true` в ровно одно из 19 предзаполненных Uint4-полей объекта. Других веток,
подсчётов или текста в этой функции нет вовсе.

### 6.3 Имён нет — не ошибка чтения, а факт устройства дампа

**Ни одного текстового названия для любого из 19 реальных кодов не нашлось.** Проверено прицельно:

- у `V5RealTimeError`/`V8RealTimeError`/`V10LikeRealTimeError` (`ezcan`) **нет собственного
  `toString()`** вовсе — ни в одном из трёх классов не встретилось `_ toString(...)`, тогда как у
  их тёзок из **другого** семейства (`lorin`: `P6RealTimeError`, `X1RealTimeError`,
  `V18RealTimeError`, `V14RealTimeError`, `E10RealTimeError`, `E20RealTimeError`, `E25RealTimeError`,
  `V6RealTimeError`) `toString()` **есть**, с именованными полями (пример: `"P6RealTimeError{ "`,
  `lorin/bean/euc/p6/p6_real_time_data.dart:532-533`) — капкан 3 задания здесь особенно нагляден:
  соседнее семейство читаемо, наше — нет, спутать было бы легко;
- базовый класс `abstract class RealTimeError extends Object {}` (`base/vehicle_data.dart:351-353`)
  — **пустой**, ни полей, ни методов, ни толкования кодов не наследует ниоткуда.

**Вывод, а не догадка:** расшифровка текста (что именно означает `field_b` из кода 17, «перегрев
мотора» это или «обрыв датчика Холла») **в этом дампе не хранится вовсе** — ни в виде строк, ни в
виде маппинга код→enum с говорящим именем. Дальше два равновероятных пути: (а) имена лежат в
таблице локализации приложения (ключи вида `error_code_17` в ресурсах, которых blutter не
восстанавливает — он работает с кодом, не с ассетами) — та же ситуация, что нашлась у KingSong
(текст ошибки живёт не в протокольном коде, а в строковых ресурсах/на сервере); (б) для этого,
самого старого поколения колёс (V5/V8) производитель вообще не показывает текст ошибки в
приложении, только сам факт «что-то не так» (17 из 19 полей и правда нигде в этом дампе не
печатаются и не читаются иначе, кроме как этим же `fromBytes` — не проверено, что где-то дальше по
коду они хотя бы попадают в UI). Ни то ни другое не установлено в рамках сессии.

### 6.4 Сверка с нашими семью `alertId`

Пять из семи наших `alertId` численно совпадают с диапазоном `ezcan` — включая ровно то самое
хеш-число (без сдвига, без удвоения):

| Наш `alertId` | Наш текст | Есть в `ezcan [0x11,0x27]`? | Что в `ezcan` на этом коде |
|---|---|---|---|
| `0x05` | Start from tilt angle | нет, ниже диапазона | не покрыт этой таблицей вовсе |
| `0x06` | Tiltback at speed | нет, ниже диапазона | не покрыт этой таблицей вовсе |
| `0x19` | Fall Down | да | реальный флаг, `field_3b` |
| `0x1d` | bad battery cell | да | реальный флаг, `field_2f` |
| `0x20` | Low battery | да | **пустой слот** — `ezcan` признаёт код, но ничего не делает |
| `0x21` | Speed cut-off | да | **пустой слот** — то же самое |
| `0x26` | High load | да | реальный флаг, `field_4f` |

**Как читать это осторожно (капкан 1).** Совпадение пяти конкретных чисел из диапазона в 23
значения на 23-элементной шкале — это факт (числа читаны из инструкций, не подобраны по соседству),
но **это не доказательство, что оба канала — один и тот же провод.** Наш `Alert`
(`0x0F780101` — отдельный CAN-id с собственным полем `alertId` в самом кадре, разбирается
`DecodeAlert`, [`InMotionDecoder.cs:279-314`](../WheelTalk.Core/Decoding/InMotionDecoder.cs)) — это
**не** та функция, что здесь разобрана: `V5RealTimeError.fromBytes` читает код из **отдельного
под-сообщения** (`extra` кадра `RealTimeInfo`-триплета), а не из тела кадра `0x0F78xxxx`. Пять
совпадений из семи — сильный довод в пользу общего происхождения (обе стороны кодируют один и тот
же перечень аварий колеса числом, просто разными путями доставки), но не факт «один и тот же
провод» — это **вывод**, а не находка, и он прямо помечен как вывод, не факт.

Если вывод верен, любопытнее всего два совпадения на **пустых** слотах `ezcan` (`0x20`, `0x21`):
похоже, что именно эти два кода ошибок на текущей прошивке **выведены из этого канала куда-то ещё**
(или сняты вовсе), тогда как наш легаси-порт (`InMotionAdapter.java`, старый и замороженный) всё ещё
готов их показать текстом, если колесо когда-нибудь их пришлёт. Не находка о нашем коде (мы ничего
не портим — просто держим более широкий словарь, чем нужно текущей прошивке), а ещё одно
подтверждение гипотезы «протокол дрейфует» из §1.4.

### 6.5 Не путать с V10-семейством (капкан 3)

`V10LikeRealTimeError.fromBytes` (`real_time_data.dart:10-260`) устроен **совсем иначе**: не один
код с таблицей переходов, а **битовая маска** — `bytes2Uint32Le(bytes, 192)`, из которого проверяются
семь конкретных бит (`&1`, `&2`, `&4`, `&0x10000`, `&0x20000`, `&0x40000`, `&0x80000`, :1341104-1341298)
в семь отдельных булевых полей. Это архитектура, близкая скорее к плоским маскам `lorin` (пусть и на
порядок уже — 7 бит, не 45), чем к «одному коду» V5/V8. Наши фикстуры (V5F, V8S) к этой ветке не
относятся — она приведена только чтобы не спутать: **таблица §6.2 — только для V5/V8/входных типов
"1"/"5"**, для V10-семейства числа будут другими, и эта сессия их не расшифровывала.

### 6.6 Поиск текста в `inmotion-libapp.strings` — тексты есть, привязки к коду нет

Проверено по прямому указанию: `inmotion-libapp.strings` (пул строк Dart, 55 299 строк) правда
содержит богатый словарь неисправностей — по `error|fault|alarm|protection|abnormal` (без учёта
регистра) выходит **1477** совпадений, включая буквально показанные примеры («Battery pack over
charge protection.», «Sensor output error, you may need to replace the driver board.» и т. д.).
Дальше — что удалось и не удалось связать с таблицей §6.2.

**Первое, что проверено: ссылается ли на эти строки хоть один файл протокольного пакета.**
Прямой поиск точного текста каждой из строк, приведённых в задании, по всему
`blutter-inmotion-protocol` (и `ezcan`, и `lorin`, и `elephant`) — **ноль совпадений**. Ни один
класс `bean`/`factory`/`protocol.dart` ни в одном из трёх семейств не хранит и не грузит эти строки
как константу. Это означает: код, что реально печатает их пользователю, лежит **вне** пакета
`inmotion_protocol` — вероятно, в UI-пакете (`package:inmotion/pages/vehicle/...`), который в
`blutter-inmotion-protocol` не спасён (см. `AGENTS.md` §5: сохранён только пакет протокола, не всё
приложение). Ровно та же картина, что и у KingSong, только без сомнений: строки не «потеряны при
чтении», их просто нет в этом наборе файлов.

**Второе: сам пул устроен так, что порядковая догадка была бы особенно опасна.** Фраза «driver
board is overheat, please stop riding for a while.» — не единичная, она встречается **шесть раз**
на очень разных строках пула (966, 1075, 6377, 15668, 36185, 44553), «driver board» вообще —
двадцать с лишним раз на протяжении всего файла (966…52246). Это значит пул — не один
последовательный список на одну модель, а **склейка почти одинаковых текстов для разных моделей**
(у каждой модели `lorin`, а возможно и `ezcan`, — свой набор похожих фраз с мелкими отличиями).
Даже если бы нашёлся код-якорь для одного текста, «следующая строка в пуле» с большой вероятностью
принадлежала бы **другой** модели, не следующему коду той же модели. Капкан задания подтверждён на
собственных данных, не только процитирован.

**Третье, что нашлось и стоит записать отдельно** — общий, не привязанный ни к одному коду
резервный текст: `"Your vehicle is in an abnormal condition. Reference error code [%s]."`
(`inmotion-libapp.strings:6224`, соседствует со строками `VehicleSettingChooseListView.`/
`VehicleSettingTabbarState` — то есть это тоже строка экрана настроек колеса, а не протокола).
Это **резервный** текст с подстановкой `%s` — сырого номера кода — в сообщение, когда конкретного
текста для кода нет. Прямая параллель с нашей собственной веткой `_ => "Unknown Alert {0:F2}
{1:F2}, please contact palachzzz..."` в `DecodeAlert`. Найдено в пуле, но, как и специфичные
тексты, **нигде не подгружается из кода протокола** — тот же вывод, что и выше.

**Четвёртое — приведённые в задании примеры, скорее всего, не наши.** Формулировки «Battery pack
over charge protection.» / «Battery cell discharge over temperature protection.» / «Battery cell
charge low temperature protection.» по словарю совпадают со **структурой `lorin`**, не `ezcan`:
именно `lorin`-модели (P6, X1, V18, E25…) несут отдельные классы-тройки `P6BMSError`/
`P6BMSWarning`/`P6BMSProtection` (`inmotion-official-app-dictionary.md` §3, §7.2) — с полями вроде
`chargeBMSOverTempProtection`, что почти дословно повторяет найденный текст. У `V5RealTimeError`/
`V8RealTimeError` (`ezcan`, §6.1) такого деления нет вовсе — один плоский код на 19 безымянных
флагов, ни один из которых не выделен как «про батарею отдельно от остального». Формально это не
опровергает, что где-то в пуле лежит текст и для этих 19 кодов — но конкретно эти три цитаты из
задания **вероятнее принадлежат `lorin`**, а не тому семейству, что разбирает этот документ. Отмечаю
явно, чтобы не повторить капкан 3 самому.

**Пятое — проверка находки про пустые слоты (`0x20`/`0x21`) осталась непройденной.** Задание просило
свериться, не садится ли текст именно на наши два кода-«пустышки» — это можно было бы сделать только
имея код-якорь между конкретным кодом и конкретной строкой. Такого якоря не нашлось ни для одного из
19 кодов, значит и для этих двух — тоже: **не подтверждено и не опровергнуто**, а не «проверено,
расхождений нет».

**Итог по разделу.** Тексты для 19 кодов `V5RealTimeError`/`V8RealTimeError` **не найдены** —
не потому, что поиск не сделан, а потому что код, который бы их печатал, не входит в спасённые
артефакты. Девятнадцать номеров из §6.2 остаются без имён; **лучше так, чем подставить имена по
соседству в пуле**, который сам по себе доказанно ненадёжен для такой догадки (шестикратные
почти-дубликаты одной и той же фразы). Расшифровка требует либо доступа к UI-пакету приложения
(`package:inmotion/pages/vehicle/...`, вне текущего `blutter`-дампа), либо перехвата живого экрана
диагностики на реальном V5/V8 с известной неисправностью.

### 6.7 UI-пакет (`blutter-inmotion-ui`): якорь найден — код уходит на сервер, а не в локальную таблицу

Владелец спас восстановленный UI-пакет (`C:\Work\repos\loeuc\artifacts\blutter-inmotion-ui\`,
`package:inmotion` целиком, включая `pages/vehicle`). Поиск шёл не перебором файлов, а от таблицы
ошибок `ezcan` — искалось, кто читает `AbsRealTimeError`/`V5RealTimeError`. Нашлось быстро:
`pages/vehicle/fault_detection/home/controller.dart`, класс `FaultDetectionController`, метод
`loadErrorCategories` (:509-1013).

**Явное разветвление по семейству — капкан 2 в самом коде производителя.** Метод сам проверяет
`ProductModel.isEzCANModel()` (`product_model.dart:1368`, вызов —
`controller.dart:753 /* 0xb01560 */`) и после него **буквально расходится на два разных пути**:

- **ветка `isEzCANModel() == true`** (`controller.dart:801-829`) — берёт значение поля
  `VehicleDataService.field_37`, **типопроверяет его как `AbsRealTimeError`**
  (`DefaultTypeTest` против `Type: AbsRealTimeError`, `:815-820`) — то есть в этой ветке живёт ровно
  наш объект из §6.1/§6.2 (`V5RealTimeError`/`V8RealTimeError extends AbsRealTimeError`), — достаёт
  из него код (`field_7.field_b`, тот самый `errorCode`) и кладёт в `controller.field_2b`;
- **ветка `isEzCANModel() == false`** (`controller.dart:830-878`) — работает с другим полем
  (`VehicleDataService.field_37`, тип-тест уже против `AbsRealTimeError<AbsRealTimeError>` —
  другая, «дженерик»-обёртка) и в итоге собирает `DetectionErrorModel`
  (`pages/vehicle/service/base/detection_base.dart:20-236`) — структуру с **тремя списками**,
  `errorList`/`protectionList`/`warningList` (именованные параметры `getErrorModel`,
  `detection_base.dart:245` область), то есть **локальную триаж-классификацию по тяжести**.

**Для V5/V8 (`isEzCANModel() == true`) локальной триаж-структуры `DetectionErrorModel` не строится
вовсе** — код идёт по первой, более короткой ветке, без `errorList`/`protectionList`/`warningList`.
Отмечаю явно: `DetectionErrorModel` с делением на три списка — это `lorin`-путь (богатые модели с
собственными классами `P6BMSError`/`P6BMSWarning`/`P6BMSProtection`, см.
`inmotion-official-app-dictionary.md` §3, §7.2), **не наш**. Приписать его V5/V8 было бы ровно тем
капканом, который держал уже дважды — не подтвердилось, что он относится к нашей раскладке кодов.

**Куда уходит код ошибки V5/V8 — не в текст, а по сети.** И `field_2b` (номер кода из ezCAN-ветки),
и результат ветки `lorin` в итоге стекаются в один вызов:
`ApiManagerVehicle.vehicleEventDiagnosis()` (`api_manager_vehicle.dart:2552-2712`,
`controller.dart:967-968`). Эта функция **не смотрит ни в одну локальную таблицу** — она строит
`Map` с ключами `"sn"` (серийный номер), `"result"` (`"ok"`/`"fail"`), `"code"` (наш номер, 17–39),
`"description"` (список категорий, если есть — у ezCAN-ветки, судя по прослеженному пути, пуст или
null), сериализует его `jsonEncode()` и передаёт в `ApiManagerVehicle.vehicleEvent(json, "diagnosis")`
(`api_manager_vehicle.dart:2698-2703`) — **сетевой вызов** (тот же `vehicleEvent`, что строит и
другие исходящие события приложения, ключевое слово запроса — `"diagnosis"`).

**Вывод — уже не гипотеза, а прослеженный факт.** Официальное приложение **не хранит соответствие
код→текст локально для семейства `ezcan`/V5/V8 вовсе** — оно репортит сырой код на сервер
производителя запросом `"diagnosis"` и, по всей видимости, показывает пользователю то, что вернёт
сервер (сам ответ и его разбор — уже вне `pages/vehicle/fault_detection`, не прослежено, не нужно
для этого вопроса). Это именно та картина, что предполагалась по аналогии с KingSong — только
теперь она не предположена, а показана конкретным вызовом конкретной сетевой функции. Достать текст
для всех 19 кодов отсюда невозможно **в принципе**, не только из-за нехватки данных в дампе: этого
текста нет ни в `libapp.so`, ни в `libapp.strings` — он существует только на стороне сервера
производителя, недоступного этой сессии.

**Что это даёт нашей стороне.** Наш `DecodeAlert` показывает текст **локально и сразу**, без единого
сетевого запроса — для 7 известных `alertId`, при этом «неизвестный» код тоже не проглатывается
(см. §3). Официальное приложение для V5/V8, судя по прослеженному коду, скорее промолчит или
покажет общее «идёт диагностика», пока не придёт ответ сервера (или разработчик вообще не выключил
показ этого экрана для настолько старых моделей — не проверено, реально ли пользователь V5/V8 видит
эту кнопку в текущей версии приложения). **Это не находка о нашем дефекте — это находка о том, что
наш путь площе, но не хуже**: наши семь текстов доступны офлайн, их текущий (серверный) путь не
доступен вовсе без сети и активного сервера производителя.

## Спорное / открытые вопросы — решение сенсея-исполнителя, не факт

1. **§1.4 — точные смещения быстрой телеметрии в `ezcan` не сведены с нашими `ex[]`.** Я решил
   **не переносить извлечённые из асма числа (24/40/48/88/32/33) в раздел «расхождений» как факт**:
   они не проходят проверку фикстурой (капкан 3), а сам путь их извлечения (боксинг/разбоксинг Dart)
   недостаточно надёжен для утверждения на его основе. Альтернатива — потратить ещё одну сессию на
   более аккуратную трассировку конкретно `V5RealTimeInfo.fromBytes`/`AbsRealTimeInfo.fromBytes` с
   контрольной сверкой каждого шага против байтов `RAW_inmotion_V5F.csv`. Решение оставляю владельцу:
   стоит ли эта точность отдельного захода, учитывая, что наши текущие смещения уже доказаны
   фикстурами и работают на реальных колёсах.
2. **Алгоритм `genCheck`** (сумма байт или что-то сложнее) — не установлен уверенно. Тип суммы
   (однобайтовая) и сам факт, что это не XOR `lorin`, — установлены; точная арифметика — нет. Решил
   не гадать вслух и не переносить в «расхождения» с ложной уверенностью.
3. **Один ли канал у `Alert`/`0x0F780101` (наш) и `V5RealTimeError`/суб-сообщение `ezcan`.** Если да —
   расширение таблицы `alertId` даёт быструю пользу (см. §5, первая строка); если это два независимых
   механизма (например, `Alert` — легаси-путь из ещё более старого протокола, а `RealTimeError` —
   текущий), то расширять нечего, это будет чтением чужого провода. Я не нашёл в дизассемблере, кто
   шлёт `0x0F78xxxx` id (ни разу не встретился в `ezcan_factory.dart` — id этой ветки родом из другого
   старшего слова, `0x0F78`, а не `0x0F55`), а искать его в 15855-строчном `protocol.dart` за
   пределами бюджета сессии. **Обновление (§6.4):** пять из семи наших `alertId` численно совпали с
   диапазоном `V5RealTimeError` (`0x11`–`0x27`), включая два совпадения на **пустых** слотах —
   это заметно усиливает гипотезу «один и тот же перечень аварий», но не превращает её в факт: числовое
   совпадение — не доказательство общего провода, только повод доверять ей больше, чем до этой сессии.
4. **Имена/тяжесть 19 реальных кодов из §6.2 не найдены нигде в дампе.** Решил не домысливать
   смысл по номеру слота (`field_b`, `field_f`, …) — это были бы голые догадки без всякой опоры.
   Зафиксировал как «требует внешнего источника» (ресурсы приложения с ключами локализации, которые
   `blutter` не восстанавливает, либо сервер производителя — та же картина, что нашлась у KingSong).
   Если владельцу нужны именно тексты — придётся доставать `res/values*/strings.xml`-эквивалент
   Flutter-приложения (ARB/l10n-файлы) отдельным заходом, это не код протокола и вне инструментария
   `blutter`.
5. **Обновление после отдельного захода в `inmotion-libapp.strings` (§6.6).** Строки-неисправности в
   пуле действительно есть в изобилии, но ни одна не подгружается кодом пакета `inmotion_protocol` —
   значит вязка код↔текст физически не может быть построена из спасённых артефактов, а не просто «не
   нашлась с первой попытки». Решил не идти по порядку в пуле даже с оговорками: сам пул шестикратно
   дублирует близкие фразы для разных моделей на очень разных строках — «соседняя строка» доказанно
   не значит «соседний код». Три конкретных примера из поручения структурно ближе к BMS-диагностике
   `lorin` (P6/X1/V18-класса), чем к плоскому 19-флаговому коду `ezcan` — привёл это как предупреждение,
   не как поправку поручения. Проверка «не садится ли текст на наши пустые слоты 0x20/0x21» осталась
   технически невозможной без кода-якоря — честно помечена как неподтверждённая, не как «чисто».
6. **Итог после захода в `blutter-inmotion-ui` (§6.7).** Пункт 4 выше оказался верным лишь наполовину:
   якорь нашёлся — `FaultDetectionController.loadErrorCategories` явно ветвится по
   `ProductModel.isEzCANModel()`, и ezCAN-ветка отправляет код ошибки на сервер производителя
   (`ApiManagerVehicle.vehicleEventDiagnosis` → `vehicleEvent(..., "diagnosis")`), не сверяясь ни с
   одной локальной таблицей. Это меняет статус вывода с «не найдено» на «подтверждено отсутствие
   локальной таблицы, найден и процитирован код, который вместо неё делает сетевой запрос» — более
   сильное утверждение, полученное по прямому указанию проверить код рядом с таблицей ошибок, а не
   гадать по тексту. Имён 19 кодов это всё равно не даёт: их, похоже, не существует нигде в
   приложении — только на сервере, вне досягаемости любого статического анализа APK. Отдельно
   проверено и не притянуто: локальная триаж-структура `DetectionErrorModel`
   (`errorList`/`protectionList`/`warningList`) существует, но принадлежит ветке `lorin`
   (`isEzCANModel() == false`), для V5/V8 не строится вовсе — не спутано с нашей таблицей.
