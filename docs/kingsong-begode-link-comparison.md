# KingSong и Begode: способ подключения — сверка с DarknessBot

Пятое приложение — **DarknessBot** (`darkness_bot`, Flutter/Dart, восстановлено дизассемблером
`blutter` из AOT-снапшота), артефакт `C:\Work\repos\loeuc\artifacts\blutter-darknessbot\
darkness_bot\` (146 файлов, **не обфусцирован** — имена классов/методов/полей разрешены). По
InMotion разбор этого приложения уже дал ответ на давнюю жалобу (тип записи, задокументировано в
`docs/polling-architecture-review.md` §5). Здесь — та же проверка для **KingSong** и **Begode**,
своих файлов, а не переоткрытие раскладки кадров (она уже сверена:
[`kingsong-telemetry-comparison.md`](kingsong-telemetry-comparison.md),
[`kingsong-commands-comparison.md`](kingsong-commands-comparison.md),
[`begode-comparison.md`](begode-comparison.md)). Опрос по нашей стороне для обеих марок уже разобран
в [`polling-architecture-review.md`](polling-architecture-review.md) §2 — здесь он не переизлагается,
только сверяется числами со стороны DarknessBot, которые тот документ сам называет непроверенными
(«здесь не перепроверялись»).

**Метод и его границы.** Дизассемблер восстанавливает имена, но не порядок кода как в исходнике —
читал по вызовам (`bl #addr ; ClassName::method`) и по значениям constant-пула (`objs.txt`), не
сверху вниз. Целые числа, встроенные прямо в машинный код как непосредственные операнды
Dart-переменной (`mov x0, #0x2a` и т.п.), у Dart AOT на ARM64 могут быть **SMI-тегированы —
вдвое больше настоящего значения** (капкан задания: «видишь 40 — читай `0x14`»); это касается
байтов протокола внутри переменных. Значения из `objs.txt` (заранее вычисленные constant-объекты,
например `Duration`) показаны уже **декодированными** — проверено на `Duration@a565d1: int(0xf4240)`,
это ровно 1 000 000 микросекунд = 1 секунда, круглое число без всякого удвоения — там, где число
опирается на `objs.txt`, деление на два не применяется, это сказано отдельно по каждому месту.
Счётчики циклов, посчитанные напрямую регистровым `add r, r, #1` (не через тегированную SMI-цепочку
Dart `int`), тоже читаются как есть — это касается найденного ниже предела `wait()`.

**Наша сторона.** `WheelTalk.Core/Detection/WheelProfiles.cs`,
`WheelTalk.Droid/Ble/AndroidBleClient.cs` (`SelectCharacteristics`, `BeginWrite`),
`WheelTalk.Core/Decoding/GotwayDecoder.cs`, `WheelTalk.Core/Decoding/KingsongDecoder.cs`.

## 1. GATT-профиль и выбор характеристик

### 1.1 Begode — одна пара, без запасных путей

`GotwayAdapter.isCompatible()` (`gotway_adapter.dart:2785-3040`) проверяет присутствие **ровно
двух** UUID у обнаруженного устройства — сервис `0000ffe0-…` (`:2804-2806`) и характеристику
`0000ffe1-…` под ним (`:2834-2836`, перепроверяется ещё дважды на соседних путях кода, `:2955-2958`,
`:2998-3001` — тот же UUID, не альтернатива). Ни одного другого сервиса, ни проверки по рекламному
имени в этом методе нет. В конце — вызов `BaseAdapter.isCompatible()` (`:3036`,
`base_adapter.dart:1566-1618`), который у базового класса лишь нормализует и сохраняет
идентификатор устройства (`Ext.identifier`, `bluetooth_device_extension.dart:6-28`) — не добавляет
условий.

**У нас** — та же единственная пара `ffe0`/`ffe1` для Gotway
([`WheelProfiles.cs:22-26`](../WheelTalk.Core/Detection/WheelProfiles.cs), первый Begode-профиль;
второй профиль тех же строк добавляет `fff0`/`fff1` и характеристики батареи `1801` — **шире**, чем
у DarknessBot). **Совпадает на минимальном общем знаменателе, у нас запасных путей больше.**

### 1.2 KingSong — тот же жёсткий гейт `ffe0`/`ffe1`, но с запасным путём по имени, которого нет у нас

`KingSongAdapter.isCompatible()` (`kingsong_adapter.dart:4534-4812`) устроена в три шага:

1. **Жёсткий гейт**: сервис `0000ffe0-…` (`:4553-4554`) и характеристика `0000ffe1-…` под ним
   (`:4586-4587`) — нет ни одного, метод сразу возвращает `false` (`:4592,4621` — путь `b.ne →
   r0=false`, не мягкий отказ);
2. **Второй, более мягкий шаг**: сервис `0000fff0-…` (`:4666-4667`). Если его нет —
   **запасной путь по рекламному имени устройства**: сравнение (после нормализации) с подстроками
   `"ks"`, `"rock"`, `"rw"` (`:4681,4697,4706` — три отдельных строковых литерала, не таблица имён
   моделей). Ни то ни другое не найдено — тоже `false`;
3. Дальше — повторная проверка `ffe1` (`:4731-4732,4774-4775`) с иным исходом отказа (`r0=Null`, не
   `false`) — похоже на получение ссылки на характеристику для использования дальше, не на условие
   годности. Завершается вызовом `BaseAdapter.isCompatible()` (`:4812`) и `true`.

**У нас** — три отпечатка GATT-дерева для KingSong
([`WheelProfiles.cs:71-94`](../WheelTalk.Core/Detection/WheelProfiles.cs)): `fff0`+`ffe0/ffe1`
(совпадает со вторым шагом DarknessBot), нестандартный `02f00000-…`+`ffe0`/`ffe1`/`fff3`/`fff5`/два
кастомных UUID, и `ffe0`+`ffe2`/`ffe1`. **Ни одного из этих трёх у DarknessBot нет вовсе, кроме
первого** — но у DarknessBot есть то, чего нет у нас совсем: **запасной путь по рекламному имени**
(`"ks"`/`"rock"`/`"rw"`), когда `fff0` не найден. Мы такого пути **не имеем ни для одной марки**
([`inmotion-loeuc-comparison.md`](inmotion-loeuc-comparison.md), раздел «Дополнение»: «имя из
рекламного пакета нигде не читается» — верно и для KingSong, `grep` по `WheelTalk.Core/Detection`
не находит обращений к имени устройства). **Расхождение реальное, но симметричное**: у DarknessBot
уже, но живучее (умеет опознать по имени колесо со «странным» деревом GATT), у нас — шире по числу
знакомых деревьев, но без подстраховки именем.

## 2. Рукопожатие

### 2.1 Begode — одна и та же команда, вызываемая из трёх разных мест

`GotwayAdapter.writeQuery()` (`gotway_adapter.dart:308-406`) — единственный билдер команды
рукопожатия, вызывается: из конструктора при подключении (`:9433`), из геттеров `model`/`brand`,
если значение ещё не известно (`:815,922` — то есть **лениво, по требованию читающего**, а не
только один раз на старте), и из `processBuffer` (`:1097,3129,3324,3363` — то есть **тоже
ответозависимо, как и у нас**). Сама `writeQuery()` вызывает общий `BaseAdapter.write(...)`
(`:391`, см. §4) и ждёт `Duration` (см. капкан о числах — точное значение этой конкретной паузы не
беру на веру без подтверждения по `objs.txt`, не привожу цифру).

**У нас** — `RunHandshakeAttempt()` из `Decode()` ([`GotwayDecoder.cs:147`](../WheelTalk.Core/Decoding/GotwayDecoder.cs),
уже разобрано в `polling-architecture-review.md` §2): пол 40 мс, потолок 50 попыток, шлёт, пока
пусты `_fw`/`_model`. **Форма совпадает** (ответозависимо, из декодированного кадра, с условием «пока
не известно») — числовую пару пол/потолок стороной DarknessBot напрямую не сверял (см. §3.2 про
похожий, но не тот же механизм — `wait()`).

### 2.2 KingSong — пакет из четырёх запросов, единой цепочкой

`KingSongAdapter` в явном виде опрашивает батарею **дважды по два запроса**: `askBatterySerialNumber()`
(`:3924`), `askBattery2SerialNumber()` (`:3890`), `askBatteryFirmware()` (`:3856`),
`askBattery2Firmware()` (`:3666`) — вызываются подряd, каждый с `await` на `Duration` между
(`:3572,3596,3620,3643` — конструкция `r0=askXxx(); Await(); Duration(); Await()` повторена четыре
раза). Это **фиксированная последовательность в четыре шага**, не бесконечный повтор одного запроса.
Точная длительность паузы между шагами взята из пула констант (`objs.txt`,
`Duration@a56681`) — **не привожу как факт в миллисекундах**: адрес найден и использован
единообразно во всех четырёх местах, но перевод его внутреннего поля в осмысленную величину дал
неправдоподобно малое число при первой попытке, и я не берусь утверждать его без более надёжной
перепроверки — фиксирую как **факт наличия паузы между шагами**, не как факт её величины.

**Главное — не в паузе, а в ограничении.** Все и без исключения находки о запросах-ответах в обоих
адаптерах DarknessBot проходят через общий `BaseAdapter.wait(predicate)`
(`base_adapter.dart:878-977`) — и вот здесь числа однозначны и не вызывают сомнений (см. §3.1).

## 3. Опрос — DarknessBot ограничивает circular retry везде одним общим механизмом

### 3.1 `BaseAdapter.wait()` — общий, числа не вызывают сомнений

```
цикл до 40 раз:
    ждать Duration(microseconds: 50000)   // 50 мс — литерал 0xc350=50000 прямо в коде, не из пула
    вызвать predicate()
    если predicate() == true → вернуть true
вернуть false
```
(`base_adapter.dart:878-977`, счётчик цикла — обычный регистровый инкремент `add x0,x1,#1` и
сравнение `cmp x0, #0x28`(=40) напрямую, **не тегированная Dart-SMI цепочка** — капкан на удвоение
здесь не применяется: `0x28`=40 читается как есть, не как `0x14`; `0xc350`=50000 — тоже прямой
операнд, не из `objs.txt`). Итог: **до 40 попыток по 50 мс, максимум 2 секунды**, потом отказ.

**Это тот самый общий инструмент, каким DarknessBot решает «подождать ответа, не более
определённого времени» — и он используется массово в обоих файлах**: `grep` по вызовам `wait()`
даёт **32 места в `kingsong_adapter.dart`** и **17 в `gotway_adapter.dart`**. Не единичный случай —
основной способ дождаться чего угодно (ответа на команду, смены состояния) в обеих марках.

### 3.2 Прямой ответ на вопрос про наш дефект `KingsongDecoder.cs:128`

**У DarknessBot для KingSong такой же беды нет — по архитектуре, не по счастливой случайности.**
Наш `RequestMissingIdentity()` шлёт запрос на **каждое входящее уведомление, без пола и без
потолка** ([`KingsongDecoder.cs:128,151-155`](../WheelTalk.Core/Decoding/KingsongDecoder.cs),
уже отмечено как открытый дефект в `polling-architecture-review.md` §2.1, §8.6). У DarknessBot же
**сама возможность бесконечного повтора устранена на уровне общего инструмента**: любое ожидание
ответа (включая опрос идентификации батареи, §2.2) идёт через `wait()`, которое **физически не
может** зациклиться дольше 2 секунд — после 40 попыток по 50 мс метод возвращает `false` и
вызывающий код идёт дальше, что бы это «дальше» ни значило (сдаться, попробовать другой путь,
пометить поле неизвестным). Это архитектурно ближе к нашему **Begode** (пол+потолок,
`GotwayDecoder.cs:147`), чем к нашему KingSong.

**Раскладка не 1:1 (честно, не подгоняю):** у нас пол/потолок — 40 мс/50 попыток (=2000 мс общий
бюджет); у DarknessBot — 50 мс/40 попыток (=2000 мс общий бюджет). **Разные пол и потолок, тот же
общий бюджет по времени — 2 секунды.** Совпадение общего бюджета при разных множителях интересно,
но не переоцениваю его: могло быть совпадением инженерной интуиции («пары секунд достаточно, чтобы
не заставлять ждать и не спамить»), не общим источником.

**Вывод для нашего кода**: DarknessBot подтверждает, что бесконечный повтор без потолка — это
**не свойство протокола KingSong**, требующее вечного опроса, а **наш собственный порт-дефект**:
там, где производитель и DarknessBot оба останавливаются, наш `RequestMissingIdentity` не
останавливается никогда. Это усиливает (не открывает заново) то, что уже отмечено в §8.6
`polling-architecture-review.md` как спорный пункт «чинить или оставить» — теперь есть третий
источник (родное приложение через `kingsong-telemetry-comparison.md`, и вот DarknessBot), оба не
делающие того, что делаем мы.

### 3.3 Периодического опроса телеметрии нет ни у Begode, ни у KingSong

По всему `gotway_adapter.dart` и `kingsong_adapter.dart` — **ни одного `Timer`/`Timer.periodic`**
(искал явно, капкан задания «есть ли вообще, времязависимый или ответозависимый» — здесь ответ
«ответозависимый, и то не для основной телеметрии, а только для опознания»). Единственные механизмы
ожидания в обоих файлах — `wait()` (§3.1) для рукопожатия/подтверждений и `Future.delayed` внутри
`writeQuery`/ask-последовательности (§2). **Основная телеметрия не запрашивается заново после
первого ответа** — так же, как у нас (`polling-architecture-review.md` §2: у Begode/KingSong «кто
решает — декодер», «что запускает — каждый кадр/уведомление», не таймер). **Совпадает по форме с
обеих сторон.**

## 4. Тип записи — совпадает с нами дословно, независимо перепроверено

**Капкан 1 задания предупреждал не переносить вывод с InMotion — не переношу, проверил заново для
обеих марок отдельно.**

`BaseAdapter.write(bytes, {withResponse = false})` (`base_adapter.dart:791-877`) — сигнатура несёт
именованный параметр **по умолчанию `false`**. Тело метода перед вызовом плагина инвертирует его
(`eor x5, x0, #0x10` — переключает Dart-тег `true`↔`false`, `:4e434c-4e4350`) и передаёт как
`withoutResponse` в `BluetoothCharacteristic.write(...)` — метод из **`package:darkness_blue_plus`**
(`:4e4364`, внешний BLE-плагин команды, не часть декомпилированного `darkness_bot`). Значит: **по
умолчанию — без подтверждения**, если только вызывающий код явно не передаст `withResponse: true`.

**Ни `gotway_adapter.dart`, ни `kingsong_adapter.dart` не содержат ни одного обращения к
именованному параметру `"withResponse"`** (`grep` по литеральной строке — ноль совпадений в обоих
файлах; для сравнения, у Dart-компилятора имена именованных параметров, использованных в вызове,
обязаны появиться как строковый литерал в дескрипторе аргументов — их отсутствие означает, что
параметр нигде не передан явно, значит везде остаётся значение по умолчанию). **И Gotway, и KingSong
пишут без подтверждения — подтверждено чтением кода, не унаследовано с чужих слов.**

**У нас** — `NoResponse` зашит литералом в обоих местах `BeginWrite`
([`AndroidBleClient.cs:373,378`](../WheelTalk.Droid/Ble/AndroidBleClient.cs)) для всех протоколов
одинаково. **Совпадает для Gotway и KingSong с обеих сторон.** Расхождение (по `polling-architecture-review.md`
§5.2) есть только для InMotion — эта марка вне периметра этой части, не проверял здесь заново.

нашёл. Управление соединением, судя по всему, целиком лежит в самом BLE-плагине
`package:darkness_blue_plus` — **отдельном пакете, не входящем в 146 файлов `darkness_bot`**,
который мне не предоставлен и не декомпилирован. **Честно: не установлено**, не «нет данных
вовсе» — просто файла с этой логикой не нашёл в выданном артефакте. Не домысливаю по аналогии с
InMotion (капкан 1) — это отдельный, непроверенный вопрос.

## Спорное / решения по ходу разбора

1. **Точная величина паузы в ask-последовательности KingSong (§2.2)** — нашёл механизм
   (четыре запроса, пауза между каждым через один и тот же объект `Duration` из пула), но не
   доверяю своему первому переводу его внутреннего поля в миллисекунды (число получилось
   неправдоподобно маленьким — вероятно, спутал адрес объекта константы или неверно применил
   капкан удвоения именно к этому полю). Оставил как факт паузы без цифры — лучше честный пробел,
   чем красивое, но не проверенное число.
2. **Совпадение общего бюджета `wait()` (2 с) у нас и у DarknessBot для Begode (§3.2)** — совпадение
   красивое (2000 мс что там, что там), но при разных пол/потолок это могло быть параллельной
   инженерной интуицией, не общим происхождением числа. Не выдаю за большее, чем оно есть.
3. **Переподключение/обрыв (§5)** — не нашёл нужного файла в артефакте. Если у владельца есть доступ
   к декомпиляту плагина `darkness_blue_plus` отдельно — вопрос закрывается быстро; в текущем
   `darkness_bot`-пакете этой логики нет.
4. **Ленивый вызов `writeQuery()` из геттеров `model`/`brand` (§2.1)** — интересная деталь
   архитектуры (запрос уходит не только при разборе кадра, но и когда UI-код читает нераспознанное
   поле), которая не имеет прямого аналога в нашем декодере (`GotwayDecoder` не запрашивает данные
   в момент чтения свойства). Не привожу как расхождение-дефект — просто другой стиль, не
   тестировал, эквивалентен ли он по итоговой частоте запросов.
