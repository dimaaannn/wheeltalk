## 0. Правила работы в этом репозитории

Прочитать [AGENTS.md](../../AGENTS.md) целиком до первой правки. Ключевое, что нарушают чаще всего:

- **Избегать избыточности кода и лишних проверок.** Не добавлять слой/обёртку/защиту «на всякий
  случай». Если проверка не предотвращает конкретный правдоподобный сбой — её быть не должно.
- **Тесты — только для сложной логики.** Декодеры уже покрыты 17 тестами. UI, DI-проводка и
  BLE-обвязка тестами не покрываются — не писать.
- **Данные проверять там, где они используются**, а не заранее при старте.
- Комментарии в коде — на английском (как везде в репозитории), документация — на русском.
- **Вся бизнес-логика живёт в `WheelTalk.Core`**, в приложении — только реализация платформенного
  (BLE-адаптер, экраны, Android-специфика). Правило: если код можно выполнить без единого
  `using Android.*` — ему место в ядре.
- Консольный проект `WheelTalk` правится **только механически**, вслед за изменениями API ядра —
  он обязан продолжать собираться и работать. Новую функциональность в него не добавлять.

Коммитить по фазам в ветку `android`, сообщение — в стиле существующей истории (английский,
повелительное наклонение, объяснение «почему» в теле), с трейлером
`Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.

## 1. Зафиксированные решения (согласовано с пользователем, не пересматривать)

| Параметр | Решение |
|---|---|
| UI-стек | .NET MAUI, **единственный** таргет `net10.0-android`. Никакого multi-targeting. |
| Разметка | XAML + code-behind. **Без** MVVM-фреймворка, без CommunityToolkit, без ViewModel-слоя — подписка на события и присвоение значений напрямую в code-behind. |
| Имя проекта | `WheelTalk.App` (не `.Droid`: позже к нему может добавиться Windows-голова), namespace `WheelTalk.App`, applicationId `com.wheeltalk.app`. |
| Переиспользование ядра | `ProjectReference` на `WheelTalk.Core`. Ядро **не править**. |
| BLE | Нативный `Android.Bluetooth` / `Android.Bluetooth.LE`. **Не** Plugin.BLE и не другие обёртки. |
| Транспорт | `AndroidBleClient : WheelTalk.Core.Ports.ITransport`. |
| Выбор протокола | Переключатель в UI (Veteran / Begode) рядом с кнопкой скана. Декодер строится в момент подключения, а не при старте DI. |
| Входной пайплайн | `Decoder.Feed` вызывается **прямо из GATT-колбэка**, как это делает `WindowsBleClient`. TPL Dataflow не использовать — колбэки одного GATT-соединения приходят последовательно, лишний слой не нужен. |
| Выдача телеметрии | **Непрерывный поток `IObservable<TelemetrySnapshot>` (`System.Reactive`) в ядре** — см. §2.1. Подписчик сам решает, что с ним делать (фильтры, троттлинг); источник ничего не знает о потребителях. |
| Обновление UI | Только через `MainThread.BeginInvokeOnMainThread`, с троттлингом ~5 Гц (оператором Rx, не самодельным таймером). |
| Конфигурация | Классы конфигурации через `IOptions<T>` — см. §3. |

## 2. Что уже есть в ядре (сигнатуры, на которые опираться)

Всё перечисленное — `WheelTalk.Core`, менять нельзя, использовать как есть.

```csharp
// Ports/ITransport.cs
public interface ITransport
{
    event Action<byte[]>? DataReceived;
    IAsyncEnumerable<DiscoveredDevice> ScanAsync(CancellationToken ct = default);
    Task ConnectAsync(string address, CancellationToken ct = default);
    Task DisconnectAsync(CancellationToken ct = default);
    Task WriteAsync(byte[] cmd, CancellationToken ct = default);
}

// Ports/DiscoveredDevice.cs — Name пустой, пока устройство не объявило имя;
// Address — MAC в том же виде, который принимает ConnectAsync
public sealed record DiscoveredDevice(string Name, string Address, int Rssi);

// Ports/IEventSink.cs
public interface IEventSink { void Publish(WheelEvent e); }

// Services/Decoder.cs
public sealed partial class Decoder
{
    public event Action<TelemetrySnapshot>? SnapshotUpdated;
    public IWheelDecoder ProtocolDecoder { get; }
    public Decoder(WheelState state, IWheelDecoder protocolDecoder, IEventSink eventSink, ILogger<Decoder> logger);
    public void Feed(byte[] bytes);
}

// Services/WheelService.cs — подписывается на ITransport.DataReceived в конструкторе
public sealed partial class WheelService
{
    public TelemetrySnapshot? LastSnapshot { get; }
    public event Action<TelemetrySnapshot>? SnapshotUpdated;   // заменяется потоком, см. §2.1
    public WheelService(ITransport transport, Decoder decoder, ILogger<WheelService> logger);
    public Task SetLight(bool enabled, CancellationToken ct = default);
    public Task Beep(CancellationToken ct = default);
    // ...SetPedalsMode/ResetTrip/Calibrate — в этой задаче не нужны
}

// Decoding/WheelDecoderFactory.cs — единственное место выбора декодера
public static IWheelDecoder Create(WheelProtocol protocol, WheelState state, IWheelConfig config,
    TimeProvider timeProvider, ILoggerFactory loggerFactory);

// Contracts/WheelProtocol.cs — enum: Veteran, Gotway (синоним Begode)
```

Образец сборки этих объектов вместе — [BusinessLogicServiceCollectionExtensions.cs](../WheelTalk/Composition/BusinessLogicServiceCollectionExtensions.cs)
в консольном приложении. Образец реализации `ITransport` — [WindowsBleClient.cs](../WheelTalk/Ble/WindowsBleClient.cs)
(там же видно, какие UUID у колёс и как устроен цикл connect → discovery → notify).

**`Decoder` stateful и не потокобезопасен.** Байты обязаны попадать в него по порядку и из
одного потока. GATT-колбэки одного соединения это обеспечивают; ничего добавлять не нужно, но и
параллелить их нельзя.

### 2.1. Поток телеметрии (правка ядра, делается в этом плане)

Сейчас `Decoder`/`WheelService` отдают снэпшоты событием `SnapshotUpdated`. Событие заменяется на
поток `System.Reactive`:

```csharp
IObservable<TelemetrySnapshot> Telemetry { get; }   // на WheelService
```

- Реализация — `Subject`/`BehaviorSubject` внутри ядра; событие `SnapshotUpdated` убирается,
  чтобы не было двух параллельных механизмов.
- Потребители в консоли (`ConsolePresenter`, `TelemetryCsvWriter`, `TestHarness`) переводятся на
  подписку — правка механическая, поведение не меняется.
- Время и планировщики во всех операторах — через `TimeProvider`/явный `IScheduler`, чтобы это
  было проверяемо тестами. Дефолтные планировщики Rx не использовать.
- Каждая подписка в UI обязана отписываться при уходе страницы.

Так поток готов к тому, что на него сядут движок тревог и другие потребители
([План 4](android-plan-4-alerts-and-background.md)), а не только сетка значений.

## 3. Конфигурация

Все параметры поставляются классами конфигурации через `IOptions<T>`. Правила:

- классы **мутабельные**, значение читается в момент использования, а не кэшируется подписчиком;
- изменение параметра во время работы = присвоение поля тому же экземпляру, который раздаёт
  `IOptions<T>` (он всегда один);
- `IOptionsMonitor` и перечитывание конфигурации **не использовать**, пока не появится случай,
  где без них нарушается консистентность набора значений;
- валидацию опций не добавлять.

### 3.0. Два слоя: дефолты и пользовательские настройки

| Слой | Где лежит | Кто пишет |
|---|---|---|
| **Дефолты** | `appsettings.json` в ресурсах приложения (`MauiAsset`), тот же формат, что у консоли | только разработчик, правится с пересборкой |
| **Пользовательский** | отдельный JSON-файл в каталоге данных приложения (`FileSystem.AppDataDirectory`) | приложение, при изменении настроек пользователем |

Пользовательский слой накладывается поверх дефолтов (`ConfigurationBuilder`: сначала ресурс,
затем пользовательский файл как `optional: true`). Значений, которых пользователь не менял, в его
файле нет — он остаётся коротким и понятным.

**Настройки хранятся отдельно для каждого колеса** — пороги тревог, протокол и прочее у разных
колёс отличаются. Структура пользовательского файла: словарь по MAC-адресу, внутри — секции
настроек этого колеса; плюс секция общих настроек, не привязанных к колесу. При подключении к
колесу его секция накладывается на дефолты и попадает в живые экземпляры опций.

**При изменении настройки пользователем** — два действия сразу: обновить поле в живом экземпляре
опций (действует немедленно) и записать значение в пользовательский файл (переживает перезапуск).
Перечитывания конфигурации при этом не происходит.

В базовом плане достаточно самой схемы (загрузка, наложение, запись). Пользовательского интерфейса
настроек здесь нет — он появится вместе с параметрами, которые есть смысл менять.

### 3.1. Конфигурация колеса

Создать в проекте POCO `AppWheelConfig : IWheelConfig` — копию
[WheelTalk/Configuration/AppWheelConfig.cs](../WheelTalk/Configuration/AppWheelConfig.cs) с теми
же дефолтами:

```
GotwayNegative = "0", UseBetterPercents = false, HwPwm = false, CustomPercents = false,
CellVoltageTiltback = 330, RotationSpeed = 500, RotationVoltage = 840, PowerFactor = 90,
BatteryCapacity = 0, LightEnabled = false,
UseRatio = false, AutoVoltage = true, GotwayVoltage = "1", IsAlexovikFW = false
```

`GotwayVoltage = "1"` соответствует пакету 84 В / 20S тестового колеса Begode MTen3 — не менять.
Экземпляр должен быть **один общий и мутабельный**: декодеры пишут в него (`HwPwm`,
`LightEnabled`, `IsAlexovikFW`), копия сломает логику.

Деплой и диагностика:

```
dotnet build WheelTalk.App/WheelTalk.App.csproj -t:Run     # собрать, установить, запустить
adb logcat -d -t 300                                        # последние строки лога
adb logcat -c                                               # очистить перед прогоном

**Самопроверка без участия пользователя.** Агент не может нажимать кнопки руками, но может:

```
adb exec-out screencap -p > screen.png                      # скриншот, его можно прочитать

## 5. Фазы

Каждая фаза заканчивается работающим на телефоне артефактом. Не переходить к следующей, пока
гейт текущей не пройден. После каждой фазы — коммит.

### Фаза 1 — Каркас и подключение ядра

1. `dotnet new maui -n WheelTalk.App` в корне репозитория, вычистить всё, кроме `net10.0-android`
   (в шаблоне `TargetFrameworks` собирается из нескольких условных строк — оставить одну).
2. Добавить проект в `WheelTalk.slnx`, поставить `ProjectReference` на `WheelTalk.Core`.
3. `SupportedOSPlatformVersion` не выше 30 (телефон — API 30).
4. Логирование: `ILoggerFactory` с провайдером, пишущим в logcat (`Android.Util.Log`), — своя
   реализация на несколько строк, без Serilog и без файловых синков.
5. DI в `MauiProgram.cs`: `AppWheelConfig` как `IWheelConfig` через `IOptions<T>` (§3),
   `TimeProvider.System`, `IEventSink` (пишет в логгер), `AndroidBleClient` как `ITransport`.
   `WheelState`/`IWheelDecoder`/`Decoder`/`WheelService` **не регистрировать в DI** — они зависят
   от выбранного протокола и создаются в момент подключения (см. Фазу 3).
6. Правка ядра из §2.1 (поток телеметрии) делается здесь же, вместе с механическим переводом
   консольных потребителей на подписку. `dotnet test` и консольное приложение обязаны остаться
   рабочими.

**Гейт T1:** приложение собирается, ставится и запускается на телефоне; в logcat видна строка
старта из своего логгера.

### Фаза 2 — Экран скана

1. Единственный экран с кнопкой **«Сканировать»**, переключателем протокола (Veteran / Begode)
   и списком найденных устройств (`CollectionView`): строка = `имя`, мелким шрифтом `MAC` и `RSSI`.
2. Устройства без имени в список **не** попадают (у колёс имя всегда есть; безымянных вокруг десятки).
3. Список ведётся по `Address` как ключу: повторное событие по тому же адресу обновляет строку,
   а не добавляет новую (`DiscoveredDevice` приходит второй раз, когда разрешилось имя).
4. Разрешения запрашивать перед стартом скана:
   - API ≤ 30 (наш телефон): `ACCESS_FINE_LOCATION` в рантайме + `BLUETOOTH`/`BLUETOOTH_ADMIN`
     в манифесте. Дополнительно проверить, что **геолокация включена в системе** — иначе скан
     молча не вернёт ничего; при выключенной показать это на экране, а не молчать.
   - API ≥ 31: `BLUETOOTH_SCAN` + `BLUETOOTH_CONNECT`. В манифесте объявить обе группы, чтобы
     приложение работало и на новых телефонах.
5. Скан останавливать при уходе с экрана и перед подключением.

**Гейт T2:** на телефоне нажатие кнопки даёт список реальных окружающих устройств с именами.
Проверяется агентом через `uiautomator dump` + `input tap` + скриншот.

### Фаза 3 — `AndroidBleClient : ITransport` и подключение

Реализовать интерфейс целиком:

- `ScanAsync` — `BluetoothLeScanner` + `ScanCallback`, режим `ScanMode.LowLatency`, результаты
  через `Channel` наружу в `IAsyncEnumerable` (как сделано в `WindowsBleClient`). Дедуп по адресу
  и повторная выдача при разрешении имени — внутри клиента.
- `ConnectAsync(address)` — `BluetoothAdapter.GetRemoteDevice(address)` (MAC **в верхнем регистре**),
  `device.ConnectGatt(context, autoConnect: false, callback, BluetoothTransports.Le)`,
  затем в колбэке `DiscoverServices()`, поиск сервиса `0000ffe0-0000-1000-8000-00805f9b34fb` и
  характеристики `0000ffe1-0000-1000-8000-00805f9b34fb`.
- **Включение нотификаций — два шага, второй забывают чаще всего:** `gatt.SetCharacteristicNotification(ch, true)`
  **и** запись `EnableNotificationValue` в дескриптор CCCD `00002902-0000-1000-8000-00805f9b34fb`.
  Без записи дескриптора подключение выглядит успешным, а данные не идут.
- `WriteAsync` — тип записи `WriteWithoutResponse` (у колёс так).
- `DisconnectAsync` — снять нотификации, `gatt.Disconnect()` **и** `gatt.Close()` (без `Close`
  Android держит соединение и следующее подключение падает).
- API 33+ развёл методы записи характеристик/дескрипторов на новые перегрузки, а старые пометил
  obsolete. Проект собирается под API 36 — использовать новые перегрузки, ветку для API ≤ 32
  добавлять только если компилятор/рантайм этого потребуют (телефон — API 30).

Сборка сессии при подключении: `WheelState` → `WheelDecoderFactory.Create(выбранный протокол, ...)`
→ `Decoder` → `WheelService`. При отключении сессия выбрасывается целиком; повторное подключение
создаёт новую (у `WheelState` и декодеров нет сброса — переиспользовать нельзя).

**Гейт T3:** после тапа по колесу в списке приложение показывает состояние «подключено» и растущий
счётчик принятых байт/кадров. Требует включённого колеса — **тест на железе, согласовать с
пользователем**; если колеса нет под рукой, остановиться и сообщить.

### Фаза 4 — Экран телеметрии

1. Переход на второй экран после успешного подключения (`Navigation.PushAsync`), кнопка «Отключить»
   возвращает на экран скана.
2. Сетка в две колонки `краткое имя : значение`, прокручиваемая, моноширинный шрифт для значений.
   Поля (из `TelemetrySnapshot`), именно в таком порядке:

   `speed` SpeedKmh · `pwm` Pwm · `pwm max` MaxPwm · `V` VoltageV · `A` CurrentA ·
   `phase A` PhaseCurrentA · `W` PowerW · `bat` Battery · `t°` TemperatureC · `t2°` Temperature2C ·
   `top` TopSpeedKmh · `trip` WheelDistanceKm · `total` TotalDistanceKm · `from start` DistanceFromStartKm ·
   `angle` Angle · `charge` ChargingStatus · `sleep` SleepTimerSec · `alarm` WheelAlarm ·
   `alert` Alert · `model` Model · `fw` Version · `type` WheelType ·
   `bms1` MinCell/MaxCell/CellDiff · `bms2` MinCell/MaxCell/CellDiff

3. Подписка на поток `WheelService.Telemetry`, отрисовка **каждого** снэпшота через
   `MainThread.BeginInvokeOnMainThread`. Троттлинг не нужен — см. §5.1.
4. Отписка при уходе с экрана — обязательно, иначе подписка живёт всю сессию.

### 5.1. Частота обновления — измерено, потолок задаёт колесо

На живом Sherman L: **данные 5,0 Гц, сырые BLE-кадры 23,5 Гц** (~4,7 кадра на один пакет
телеметрии). Записи подтверждают то же для обоих протоколов: MTen3 — 29 строк за 6,9 с (4,2 Гц),
Sherman L — 30 строк за 5,9 с (5,1 Гц); столько же получалось и через Windows-клиент.

**Пять герц — темп прошивки колеса, а не ограничение приложения.** Ни «сырые» вызовы, ни обход
биндингов, ни отдельная реализация транспорта этого не изменят: чаще колесо просто не отправляет.
Что со стороны телефона действительно помогает — запрос `RequestConnectionPriority(High)` после
подключения: он не добавляет пакетов, но убирает ожидание между готовым пакетом и его приёмом,
то есть уменьшает задержку показаний. Запрос удовлетворяется (в логе `Ble.HighPriorityRequested True`).

Следствие для тревог: чувствительность к всплескам ШИМ обеспечивается не частотой опроса, а тем,
что движок берёт **максимум за окно** ([План 4](android-plan-4-alerts-and-background.md), §3.1), —
ни один пришедший снэпшот не теряется, даже если экран перерисовать не успел.

**Гейт T4:** живые цифры с колеса на экране; при покачивании колеса рукой меняются `speed`,
`angle`, `A`. **Тест на железе с пользователем.**

### Фаза 5 — Устойчивость и документация

1. Проверить: отключить колесо / отойти → приложение не падает, показывает потерю связи и даёт
   вернуться к скану и подключиться снова.
2. Обновить [AGENTS.md](../../AGENTS.md): новый проект в структуре, как собирать и деплоить на телефон.
3. Переписать этот файл под то, что получилось (что сделано, где что лежит, известные ограничения).

отключился → подключился снова.

## 6. Подводные камни

- **CCCD `0x2902`** — см. Фазу 3. Симптом пропуска: подключились, ошибок нет, `DataReceived` молчит.
- **Геолокация на Android ≤ 11** должна быть включена в системе, иначе `startScan` не вернёт
  ни одного результата и не сообщит об ошибке.
- **`gatt.Close()`** обязателен при отключении.
- **Скан во время подключения** мешает установлению связи — останавливать до `ConnectAsync`.
- **MAC в `GetRemoteDevice` — только верхний регистр**, иначе `IllegalArgumentException`.
- **Veteran-распаковщик собирает пакет из нескольких кадров и сбрасывает недособранное по таймауту
  реального времени.** Кадры должны идти подряд, как приходят по BLE. Проявляется, только если
  кто-то вздумает искусственно замедлить подачу байт.
- **У Begode/MTen3 более старый Bluetooth-стек**; на Windows это потребовало ретраев GATT-discovery
  (см. комментарии в `WindowsBleClient`). На Android проблем быть не должно — но если discovery
  падает с первого раза, лечится тем же: повтор через ~500 мс.
- **PWM у Begode считается программно** (аппаратного значения нет) — это нормально, поле всё равно
  показывается.
- Названия полей `TelemetrySnapshot` — сырой fixed-point, у большинства есть парное «человеческое»
  свойство (`SpeedRaw` / `SpeedKmh`). В UI выводить человеческие.
