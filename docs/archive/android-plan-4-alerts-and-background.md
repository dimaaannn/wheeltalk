## 1. Каркас: поток телеметрии и сессия в ядре

### 1.1. Rx как способ передачи

Телеметрия передаётся **непрерывным потоком** (`System.Reactive`), а не событием на каждое
обновление. Решение о тревоге принимает подписчик, применяя к потоку фильтры, а не источник.

Из плана 1 в ядре уже есть поток снэпшотов. Здесь к нему добавляются:

```
IObservable<TelemetrySnapshot>   // поток телеметрии (из плана 1)
IObservable<ConnectionState>     // состояние соединения: Disconnected/Connecting/Connected/Reconnecting
IObservable<AlertState>          // результат работы движка тревог (§3)
```

Планировщик/время во всех операторах — через `TimeProvider` или явный `IScheduler`, никогда не
через `DateTime.Now` и не через дефолтные планировщики Rx: иначе логика не проверяется тестами
(§6). Подписки в приложении обязаны отписываться при уходе страницы — утечка подписки на живой
поток телеметрии означает работу невидимых обработчиков всю сессию.

### 1.2. `WheelSession` — владелец соединения

Сессия (BLE-клиент, `WheelState`, декодер, `Decoder`, `WheelService`) переезжает в ядро и
перестаёт зависеть от жизненного цикла UI. Отвечает за:

- подключение и отключение по адресу и протоколу;
- пересоздание внутренностей при каждом новом подключении (`WheelState` и декодеры не имеют
  сброса — переиспользовать нельзя);
- состояние соединения как поток;
- **переподключение** (§2).

UI и Android-сервис подписываются на сессию; их уход не рвёт соединение.

### 1.3. Конфигурация — через `IOptions`

Схема конфигурации (дефолты в ресурсах + пользовательский файл поверх, отдельные настройки для
каждого колеса, мутабельные классы опций, без `IOptionsMonitor` и без валидации) описана в
[Плане 1, §3](android-plan-1-base-app.md) и здесь не повторяется.

Классы этого плана — `AlertOptions` (§3.5) и `ConnectionOptions` (интервал переподключения).
`AlertOptions` — **настройка уровня колеса**: пороги у разных колёс разные, и храниться они должны
в секции конкретного колеса.

## 2. Переподключение и работа в фоне

Это самая важная часть плана — важнее самих тревог. Приложение, пока оно запущено, **всегда**
стремится к состоянию «подключено».

### 2.1. Поведение

| Событие | Поведение |
|---|---|
| Запуск приложения | Сразу пытается подключиться к последнему успешному колесу (адрес и протокол — в `usersettings.json`, пишет их `UserSettingsStore`; `Preferences` в приложении не используются нигде). Скана при этом нет |
| Первый запуск, колеса в памяти нет | Экран предлагает сканирование (кнопка в меню, см. [План 3](android-plan-3-main-screen.md)) |
| Обрыв связи | Немедленно начинает повторные попытки с интервалом ~5 с, **бесконечно**, пока приложение живо |
| Колесо выключено и недоступно | Попытки продолжаются бесконечно. На экране остаются последние актуальные значения до обрыва, поверх них — заметный индикатор отсутствия связи с возрастом данных; интерфейс при этом не блокируется (подробности — в [Плане 3](android-plan-3-main-screen.md), §1.6) |
| Пользователь выбрал другое колесо | Текущая сессия закрывается, новая привязка сохраняется |
| Явный выход (двойное «назад») | Единственный способ прекратить: сессия закрывается, сервис останавливается, активности закрывает `FinishAffinity()`. Процесс при этом не убивается — его добирает система |

Логика переподключения — **в ядре** (`WheelSession`), в приложении только следствия: показать
состояние и удержать сервис живым. Ретраи не должны множиться: одна активная попытка в момент
времени, каждая новая — только после завершения предыдущей.

### 2.2. Android-сервис

Соединение обязано жить вне Activity, поэтому нужен foreground-сервис: `[Service]` с
`StartForeground(...)`, стартует при первом подключении, останавливается при явном выходе.

**Ограничение платформы:** foreground-сервис на Android 8+ **обязан** иметь постоянное уведомление —
без него система убьёт процесс через считанные минуты после сворачивания, и суточная работа в фоне
станет невозможна.

В этой итерации уведомление постоянное и **текстовое**: канал минимальной важности, без звука и
вибрации, одна строка состояния, тап открывает приложение. Показ телеметрии прямо в уведомлении
(как в оригинальном WheelLog — скорость, заряд, ШИМ, кнопки) — **в план на будущее**; разметка и
поведение того уведомления описываются в рамках [Плана 2](android-plan-2-ui-analysis.md).

Манифест и разрешения:
- `FOREGROUND_SERVICE` (API 28+);
- `android:foregroundServiceType="connectedDevice"` + `FOREGROUND_SERVICE_CONNECTED_DEVICE` —
  обязательны с API 34; на нашем API 30 не нужны, но объявить сразу, иначе приложение не заработает
  на современных телефонах;
- `POST_NOTIFICATIONS` (runtime, API 33+);
- `VIBRATE`.

**Doze и «убийцы» вендоров.** Blackview, как и большинство китайских прошивок, выгружает фон
агрессивно. ~~Предусмотреть кнопку, открывающую системный диалог отключения оптимизации батареи
(`Settings.ActionRequestIgnoreBatteryOptimizations`).~~ Кнопки в коде нет, и она не понадобилась:
полевые прогоны 28.07.2026 фон пережил **без** исключения из экономии батареи, а заводить ручку
под сбой, который не воспроизвёлся, — против собственного правила серии (план 11, «сбой должен
быть правдоподобным»). Если долгий прогон (план 5, §6.5) покажет обратное — пункт вернуть.
Автозапуск-менеджер прошивки программно не обходится — это пункт инструкции пользователю.

**WakeLock** заранее не закладывать. Если на суточном прогоне окажется, что при погашенном экране
кадры рвутся или идут рывками — взять `PARTIAL_WAKE_LOCK` на время соединения и перепроверить.

### 2.3. Гейт T1 — сутки в фоне (главный гейт плана)

Подключиться к колесу, свернуть приложение, погасить экран и оставить на **24 часа**. Колесо при
этом уснёт и, возможно, выключится — это часть проверки: приложение обязано всё это время
продолжать попытки и восстановить связь, когда колесо снова включат.

```
adb logcat -c
adb shell input keyevent 3 && adb shell input keyevent 26      # свернуть, погасить экран
adb shell dumpsys activity services com.wheeltalk.app          # сервис числится foreground
adb logcat -d | grep -Ec "Frame|Reconnect"                     # активность продолжается
adb shell dumpsys battery unplug && adb shell dumpsys deviceidle force-idle   # проверка Doze
adb shell dumpsys deviceidle unforce && adb shell dumpsys battery reset
```

Промежуточная отсечка на 15 минутах — чтобы не ждать сутки ради очевидной ошибки. **Тест на
железе, с пользователем.** Без прохождения T1 к тревогам не переходить.

**Статус на 30.07.2026: гейт не пройден, но половина ответа есть.** Фон проверен ~5 минутами на
полевом выходе, а к тревогам при этом перешли — правило нарушено, см. оговорку в шапке. Замер того
же дня ([план 15](../android-plan-15-background-survival.md)) показал, что процесс и служба живут
часами, связь держится, а приложение — в белом списке батареи; суточный прогон с живым колесом
по-прежнему за выездом и висит в [плане 5, §6.5](android-plan-5-ride-logging.md).

## 3. Движок тревог

Тревога вычисляется в ядре из потока телеметрии. Каналов **два, они независимы и звучат
по-разному**: ШИМ — агрессивно и нарастающе, скорость — мягко и редко.

### 3.1. Как берётся значение: пиковое, а не последнее

Единичное превышение обязано поднять тревогу — иначе кратковременный всплеск ШИМ, который как раз
и предшествует срыву, будет пропущен между кадрами.

Поэтому в расчёт идёт **максимум за скользящее окно длиной `Hold`** (по умолчанию 500 мс, окно
сдвигается с шагом `Step` — 100 мс), а не последний пришедший кадр. Следствия, которые и
требовались:

- одиночный выброс держит тревогу ещё `Hold` после того, как значение упало;
- дребезг вокруг порога не превращается в тарахтение — тревога уже удерживается;
- отдельные пороги «входа» и «выхода» не нужны: удержание делает их работу.

`Hold` и `Step` — параметры конфига (`Alerts:Hold`, `Alerts:Step`), общие для обоих каналов.
В плане они значились одним параметром `AlertHold`; в коде их два — шаг окна нужен отдельно
и цепочке (§3.6), и счётчику молчания (§3.4).

### 3.2. ШИМ: нарастающая тревога между двумя уставками

Два порога, между которыми тревога плавно усиливается:

- **нижняя уставка** — начало слышимых, но не критичных предупреждений;
- **верхняя уставка** — максимальная тревога, непрерывный сигнал.

Ядро отдаёт **интенсивность 0..1**: 0 — ниже нижней уставки, линейный рост между уставками,
1 — на верхней и выше. Как именно интенсивность звучит — дело приложения (§5.1); ядро про звук
не знает.

### 3.3. Скорость: мягкое напоминание

Двоичное состояние «превышена / нет». Пока держится — ненавязчивый сигнал с интервалом
`SpeedRepeatInterval` (по умолчанию 5 с, не 10 000 мс из первой редакции). Никакого нарастания.

Пока активна тревога по ШИМ, сигнал скорости **не звучит**: колесо на пределе — не тот момент,
чтобы мешать вторым звуком. (Параметр конфига, по умолчанию включено.)

### 3.4. Снятие тревоги — гарантированное

Тревога снимается, когда **значение ниже уставки И истекло `Hold`**. Два требования к
реализации, оба обязательны:

- снятие управляется **временем, а не приходом кадров**: реализация на `IScheduler`, а не
  «пересчитаем на следующем снэпшоте» — иначе звук останется висеть навсегда, когда кадры
  кончились;
- поток тревог отдаёт **состояние**, а не команды «включи/выключи». Приложение звучит ровно
  столько, сколько состояние активно; пропущенное событие не может оставить сигнал включённым.

### 3.6. Как это ложится на Rx

Движок тревог — **цепочка операторов над потоком телеметрии**, а не самодельный конечный автомат
с таймерами. Rx здесь закрывает ровно те три вещи, которые в этой задаче сложнее всего написать
руками: скользящее окно, удержание и снятие при обрыве.

Опорная идиома для обоих каналов — **скользящее окно с шагом**, в которое `Merge`-ом влит поток
разрывов связи (вид после пересмотра 29.07.2026, см. §3.4; код — `AlertEvaluator.cs:35-68`):

```
telemetry.Buffer(Hold, Step, scheduler)   // окна длиной Hold, каждые Step
         .Merge(drops)                    // разрывы связи — в тот же разбор, не вторым потоком
         .Scan(...)                       // счётчик пустых окон: пусто — держим прежнее состояние,
                                          //   молчание дольше Silence — отпускаем; обрыв обнуляет удержанное
         .Select(...)                     // Max по окну → интенсивность 0..1 по уставкам
         .DistinctUntilChanged()
```

Почему именно так:

- `Max` по окну даёт **пиковое** значение — одиночный выброс не теряется между кадрами (§3.1);
- окно, съезжая, само роняет значение через `Hold` после того, как превышение прекратилось —
  удержание получается бесплатно, без отдельного таймера;
- ~~**пустое окно даёт ноль** — при обрыве связи или выключенном колесе кадры перестают приходить,
  и тревога гаснет сама, ровно как требует §3.4. Это и есть та «отмена при обрыве», которую иначе
  пришлось бы городить вручную и обязательно где-нибудь забыть;~~ **пересмотрено 29.07.2026:**
  пустое окно — «пока нечего сказать», состояние держится, пока молчание не затянулось на
  `Silence`. Что вскрыло исходное поведение и почему оно опасно — §3.4;
- **разрывы связи вливаются `Merge`-ом в общий `Scan` и обнуляют удержанное состояние.** Двумя
  сложенными потоками это работать не может: «Стоп» вставлял «тихо», а окна следом продолжали
  выдавать удержанную тревогу, и она возвращалась через сотню миллисекунд. Сказать «тихо» и
  продолжать помнить обратное — нельзя;
- `DistinctUntilChanged` не даёт потоку тревог дёргаться на каждом окне.

Канал скорости — та же цепочка с `Any(v => v > threshold)` вместо `Max`. Периодичность мягкого
сигнала (`SpeedRepeatInterval`) — уже в приложении: ядро отдаёт состояние, приложение решает, как
часто его озвучивать.

~~Дополнительно поток тревог сбрасывается в ноль по состоянию соединения (`Disconnected`/
`Reconnecting`) — подстраховка на случай, если кадры перестали приходить не полностью, а
частично.~~ После пересмотра это не подстраховка, а **основной механизм** снятия тревоги при
обрыве — см. пункт про `Merge(drops)` выше.

Функция `Intensity` (значение → 0..1 по уставкам) стала **публичной**: по ней плеер записанных
поездок рисует тревожные полосы, не поднимая настоящую тревогу, а вторая копия формулы
разошлась бы с первой при первой же правке порогов.

Важное следствие для UI: после обрыва на экране остаются последние значения — например, ШИМ 85 %, —
а тревога при этом молчит, и это правильно. Объясняет расхождение именно индикатор отсутствия
связи (План 3, §1.6): цифры историчны, тревожиться не о чем.

Всё это проверяется на `TestScheduler` без единого реального ожидания: виртуальное время
прокручивается вперёд, и видно, что происходит с окном на любой миллисекунде (§6).

## 4. Консольное приложение

Консоль — инструмент первичной отладки, а не продукт: правится свободно, исходя из того, что
нужно проверить повторно. Обязательное требование одно — она должна собираться и работать после
изменений API ядра.

Вывод тревог в консоль (подписка на тот же поток, печать смены состояния строкой) делать **только
если понадобится отлаживать движок без телефона** — например, прогоном записанной поездки. Как
самоцель «доказать платформонезависимость» это не нужно: её доказывают тесты ядра.

## 5. Реакция на тревогу в приложении

Все реакции — реализация, живут в `WheelTalk.App` и включаются подпиской на `IObservable<AlertState>`.

### 5.1. Звук

Два разных сигнала, чтобы на слух, не глядя на экран, было понятно, что именно происходит.

**ШИМ — нарастающий.** Интенсивность из §3.2 (0..1) отображается в звук так, чтобы приближение к
верхней уставке слышалось как нарастание тревоги; на интенсивности, близкой к 1, —
**непрерывный сигнал** без пауз. ~~Пауза между сигналами сжимается от ~700 мс при интенсивности
0 до нуля при 1, тон становится выше и громче. Соответствие «интенсивность → пауза/тон» живёт в
приложении и подбирается на слух.~~ **Пересмотрено:** свои пропорции звучали хуже и дребезжали
на границе сплошного — взяты пропорции оригинала: **период постоянный, 200 мс, растёт только
длина тона — 20 → 200 мс**, и на потолке сигнал сливается в сплошной сам, без отдельного режима.
Соответствие «интенсивность → ритм» переехало из приложения **в ядро под тесты**
(`WheelTalk.Core/Alerts/AlertRhythm.cs`, `AlertRhythmTests`). Разбор пяти заходов, которые к
этому привели, — [план 6, §10.5](android-plan-6-settings-and-chrome.md).

**Скорость — мягкий.** Один короткий негромкий сигнал раз в `SpeedRepeatInterval`, тон заметно
ниже и спокойнее, чем у ШИМ. Не звучит, пока активна тревога по ШИМ (§3.3).

**Гарантия тишины.** Звук привязан к состоянию потока: как только тревога снята, воспроизведение
прекращается немедленно, включая непрерывный сигнал. Отдельно проверить, что звук гаснет при
обрыве связи, при уходе приложения и при выходе — не должно оставаться ни одного пути, на котором
сигнал остаётся включённым.

- Сейчас — генератор тона (`ToneGenerator`), без файлов-ресурсов. Проигрывание mp3 — **в план на
  будущее** (когда появится подобранный сигнал).
- Играть по каналу будильника с соответствующими `AudioAttributes`: сигнал **обязан пробиваться
  через беззвучный режим и «Не беспокоить»**.
- Музыка в наушниках не прерывается — сигнал играет поверх. Приглушение (duck) сделать
  **опциональным** параметром в конфиге, по умолчанию выключено. **Приглушение не реализовано —
  пункт открыт.**
- Работает из сервиса, а не из UI: при погашенном экране и в фоне звук обязателен.
- ~~Переключатель «Звук тревог» на заглавном экране, состояние — в `Preferences`.~~ Стало:
  каналы тревоги — три настройки `AlertSignals:Sound`/`Vibration`/`Torch` на странице
  «Предупреждения», хранятся слоями настроек (план 6); `Preferences` не используются нигде.

### 5.2. Вибрация

Короткая серия на время тревоги (`Vibrator`, разрешение `VIBRATE`).

### 5.3. Моргание экрана

> **Пересмотрено планом 7 и переносом на голый Android.** Не рамка по периметру, а **две
> горизонтальные полосы** сверху и снизу (`AlertBarsDrawable`): рамка росла внутрь ровно туда,
> где у лент стоят цветные полосы шкал, и на предельном ШИМ гасила оба прибора. Частота мигания
> **постоянная — 3 Гц** (WCAG 2.3.1), а не 1→4 Гц по интенсивности; толщина от интенсивности —
> в силе. **Недоделка кода:** настройка `Alerts:MaxBorderCoverage` осиротела — полосы берут
> константу `0.096f` (`AlertBarsDrawable.cs`), ползунок на странице настроек есть, но ни на что
> не влияет. Это нарушение правила плана 6, §0 («каждая настройка должна что-то менять»).

Только при **включённом экране и приложении на переднем плане** — рисовать поверх чужих экранов
нельзя (потребовало бы `SYSTEM_ALERT_WINDOW`, в эту итерацию не входит).

Мигает **красная рамка по периметру экрана**, а не заливка: показания остаются на месте и не
конкурируют с тревогой за внимание.

- **Толщина рамки растёт вместе с интенсивностью** (§3.2): у нижней уставки — тонкая полоска по
  краю, у верхней — максимальная. Предел задаётся конфигом как доля экрана (`MaxBorderCoverage`),
  чтобы рамка никогда не съела площадь с цифрами.
- Рамка **мигает**, частота растёт с интенсивностью (примерно от 1 Гц у нижней уставки до 4 Гц у
  верхней). Тревога по скорости рамку не мигает — рисует тонкую жёлтую, статичную.
- **Текст и цифры не мигают и не меняются** — ни цвет, ни размер, ни прозрачность, ни положение.
  Рамка растёт внутрь от края и никогда не перекрывает показания.
- Цвета, частоты и предельная толщина — предварительные, пользователь проверит в реальных
  условиях; **пометить как подлежащее подбору**.
- Останавливать таймер в `OnDisappearing`, иначе он будет работать впустую.
- Принудительная яркость экрана — **пока не трогаем**, вынести в список «подумать».

### 5.4. Фонарик телефона

Мигать вспышкой камеры (`CameraManager.SetTorchMode`) синхронно с экраном и **только по тревоге
ШИМ** — мягкое напоминание о скорости фонариком не сопровождается. Отдельного разрешения
не требует. Обязательно гасить при снятии тревоги, при выходе и при сбое — фонарик, оставшийся
включённым, сажает батарею и греет телефон.

### 5.5. Фара колеса — не делаем

Мигание фарой самого колеса из плана **исключено** (решение пользователя): чтобы мигать, надо слать
команды по BLE дважды в секунду ровно в тот момент, когда канал нужен для телеметрии, а состояние
света приходится запоминать и восстанавливать. Перенесено в список будущего — вернёмся, если
появится способ сделать это чище.

## 6. Проверка

**Симулятор данных — только для автотестов**, в приложение не встраивать. Тесты в
`WheelTalk.Tests`: синтетический поток снэпшотов (пилообразный ШИМ, ступеньки скорости, одиночные
выбросы, обрыв потока) подаётся в движок тревог на `TestScheduler`/`FakeTimeProvider`, проверяются:

- **одиночное превышение** между кадрами поднимает тревогу и удерживает её ровно `Hold`;
- ~~тревога **гаснет сама**, если поток телеметрии прекратился, — через `AlertHold`, без единого
  нового кадра;~~ пересмотрено вместе с §3.4: отсчёты реже окна тревогу **не гасят**, замолчавший
  навсегда поток отпускает её через `Silence`, а разрыв связи — сразу;
- интенсивность ШИМ: 0 ниже нижней уставки, линейный рост между уставками, ровно 1 на верхней и выше;
- сигнал скорости повторяется с заданным интервалом и подавляется, пока активна тревога по ШИМ;
- снятие происходит только при выполнении обоих условий — значение ниже уставки **и** истёкшее
  удержание.

Это ровно тот случай «сложной логики», для которого AGENTS.md требует тесты.

Бесконечные попытки восстановления, автоподключение к последнему колесу при старте, выход двойным

**Гейт:** выключить колесо на минуту и включить снова — приложение восстановило связь само,
без действий пользователя. **На железе.**

### Фаза 4 — Движок тревог в ядре
`AlertEvaluator` + `AlertOptions` + тесты + вывод в консоль.
**Гейт:** тесты зелёные; консоль печатает смену уровня на записи/симуляции.

### Фаза 5 — Реакции
Звук (два разных сигнала), вибрация, моргание фона, фонарик телефона.
**Гейт:** на реальном колесе при разгоне выше отладочных порогов — сигнал ШИМ слышен в кармане при
погашенном экране и **нарастает** по мере приближения к верхней уставке, на переднем плане мигает
фон и фонарик; мягкий сигнал скорости звучит отдельно и молчит, пока идёт тревога по ШИМ. Отдельно
проверить **тишину**: сбросить газ — сигнал пропадает через полсекунды; выключить колесо посреди
тревоги — сигнал пропадает сам. **На железе, с пользователем.**
