# План 22. Инсет верхних уведомлений и управляемый реплей для агентских прогонов

> **Статус: §1 и §2 сделаны, оба 03.08.2026** — §1 записан со слов владельца 02.08.2026, по
> скриншоту с эмулятора. **Ветка:** `dev`. Командный вход закрыт и описан в AGENTS.md («Как
> гонять приложение без колеса»); план закрыт целиком.

## 1. Уведомления у верхней кромки — под системной строкой

**Симптом (скриншот 02.08.2026, реплей на эмуляторе):** полоса тревоги колеса
(«Unknown Alert 482.00 …») прижата к самому верху, и системные часы со значками лежат прямо на
её тексте — первая строка не читается.

**Причина.** Edge-to-edge отдаёт верхний инсет **панели** (`MainActivity` → `PanelChrome.TopInset`
→ тень и отступ канвы), а `AlertStrip` — первый ребёнок колонки `MainScreenView` с собственным
паддингом 2 dp (`AlertStrip.cs:28`) и про инсет не знает: появляясь, она встаёт под статус-бар.

**Правка.** Полоса, когда видима, добирает верхний паддинг на высоту инсета: `MainScreenView`
уже собирает экран и может отдать инсет полосе тем же путём, каким `MainActivity` отдаёт его
панели (значение у активности уже есть — `_topInsetPx`). Правило владельца — **общее**: любой
элемент, прижатый к верхней кромке, обязан компенсировать системную строку; сейчас таких два —
полоса тревоги и панель, панель уже умеет.

Проверка — на стенде: `LabSettings.WheelAlarm` включает полосу, «Панель под системной строкой»
даёт ненулевой инсет; скриншот до/после.

**Смежный записанный долг** ([handover](handover.md), хвост): полоса задумана накладкой поверх
панели, а не членом разметки, сдвигающим её вниз. Решается отдельно; паддинг-правка ему не
мешает и не отменяет его.

**Сделано 03.08.2026.** `AlertStrip.TopInset` (`WheelTalk.Dashboard.Droid/Screen/AlertStrip.cs`) —
верхний паддинг сверх базовых 2 dp, правится только при изменении значения (тот же приём, что у
`Show`). Инсет нулевой — паддинг равен прежнему, полоса выглядит как раньше.

Правило владельца общее — оба места, где верхний инсет становится известен активности, отдают его
и полосе:
- `MainActivity.OnCreate` — тот же коллбэк `EdgeToEdge.Apply`, что уже кормил `_topInsetPx` панели
  (`Main/MainActivity.cs`): теперь пишет и в `_alertStrip.TopInset`.
- `LabActivity.BeforeFrame` — за каждый кадр, тем же значением и под тем же условием, что уже
  идёт в `PanelChrome.TopInset` (`_settings.UnderSystemBar ? _barInset : 0`): стенд решает, стоит
  ли экран под баром сейчас, одним переключателем на оба элемента, а не двумя независимыми.

**Чем проверено:** `dotnet build` обоих проектов (`WheelTalk.Droid`, `WheelTalk.Lab.Droid`) — без
ошибок, без новых предупреждений. Один прогон `WheelTalk.Lab.Droid` на эмуляторе (Pixel 5, API 32),
режим «экран целиком» + «Тревога колеса»: скриншот при «Панель под системной строкой» включено
(инсет ненулевой) показывает заметный зазор над текстом полосы; скриншот при выключенном тумблере
(инсет нулевой) — текст вплотную к соседней строке ровно как до правки. На боевом приложении вживую
не проверялось (эмулятор не изображает статус-бар поверх контента так же требовательно, как
реальный телефон) — первый же выезд/прогон на телефоне закрывает этот хвост.

## 2. Управляемый реплей: команды вместо свайпов по таймеру

**Симптом.** Агентские проверки на эмуляторе водят приложение «руками» — `adb shell input
swipe/tap` по координатам и таймингу. Это хронически промахивается: шторка сама закрывается
через 5 секунд (ловушка уже записана в handover), между командами adb проходит больше, чем ждёт
UI, координаты плывут между конфигурациями, а при двух подключённых устройствах касание может
уйти не туда. Каждый промах — потерянный прогон и повторная сборка вывода.

**Сделано сразу (02.08.2026): пуск — по тапу на плашку.** Плашка «Запись готова» и так стоит на
переднем плане, когда реплей готов, — решение владельца: действие сидит прямо на ней
(`OnLinkBadgeTapped` при `IsReplay` зовёт тот же путь, что кнопка «Пуск»; текст плашки сменён на
«нажмите для пуска»). Это закрывает самый частый промах — свайп шторки ради одной кнопки — и
для человека, и для агента: плашка — крупная цель со стабильным местом.

**Сделано 03.08.2026: командный вход без касаний** — для «стоп», экранов и всего, где цель не
плашка. `MainActivity` уже `LaunchMode.SingleTop`; extras разбираются, когда `_transport.IsReplay`:

```
adb shell am start -n com.wheeltalk.droid/.MainActivity --es replay start
adb shell am start -n com.wheeltalk.droid/.MainActivity --es replay stop
adb shell am start -n com.wheeltalk.droid/.MainActivity --es open rides|data|settings|sheet
```

Имя компонента в командах — не то, что стояло в черновике плана (`.Main.MainActivity`): у
активности не было `Name`, и .NET for Android давал ей имя из crc64-хеша пространства имён
(`crc64b98d88d13fa3ef38.MainActivity` в собранном манифесте) — обе записи черновика ответили бы
«Activity class does not exist». Активности задано явное
`Name = "com.wheeltalk.droid.MainActivity"`: имя, на которое ссылаются снаружи, — контракт, а не
деталь сборки, и хешу в документации не место, он молча разъедется при переименовании.

- `replay start|stop` **не тумблер**: `ReplayToggleAsync` (кнопка шторки) и команда сходятся в
  одном `ReplaySetRunningAsync(bool run)`, который сверяет желаемое состояние с
  `_session.CurrentState` и ничего не делает, если оно уже такое. Кнопка приходит туда с
  «наоборот, чем сейчас», команда — с явным `start`/`stop`. Иначе `start` на уже идущем реплее
  останавливал бы его — то есть промахивался бы ровно так же, как `input tap`, и вход не имел бы
  смысла. Второй логики нет: за развилкой те же `Connect`/`Disconnect`+`ClearReadings`.
- `open …` зовёт `OpenScreen` (`rides`/`data`/`settings`) и `_sheet.Toggle()` (`sheet`) — то, что
  раньше доставалось свайпами.
- Extras разбираются **на двух путях**: `OnNewIntent` (активность на вершине) и `Intent` в
  `OnCreate` (приложение подняли самой командой, либо экран пересоздан). `SetIntent` в
  `OnNewIntent` намеренно не зовётся — extras разбираются тут же и больше никем не читаются, а
  подменённый `Intent` пережил бы пересоздание Activity и повторил бы команду при восстановлении.
- Ветка регистрируется **только при реплей-транспорте** (`ITransport.IsReplay`): на живом колесе
  внешнего входа не существует — не спрятан, а не создан, тем же правилом, что кнопка «Пуск»
  в шторке.
- Непонятое значение ничего не ломает: пишется `Ui.CommandUnknown`, а сам факт команды — `Ui.Command`,
  чтобы по `adb logcat -d -s WheelTalk` было видно, дошла она или нет.
- Стенд (`WheelTalk.Lab.Droid`) при необходимости получает такой же вход отдельным шагом —
  сценарий/позиция/вариант панели; решить по факту первого промаха, не впрок. **Не сделано** и
  делать впрок не нужно.

Врезка в AGENTS.md («Как гонять приложение без колеса», рядом с «Как проверять Android-приложение
на телефоне») написана: агентам пользоваться командами, `input swipe/tap` остаётся для проверки
самих жестов.

## Проверка

По правилу ограничения циклов: §1 — компиляция + один прогон стенда с двумя скриншотами
(полоса при нулевом и ненулевом инсете); §2 — компиляция + один прогон на эмуляторе, где весь
сценарий (пуск реплея, шторка, «Поездки», стоп) пройден командами без единого касания. Publish
не делается.

**Чем проверен §2 (03.08.2026):** `dotnet build WheelTalk.Droid/WheelTalk.Droid.csproj` — без
ошибок и без новых предупреждений; плюс сверка имени компонента по собранному
`obj/Debug/net10.0-android/android/AndroidManifest.xml` — там стоит ровно
`com.wheeltalk.droid.MainActivity`, то есть то, что написано в командах. Эмулятор для этой сверки
не нужен, и именно она ловит «Activity class does not exist» до прогона.

**Вживую не проверено:** эмулятора в `adb devices` не было, а поднимать его правило ограничения
циклов не велит. Что смотреть на первом же прогоне:

- сами команды — весь сценарий (пуск реплея, шторка, «Поездки», стоп) без единого касания;
- **`--es open sheet` при холодном старте**: приложение поднимается той же командой, поэтому
  `_sheet.Toggle()` зовётся из `OnCreate` — до первого layout pass, — и шторка может не показаться.
  На горячем пути (`OnNewIntent`) этого вопроса нет. Впрок не чинится: `QuickSheet` умеет ждать
  раскладки (`GlobalLayoutOnce`), так что вполне возможно, что чинить нечего.

**Чем проверен §1 (03.08.2026):** оба `dotnet build`; один прогон `WheelTalk.Lab.Droid` на
эмуляторе (Pixel 5, API 32 — в `adb devices` было пусто, эмулятор поднят один раз этим же заходом).
Подробности и скриншоты — по месту симптома, в §1.
