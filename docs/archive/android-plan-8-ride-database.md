>
> Код живёт в новом проекте `WheelTalk.Storage`. Гейт фазы 2 пройден на **настоящей поездке**
> Sherman L: тысяча с лишним строк, записанных в базу и прочитанных обратно, дали побайтово тот же
> CSV, что пишется прямо с колеса. Гейт фазы 1 пройден на реплее в эмуляторе — см. §6.
>
> ~~Пока нет фазы 3, выгрузка последней поездки живёт кнопкой на странице «Запись».~~ Фаза 3
> сделана, и временная кнопка ушла: экспорт живёт в списке поездок (`RidesActivity`), а на
> «Записи» стоит кнопка «Поездки», которая туда ведёт. Читаемость CSV чужими сервисами — прежняя
> и единственная причина держать формат посимвольно.

CSV хорош ровно одним: его понимают чужие сервисы. Всем остальным он плох — у файла нет самой
сущности «поездка» (она подразумевается именем), нельзя спросить «покажи поездки за неделю»,
нельзя дописать итоги задним числом, а любой график требует перечитать файл целиком.

Поэтому: база — то, куда пишем, CSV — то, что отдаём наружу.

## 0. Правила

- [AGENTS.md](../../AGENTS.md) — читать до первой правки.
- **Формат экспорта не изобретается заново.** `WheelTalk.Core/Logging/RideLog.cs` и его тесты
  уже описывают формат посимвольно; экспорт обязан идти через них, иначе появится второй
  ответ на вопрос «как выглядит строка».
- Сырой дамп — **не в базе**. Это поток байт для отладки, его читает `ReplayTransport`, и
  файл для него правильное место.

## 1. Зафиксированные решения

| Параметр | Решение |
|---|---|
| Что в базе | Телеметрия поездок и пользовательские настройки ([план 6](android-plan-6-settings-and-chrome.md) §2.2). Файл, версию схемы и таблицу `wheel` заводит **этот** план — план 6 добавляет свою таблицу поверх готовой базы |

| Колесо | Отдельной таблицей с `id`. На неё же ссылаются пользовательские настройки ([план 6](android-plan-6-settings-and-chrome.md) §2.2) — иначе «колесо» будет означать разное в двух местах одной базы |
| Экспорт | Через `RideLog` — тот же формат, что писали раньше, вплоть до CRLF и констант в `torque`/`roll`/`mode` (§2.2) |
| Очистка старых данных | **Отложено** — см. §5. Отметка поставлена: без неё база растёт вечно |
| Библиотека | `Microsoft.Data.Sqlite` и SQL руками. ORM тут нечего делать: таблиц две, запросов пяток, а лишняя зависимость в приложении, которое пишет пять строк в секунду, — это цена без выгоды |
| Где живёт код базы | В новом проекте `WheelTalk.Storage` (`net10.0`), на который ссылаются приложение, консоль и тесты. В приложении его держать нельзя: `WheelTalk.Tests` собирается под `net10.0-windows` и на `net10.0-android` сослаться не может — схема, миграция и чтение для экспорта оказались бы вне досягаемости тестов. В ядре — не хочется: оно нарочно выделено переносимым, и тащить туда SQLite значит разменять эту переносимость |

## 2. Схема

Три таблицы: колесо, поездка, телеметрия. Поездка появляется в момент старта записи и
закрывается в момент остановки — именно то, чего у файла не было.

```sql
CREATE TABLE wheel (
    id        INTEGER PRIMARY KEY,
    mac       TEXT NOT NULL UNIQUE,
    name      TEXT,                 -- как его называет владелец; задавать пока негде, но список поездок без имени читается плохо
    protocol  TEXT NOT NULL
);

CREATE TABLE ride (
    id          INTEGER PRIMARY KEY,
    wheel_id    INTEGER NOT NULL REFERENCES wheel(id),
    started_at  TEXT NOT NULL,      -- UTC, ISO-8601 с Z
    ended_at    TEXT,               -- NULL, пока пишется: так видно записи, оборванные падением
    utc_offset_minutes INTEGER NOT NULL,  -- пояс, в котором ехали: экспорт печатает местное время
    model       TEXT,               -- модель и прошивка не меняются по ходу поездки,
    version     TEXT                -- поэтому им место здесь, а не в каждой из тысяч строк
);

-- Быстрая таблица: только то, что меняется каждый кадр. Всё целое, всё в сотых долях
-- единицы — ровно то разрешение, в котором значение пришло с колеса.
CREATE TABLE telemetry (
    ride_id         INTEGER NOT NULL REFERENCES ride(id),
    wheel_id        INTEGER NOT NULL REFERENCES wheel(id),
    at              TEXT    NOT NULL,   -- UTC, ISO-8601 с Z

    speed           INTEGER NOT NULL,   -- 1/100 км/ч
    voltage         INTEGER NOT NULL,   -- 1/100 В
    phase_current   INTEGER NOT NULL,   -- 1/100 А
    current         INTEGER NOT NULL,   -- 1/100 А
    power           INTEGER NOT NULL,   -- 1/100 Вт
    pwm             INTEGER NOT NULL,   -- 1/100 %
    battery_level   INTEGER NOT NULL,   -- %
    distance        INTEGER NOT NULL,   -- метры
    totaldistance   INTEGER NOT NULL,   -- метры
    system_temp     INTEGER NOT NULL,   -- 1/100 °C
    temp2           INTEGER,            -- 1/100 °C; пишет только Gotway
    tilt            INTEGER,            -- 1/100 °; пишет только Veteran
    alert           TEXT                -- NULL почти всегда: пишется только когда изменилась
);

-- Медленная таблица: состояние, а не поток. Строка пишется раз в минуту и, сверх того,
-- немедленно при изменении — иначе редкое событие потерялось бы между отсчётами.
CREATE TABLE wheel_state (
    ride_id         INTEGER NOT NULL REFERENCES ride(id),
    at              TEXT    NOT NULL,
    charging_status INTEGER NOT NULL,
    wheel_alarm     INTEGER NOT NULL
);

-- Пакеты батареи — отдельной строкой на пакет, а не колонками. Пакетов бывает два (Sherman L),
-- один, или ни одного: MTen3 не отдаёт по батарее ничего и не будет — у него есть только общее
-- напряжение, а оно лежит в telemetry. Строк на такое колесо просто не появится.
CREATE TABLE pack_state (
    ride_id   INTEGER NOT NULL REFERENCES ride(id),
    at        TEXT    NOT NULL,
    pack_no   INTEGER NOT NULL,
    -- 1/1000 В: за ячейками следят по разнице вида 4.167 против 4.190, в сотых она бы пропала
    cell_min  INTEGER, cell_max INTEGER, cell_avg INTEGER,
    temp_min  INTEGER, temp_max INTEGER, temp_avg INTEGER,   -- 1/100 °C, по датчикам пакета
    health    INTEGER
);

CREATE INDEX telemetry_by_ride  ON telemetry(ride_id, at);
CREATE INDEX wheel_state_by_ride ON wheel_state(ride_id, at);
CREATE INDEX pack_state_by_ride  ON pack_state(ride_id, at);
```

**SQL выше — схема первой версии, оставлен как отправная точка.** Миграций с тех пор уже четыре:
v3 добавила посчитанные итоги поездки в `ride` (§3.1), v4 — `pack_state.current`
([план 9](../android-plan-9-prediction.md)), v5 убрала `wheel.name` (ниже). Актуальная схема — в коде
`WheelTalk.Storage`.

**~~`wheel.name` так и пустует~~ — колонки больше нет (v5, 30.07.2026).** Имя колеса задаётся
настройкой `Wheel:Name` и живёт **только** в ней; колонка, заведённая в v1 под то же имя, не
заполнялась ни разу и удалена — решение владельца по [плану 13 §3.1](android-plan-13-debts.md).
Список поездок подставляет имя при показе (`RideFormat.WheelName`), а не хранит вторую копию:
копия разошлась бы с настройкой при первом же переименовании. Поездки других колёс подписываются
моделью или MAC, как раньше, — настройка одна на выбранное колесо.

**Где лежит файл.** Там же, где журналы, — во внешнем каталоге приложения
(`RideFiles.Root`, то есть `Android/data/com.wheeltalk.droid/files/` — пакет сменился при переезде
на голый Android; в комментарии `RideFiles.cs` до сих пор стоит старый `com.wheeltalk.app`,
недоделка кода). Это выбрано не по привычке:
внутренний каталог достаётся только через `run-as`, и `adb pull` поездки перестал бы работать.
Забирать базу в режиме WAL надо вместе с `-wal` и `-shm` — или сделать
`PRAGMA wal_checkpoint(TRUNCATE)` перед выгрузкой.

**Версия схемы — в `PRAGMA user_version`.** Правила на открытии: версия меньше нашей — миграции
подряд; больше — не писать и сказать об этом (база от более новой сборки); файл не открывается —
**переименовать рядом, а не удалить**. Записанные поездки — единственные данные, которых у нас
нигде больше нет, и «пересоздадим базу» их убивает.

### 2.1. Почему так, а не «колонки как в экспорте»

Отправная точка — колонки экспорта плюс идентификаторы колеса и поездки. Это правильный
инстинкт: экспорт остаётся проекцией таблицы, а не пересборкой из чужих полей, и схему можно
читать, зная формат WheelLog. Что изменено и почему:

- **`wheel_id` в каждой строке — оставлен намеренно.** Формально он избыточен (поездка и так
  знает своё колесо), но главный запрос — «заряд этого колеса за последние 12 часов» — идёт
  **по времени, а не по поездке** и пересекает их границы. С `wheel_id` это один индекс, без
  него — join к `ride` на каждый такой график. Один INTEGER на строку того стоит.
  Индекса по нему пока **нет**: индексы пишутся на каждой вставке, пять раз в секунду, а график
  ещё не написан. Индекс заводится вместе с ним.
- **`date` и `time` слиты в `at`.** Две текстовые колонки — артефакт `SimpleDateFormat`, в
  шаблоне которого стоит запятая. В базе это ломает ровно то, ради чего база заводится:
  диапазон по времени пришлось бы искать по склейке двух строк.
  Формат — **UTC, ISO-8601 с `Z`**: только он сортируется как текст, а значит годится для
  индекса по времени. Смещение, в котором ехали, лежит в `ride.utc_offset_minutes` — экспорт
  обязан напечатать местное время, как это делает оригинал, и без смещения его не восстановить.
- **Округление, а не усечение.** `pwm` и `tilt` — не сырые поля кадра, а вычисленные `double`
  (`WheelState.Pwm = CalculatedPwm * 100`, и у Gotway ШИМ вообще выводится из скорости и
  напряжения). Записывать их надо через `Math.Round(x * 100)`: приведение к целому усекает там,
  где `F2` округляет, и `5.126` дало бы в экспорте `5.12` против `5.13` в исходном CSV — то
  есть гейт фазы 2 развалился бы на живых данных.
- **Числа, а не отформатированные значения**, всё целое в сотых долях единицы. Это ровно то
  разрешение, в котором значения приходят с колеса: скорость, напряжение и токи — сотые, и
  `%.2f` в CSV с ними совпадает. Тысячные ШИМ смысла не имеют, а вот `system_temp` в CSV — целые
  градусы, тогда как у нас сотые, и на графике температуры это видно.
- **`torque`, `roll`, `mode` не хранятся.** Наши декодеры их не производят, значение в каждой
  строке было бы одно и то же. Экспорт печатает их константами — это делает `RideLog`, и он уже
  это делает. Что это за величины и почему константы именно такие — §2.2.
- **`temp2` и `tilt` допускают NULL.** Температуру мотора пишет только Gotway, угол наклона —
  только Veteran. Ноль в этих колонках выглядел бы как измерение, а не как «протокол молчит»;
  на графике разница принципиальная.
  **NULL — ради графиков, а не ради файла.** Экспорт печатает в этих колонках ноль, потому что
  ноль там был у живого снэпшота и его же печатал `RideLog`: в оригинале эти поля — примитивы,
  которые `reset()` обнуляет, и `%.2f` печатает `0.00`, а не пустоту. (В первой редакции плана
  здесь стояло «экспорт печатает пустые колонки» — это была ошибка, гейт фазы 2 её и поймал бы.)
- **`model` и `version` подняты в `ride`.** Они не меняются по ходу поездки; в строке это
  повторение одной и той же строки тысячи раз.
- **Максимумы не хранятся вовсе.** `MaxPwm` и `TopSpeed` — это `max()` по уже записанным
  строкам, то есть чистое дублирование в каждом отсчёте. Итоги поездки считаются один раз при
  закрытии и кладутся в `ride` (§5).
- **Медленное — в отдельную таблицу.** BMS, состояние зарядки и флаг тревоги колеса меняются не
  покадрово, и писать их пять раз в секунду незачем: строка раз в минуту. Но «раз в минуту» без
  оговорки теряет редкое событие, поэтому строка пишется **ещё и при любом изменении**. Это
  разница между «медленной величиной» и «редкой»: первую можно опрашивать, вторую — нельзя.
  **Уточнение по итогам фазы 1: решать это надо по полю, а не по таблице.** Зарядка и флаг
  тревоги действительно редкие — стоят минутами, потом переключаются. Напряжения ячеек — нет:
  они плывут с каждой сменой нагрузки, и «писать при изменении» дало на реплее 106 строк
  `pack_state` за полторы минуты вместо четырёх. Пакет теперь **опрашивается по часам**, как
  термометр, а внеочередную строку получает только `health` — единственная дискретная величина,
  которую пакет сообщает.
- **Пакеты — строками, а не колонками.** Их бывает два, один или ноль, и колонки под второй
  пакет у большинства колёс стояли бы пустыми. У MTen3 по батарее нет вообще ничего и не будет —
  только общее напряжение, которое и так лежит в `telemetry`; на такое колесо строк в
  `pack_state` просто не появится.
- **По ячейкам и температурам — минимум, максимум и среднее**, а не одно значение. Датчиков в
  пакете несколько, ячеек десятки, и мгновенный отсчёт одной из них раз в минуту не говорит
  ничего. Разброс — это и есть состояние пакета: `CellDiff` не хранится, он выводится из
  минимума и максимума.
- **Температура пакета нужна не для красоты:** от неё зависит внутреннее сопротивление, а без
  него не посчитать ни просадку, ни остаток хода ([план 9](../android-plan-9-prediction.md) §2.2).
- **Всё по пакетам — необязательное.** Колонки допускают NULL, и отсутствие данных должно
  выглядеть как отсутствие, а не как ноль. Серийники, даты производства и карта балансировки в
  поездке не нужны — если понадобятся, им место в `wheel`.
- **BMS — то, ради чего стоило отходить от формата экспорта.** Деградация пака видна только на
  длинной истории, а в CSV WheelLog таких колонок нет вовсе. Пишет их только Veteran; у
  Gotway/Begode строки `wheel_state` будут с пустыми колонками BMS, и это нормально.

Обратная сторона, которую надо принять: экспорт перестаёт быть `SELECT *` и становится
`SELECT` с делением на сто и форматированием. Это уже написано и покрыто тестами
(`RideLog.FormatLine`), так что цена — один запрос, а не новый формат.

### 2.2. Что такое `torque`, `roll` и `mode` (проверено по исходникам)

Все три — колонки формата WheelLog, которые мы не заполняем. Разобрано, чтобы решение не
держалось на догадке.

**`torque`** — `WheelData.mTorque`, `double`, лейбл в интерфейсе `Torque`, единица из
`strings.xml` — `N*m`. Присваивается **только** в `InmotionAdapterV2` (все восемь разборщиков
кадра реального времени), знаковое 16-битное little-endian с кадра, делится на 100. Ни
`GotwayAdapter`, ни `VeteranAdapter`, ни KingSong, ни Ninebot, ни Inmotion V1 его не трогают —
там остаётся ноль после `reset()`. Знак (тяга или торможение) в исходниках нигде не оговорён.

**`roll`** — крен, `WheelData.mRoll`, `double`, лейбл `Roll`, градусы (символ `°` вшит в формат
вывода). Пишут две ветки Inmotion: V2 — знаковое 16-битное LE делённое на 100; V1 — 4-байтное LE
делённое на **90.0**, причём для моделей V8F/V8S/V10\* оно тут же принудительно обнуляется, без
объяснения. У Gotway и Veteran не присваивается. Осторожно: у Gotway есть настройка
`roll_angle` («Roll angle cut off») — это **другое**, настройка колеса, а не телеметрия.

**`mode`** — `WheelData.mModeStr`, свободная строка, поле по умолчанию `"Unknown"`, а `reset()`
ставит пустую. Пишут трое: Inmotion V2 склеивает из битов состояния (`"Active"`, `" Charging"`,
`" Lifted"` и их сочетания — пробелы в строках именно такие); Inmotion V1 переводит числовой
режим в имя (`Idle`, `Drive`, `Zero`, `LargeAngle`, `Check`, `Lock`, `Error`, `Carry`,
`RemoteControl`, `Shutdown`, `pomStop`, `Unlock`); KingSong печатает сырой байт десятичным
числом. У Gotway и Veteran не присваивается.

**Отсюда следствие, изменившее наше решение.** Раз для Veteran и Gotway поля остаются нулями, а
`LoggingService` печатает их через `%.2f`, то настоящий лог WheelLog с Sherman L содержит в
`torque` и `roll` именно `0.00`, а не пустоту. Мы писали пустые — и тем самым расходились с
форматом ровно там, где обещали совпадение: чужой парсер, приводящий эти колонки к числу,
пустой строки не видел никогда. Исправлено: `0.00` в обе, `mode` остаётся пустым — его и
оригинал очищает в `reset()`.

**Хранить их в базе всё равно незачем.** Это чужие поля чужих протоколов; наши декодеры их не
производят, и появятся они не раньше, чем появится Inmotion. Экспорт печатает константы.

**Мелочь напоследок:** `LogHeaderEnum` объявляет `TORQUE`, `ROLL` и `MODE`, но обратный парсер
`ParserLogToWheelData` их не читает вовсе. Эти три колонки в оригинале пишутся и никогда не
читаются обратно.

### 2.3. Порядок величин

Полтора десятка целых колонок; SQLite хранит малые целые в один-два байта. Строка выходит
байт в тридцать, пять строк в секунду — порядка полумегабайта на час поездки. `wheel_state`
на этом фоне не считается: шестьдесят строк в час. Годы такого не страшны, но именно поэтому
очистка из §5 обязательна.

**Незакрытая поездка — это нормально.** Телефон разрядился, приложение убили — `ended_at`
остался пустым, строки на месте. Закрывать такие при старте по последней строке.

## 3. Фазы

### Фаза 1 — База и запись ✅
Схема, открытие/миграция, `RideStore` (начать поездку → писать строки → закончить).
`RideRecorder` переключается на него вместо `BufferedLogFile`. Запись пачками в транзакции —
по той же причине, по которой сейчас буферизуется файл: телеметрия приходит с потока, который
кормит декодер. Режим WAL.

**Гейт:** на реплее в эмуляторе поездка появляется в базе, строки идут, `wheel_state` набирает
строку в минуту, остановка проставляет `ended_at`; после «убийства» приложения посреди записи
данные на месте, поездка закрывается при следующем старте.

Внеочередную строку «при изменении» реплеем не проверить: синтетический дамп собран из одного
кадра-шаблона, поэтому BMS, зарядка и флаг тревоги в нём постоянны и меняться не могут. Эта
ветка проверяется юнит-тестом в `WheelTalk.Storage`, а на живом колесе — заодно с полевой
проверкой плана 5.

### Фаза 2 — Экспорт в WheelLog CSV ✅
Чтение поездки из базы → `RideLog.Header` + `RideLog.FormatLine` → файл с тем же именем, что
писался раньше (`yyyy_MM_dd_HH_mm_ss.csv` в каталоге по MAC).

**Гейт:** экспорт поездки, записанной на том же дампе, что и файл из плана 5, даёт **побайтово
тот же CSV** — кроме времени в первых двух колонках.

**Пройден, и строже, чем требовалось:** `RideExportTests` берёт настоящую поездку Sherman L
(`shermanl_raw_ride_20260728.csv`, кадры прямо с колеса), декодирует её в тысячу с лишним
снэпшотов и прогоняет двумя путями — прямо в `RideLog`, как писал план 5, и через базу. Отметки
времени тоже подаются одинаковые, поэтому совпадать обязаны **все** колонки, включая первые две.
Совпадают.

Это не украшение теста: две вещи, которые здесь вероятнее всего разъедутся, — округление
вычисленного ШИМ и часовой пояс, и ни одна из них не видна на значениях, которые кто-то выбрал
круглыми. Заодно выяснилось, что `Math.Round` по умолчанию округляет к чётному, а `F2` —
от нуля; на `0.125` это разница между `0.12` и `0.13`, и хранить надо так, как печатает формат
(`Hundredths.Of`).

### Фаза 3 — Список поездок и экспорт из интерфейса ✅ (согласовано и сделано, гейт на телефоне не пройден)

Оригинал разобран целиком — что у него устроено хорошо, что плохо и почему, см. §7. Ниже — что из
этого взято, а что сделано иначе и по какой причине. Отступления от согласованного текста собраны
в §3.5.

#### 3.1. Итоги считаются один раз при закрытии поездки

Схема v3 добавляет в `ride` посчитанные итоги. Считать их при каждом показе списка — это то, на чём
у оригинала тормозит экран: он разбирает весь CSV прямо в `onBindViewHolder`, заново при каждой
прокрутке (§7). Нам это не нужно и даром: строки уже в базе, и все итоги — один `SELECT` с
агрегатами.

| Колонка | Как считается | Почему так |
|---|---|---|
| `distance_m` | максимум `totaldistance` по последним десяти строкам минус **первое ненулевое** | Оба приёма из оригинала. Первое ненулевое чинит [известный дефект](../handover.md): одометр приходит не сразу, и ноль в первых строках даёт на разностях скачок в тысячи километров. Максимум по хвосту — защита от одного битого значения в конце |
| `duration_s` | `at` последней строки телеметрии минус первой (`RideTotals`) — не `ended_at − started_at`, как стояло здесь сначала | Полное время, включая стоянки. Честное «сколько это заняло» — по данным, которые точно есть: строки телеметрии переживают и падение приложения |
| `moving_s` | сумма интервалов, где \|скорость\| > 2 км/ч | Порог оригинала (`RIDING_SPEED = 200`). Без него «средняя» превращается в функцию от числа светофоров |
| `avg_speed` | `distance_m / moving_s` | **Не среднее по отсчётам.** У оригинала именно среднее, и оно физически бессмысленно: в его же тесте 29,7 км/ч при 19,5 км за 880 минут. Среднее по отсчётам зависит от частоты пакетов и от длины стоянок, а не от поездки |
| `max_speed`, `max_pwm`, `max_power`, `max_current` | `MAX()` по модулю | По модулю — тот же довод, что у тревог: рекуперация не должна прятать пик |
| `consumption_wh` | интеграл мощности по времени, **с вычетом дыр** длиннее секунды | Приём оригинала (`timeToExclude`). Без него ночь на зарядке обнуляет расход |
| `consumption_wh_km` | `consumption_wh / distance` | |

Итоги считаются в момент закрытия поездки и при закрытии брошенной (`RideDatabase` уже это делает).
Пересчёт по требованию — на случай, если формула изменится: пустой `duration_s` как признак
«посчитать заново», приём оттуда же.

#### 3.2. Экран списка

Источник — база, а не обход файлов. У оригинала список строится по каталогу, а строка в базе
заводится лениво при первом показе; отсюда и мусор в списке (импортированные и тестовые файлы), и
плоский список без колеса, и непредсказуемый порядок на старых Android (§7).

- **Строка:** когда (сегодня / день недели / дата), колесо, длительность, пробег, максимум ШИМ,
  расход. Колесо показываем — у нас их два, и в оригинале это упущено.
- **Порядок:** по времени начала, новые сверху. Из базы, а не из файловой системы.
- **Нажатие открывает поездку.** У оригинала главное действие спрятано в долгое нажатие, и угадать
  его нельзя — прямо названо в разборе как то, что повторять не надо.
- **Действия строки:** выгрузить в CSV, удалить. Обе — через то же меню, что у настроек.

#### 3.3. Экран поездки — итоги, без графиков

Показывает посчитанные итоги и кнопку выгрузки. **Графиков в этой фазе нет:** они требуют решений
о том, как вообще выглядят графики, а это [план 7](android-plan-7-dashboard-design.md) и первый
заказ из [ui-notes.md](../ui-notes.md) — «нажатие на заряд открывает график разряда за 12 часов».
Делать их дважды дороже, чем подождать.

Отдельно: экран поездки **не требует GPS**. У оригинала он падает в «Failed to open map», если в
логе нет координат, — то есть графики по ШИМ, току и напряжению, к геоданным отношения не имеющие,
недоступны без них. У нас GPS нет вовсе, и завязываться на него незачем.

#### 3.4. Чего в этой фазе нет

Удаление старых данных (§5), выгрузка на сторонние сервисы, импорт чужих CSV, множественный выбор,
поиск. Первое — обязательно, но отдельным решением о правиле; остальное ждёт причины.

**Гейт:** поездка выгружается с телефона без единой команды `adb`; итоги в списке сходятся с тем,
что даёт экспорт того же файла.

#### 3.5. Что вышло иначе, чем в согласованном тексте

**`consumption_wh_km` не хранится.** Это `consumption_wh`, делённое на `distance_m`, и ничего
больше. Хранимая копия частного — ещё одно место, которое может разойтись со своим же числителем,
причём молча: у миграции формулы или у пересчёта нет причин трогать все три колонки согласованно.
Считается при чтении, `null` при нулевом пробеге — «нисколько на ноль километров» это не ноль.

**Итоги досчитываются при открытии базы, а не при показе списка.** Признак — пустой `duration_s`,
как и договаривались; но пройти по недосчитанным поездкам лучше там, где файл ещё никем не занят,
чем на экране, который открыли посмотреть. Тем же проходом чинятся поездки, записанные до появления
колонок, и закрытые аварийным восстановлением. Он же — способ выкатить исправленную формулу:
очистить колонку, строки-то все на месте.

**Удаление идёт через ту же очередь, что и запись.** SQLite держит одного писателя, и удаление с
экрана списка на своём соединении, пока пишущий поток держит файл, — это `SQLITE_BUSY`, а не
удаление. Поездку, которая пишется прямо сейчас, хранилище отклоняет: экран её и не предлагает, но
«экран не попросит» — не гарантия.

**Одна условность в подсчёте времени движения названа вслух:** отсчёт держится до следующего, то
есть последний едущий отсчёт перед остановкой засчитывается целиком. На реальных 200 мс это
невидимо; в тестах шаг в секунду, и там это десятая часть — поэтому в тестах стоят точные ожидания
алгоритма, а не «правильные» числа.

**Вход в список — пока через экран записи.** На главном экране ему место, но главный экран сейчас
переделывается (план 7), и лишняя кнопка там прожила бы до первого его коммита. *Актуализация
30.07.2026: довод устарел — главный экран переделан (план 7, фаза 4); сам факт в силе: в список
по-прежнему входят через экран записи, а с главного к нему ведёт тап по панели.*

## 4. Подводные камни

- **Коммит не должен происходить на потоке BLE.** `WheelSession` отдаёт телеметрию через
  обычный `Subject`, то есть `RideRecorder.Write` выполняется на колбэке GATT — том самом,
  который кормит декодер двадцатью тремя кадрами в секунду. Коммит WAL плюс обновление индексов
  на этом потоке — единственный риск производительности, присущий именно этой схеме. Значит:
  хранилище владеет очередью и одним пишущим потоком, а `Write` только кладёт в очередь.
  Соединение при этом одно — SQLite не любит запись из разных потоков.
- **Транзакция на пачку — это окно потери.** Чем реже коммит, тем больше теряется при падении.
  Начать с секунды-двух и посмотреть, что это даёт по батарее.
- **Экспорт не должен блокировать запись.** Выгрузка часовой поездки — это тысячи строк;
  читать надо потоком, а не собирать список в памяти, и не мешать записи текущей поездки.
- **Осушение `alert` переезжает в запись.** Сейчас это состояние `RideRecorder._lastAlert`:
  текст попадает в строку, только если изменился. В базе так же — и значит `alert` строки **не
  выводится из её снэпшота**: заново его потом не восстановить, порядок строк становится частью
  данных.
- **Формат экспорта проверяется теми же тестами.** Если строка из базы разойдётся со строкой
  из снэпшота — это ошибка чтения базы, а не формата, и тест должен показывать именно это.
- **Смена колеса закрывает поездку.** У `ride` одно `wheel_id`, проставленное при создании;
  `RideRecorder` уже умеет закрывать файл при смене MAC — база должна закрывать поездку и
  начинать новую.
- **Место.** Час поездки — порядка двадцати тысяч строк; это единицы мегабайт, но растёт это
  вечно, пока не появится §5.

---

**Старые CSV не импортируются.** Файлы, записанные планом 5, остаются лежать где лежат: их
единицы, они уже в нужном формате, и код импорта ради них — работа без адресата. Но список
поездок их не покажет, и это надо знать заранее, а не выяснять, недосчитавшись поездки.

## 7. Как это устроено в оригинале (разобрано перед фазой 3)

Смотрели, чтобы не изобретать заново и не повторить чужих ошибок. Ссылки — на
`C:\Work\repos\Wheellog.Android`.

**Что у них есть.** Первичная сущность — **файл CSV**, а строка в базе Room (`TripDataDbEntry`) —
кэш итогов, который заводится лениво при первом показе элемента списка (`data/TripParser.kt:121`).
Список строится **обходом каталога** (`utils/FileUtil.kt:315-401`), база используется только как
поиск по имени файла. Границы поездки — время жизни `LoggingService`; обрыв связи её не закрывает,
файл остаётся открытым, и после реконнекта строки идут в него же с временно́й дырой.

**Что стоит перенять — и что мы берём:**

| Приём | Где у них | Что берём |
|---|---|---|
| Одометр с первого ненулевого | `TripParser.kt:148-150` | Да — это чинит наш известный дефект |
| Конец пробега как максимум по последним десяти строкам | `TripParser.kt:156` | Да — защита от битого хвоста |
| Вычет дыр длиннее секунды из времени для расхода | `TripParser.kt:142-145` | Да — иначе простой топит Вт·ч/км |
| Порог «в движении» 2 км/ч | `WheelData.java:40,170` | Да, но применяем к средней скорости, а не только к живым показаниям |
| Метка «пересчитать» пустым полем | `views/TripAdapter.kt:263` | Да — дёшево и понятно |
| Порог автостарта записи по скорости | `MainActivity.kt:439-445` | Не сейчас: у нас запись включена по умолчанию нарочно, и мусорный лог дешевле забытой кнопки |

**Что повторять не надо, и почему:**

- **Средняя скорость как среднее по отсчётам** (`TripParser.kt:163`). Зависит от частоты пакетов и
  длины стоянок, а не от поездки: в их же тесте 29,7 км/ч при 19,5 км за 880 минут
  (`TripParserTest.kt:57-66`). Мы считаем `пробег / время в движении`.
- **Разбор всего CSV в `onBindViewHolder`** (`TripAdapter.kt:255-267`) — список парсит файлы заново
  при каждой прокрутке. У нас строки уже в базе, и итоги — один запрос.
- **`TripParser` — синглтон с общим мутабельным состоянием**: гонка при параллельном разборе
  нескольких элементов.
- **Главное действие только по долгому нажатию** (`TripAdapter.kt:303-313`): по строке нажать
  нельзя, и догадаться об этом неоткуда.
- **Порядок списка отдан файловой системе** на Android 9 и ниже (`FileUtil.kt:335-368`).
- **Экран поездки требует GPS-колонок** и без них падает в алерт (`TripParser.kt:69-74`), хотя
  графики по ШИМ, току и напряжению к геоданным отношения не имеют.
- **Связь «поездка ↔ файл» по одному имени файла**, без пути и MAC: два колеса дают файлы с
  одинаковым именем и коллизию по уникальному индексу. Колонки `mac` и `start` в схеме есть, но не
  заполняются.
- **Длительность считается по одной шкале времени, а расход — по другой**, очищенной от дыр, и обе
  показаны в одной карточке. Числа между собой не сходятся, и объяснить это пользователю нечем.
  Мы показываем обе явно: полное время и время в движении.
