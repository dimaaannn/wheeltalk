## Главное ограничение этого разбора — сказать сразу

**Ни один из четырёх выданных файлов не содержит побайтового разбора полезной нагрузки
телеметрии** (напряжение/скорость/ток/температура кадра `0xA9` и т.п.). `BleService.java` —
чистый транспорт: он получает уведомления с характеристики, передаёт их дальше двум подписчикам
(`r`/`gc` через колбэки `h.a(bArr)`/`g.a(bArr)`, `BleService.java:310-320`) и рассылает их
широковещательно (`Intent("bluetooth_data")`, `BleService.java:317-319`) — но сам **не читает ни
одного байта содержимого кадра**, кроме заголовка транспортного уровня (см. ниже). `BmsService.java`
разбирает только два байта заголовка (`[16]`/`[17]`) для маршрутизации, дальше хранит кадр как сырую
hex-строку, не как поля (§5). Единственное место, где реально сопоставляются имена полей значениям
из `DeviceBleBean` (voltage/current/speed/temperature/errorCode/…, см. §3, §4), — класс(ы) вне
периметра задания (тот же обфусцированный `defpackage.fw`, что строит исходящие команды —
капкан 2 задания: сборка/разбор протокола размазаны по экранам, а не собраны в одном месте).
**Не достраиваю картину по догадке** — где формула не видна в выданных файлах, так и написано.

Что это ограничение не мешает установить с уверенностью:
- транспортную рамку кадра (конверт, GATT-профиль, два независимых канала связи);
- раскладку **отдельного** протокола BMS-опроса (`BmsService`), который живёт по другой нумерации
  типов, чем тот, что описан в комментарии нашего декодера (важное расхождение, §2.1);
- список полей, которые официальное приложение вообще держит в памяти для одного колеса
  (`DeviceBleBean`, §3) — не то же самое, что раскладка кадра, но полезный ориентир, что оно **умеет
  показывать**, в сравнении с тем, что показываем мы.

## 1. Транспортная рамка — подтверждена независимо от нашего источника порта

Наш декодер портирован из `KingsongAdapter.java` (WheelLog) — источник, которого сама официальная
компания не писала. `BleService.java`, наоборот, **их собственный код**, и в нём есть кадр,
собранный с нуля, безотносительно к `KingsongAdapter`:

```java
byte[] bArr = new byte[20];
bArr[0] = -86;   // 0xAA
bArr[1] = 85;    // 0x55
bArr[16] = 94;   // 0x5E — тип
bArr[17] = 20;   // 0x14
bArr[18] = 90;   // 0x5A
bArr[19] = 90;   // 0x5A
BleService.this.Q(bArr);
```
(`BleService.java:285-292`, внутренний класс `e.a` — `TimerTask`).

Это **независимое подтверждение конверта**, который у нас уже был в `EmptyRequest`
([`KingsongDecoder.cs:470-471`](../WheelTalk.Core/Decoding/KingsongDecoder.cs)): 20 байт,
`AA 55` в начале, `5A 5A` в конце, тип на смещении 16, байт 17 у пустых команд равен константе
`0x14` — **дословно то же значение**, что у нас во всех билдерах команд. Совпадение не случайно:
оба источника читают протокол одного и того же колеса, только с разных сторон (WheelLog нашёл это
по обратной разработке, здесь — прямо из кода изготовителя, ни разу не пересекаясь с
`KingsongAdapter.java`).

### 1.1 Периодический кадр 0x5E — у них есть, у нас нет вовсе

Кадр выше — не разовый запрос, а **heartbeat**: собирается и шлётся через `Timer().schedule(new a(),
2500L)` (`BleService.java:338`) сразу после успешной подписки на уведомления
(`onNotifySuccess`/`g()`, `BleService.java:330-339`), тип `0x5E`(94), **не встречается ни в одном из
типов, которые разбирает наш декодер** (`0xA9/0xB9/0xBB/0xB3/0xF5/0xF6/0xA4/0xB5`,
[`KingsongDecoder.cs:136-148`](../WheelTalk.Core/Decoding/KingsongDecoder.cs)) — ни как входящий, ни
как исходящий; `grep` по `0x5E`/`94` в `KingsongDecoder.cs` и в тестах ничего не находит.

**У нас после того, как имя и серийник узнаны, `RequestMissingIdentity()` перестаёт писать что-либо
вовсе** ([`KingsongDecoder.cs:150-155`](../WheelTalk.Core/Decoding/KingsongDecoder.cs) —
условие `if/else if`, оба ветвятся в пустоту, когда оба поля уже заполнены). У них — heartbeat `0x5E`
шлётся **раз в 2,5 с бесконечно**, пока держится подписка, независимо от того, что уже узнано.
**Требует проверки на живом колесе**: неизвестно, действительно ли какая-то прошивка KingSong
рассчитывает на этот периодический пинг для продолжения потока телеметрии (аналогично уже
найденному живому кейсу с KS-16S и `AT+ULKTE`, который решался постоянными запросами после каждого
уведомления, см. класс-комментарий `KingsongDecoder.cs:34-35`) — сама находка (кадр 0x5E существует
и мы его никогда не шлём) доказана чтением кода, связь с обрывами телеметрии — нет.

### 1.2 Два независимых GATT-канала — у них есть оба, у нас нет второго вовсе

`BleService` умеет открывать уведомления на **двух разных парах** служба/характеристика:

| Константа | UUID | Роль |
|---|---|---|
| `H`/`I` | `0000ffe0`/`0000ffe1` | основной канал (запись и уведомление на одной характеристике `ffe1`) |
| `J`/`K`/`L` | `0000ad00`/`0000ad01`/`0000ad02` | второй канал: запись на `ad01`, уведомление на `ad02` |

(`BleService.java:56-60`). Метод `O()` (`BleService.java:839-847`) открывает уведомления на
`ffe0`/`ffe1`; метод `P()` (`BleService.java:849-853`) — на `J`/`L` (`ad00`/`ad02`). Запись зеркально:
`Q()` пишет в `ffe0`/`ffe1` (`BleService.java:855-867`), `R()` — в `J`/`K` (`ad00`/`ad01`)
(`BleService.java:869-877`).

Выбор канала — по коду подключения: `v(String)` (`BleService.java:985-1010`) запрашивает MTU 512
(`L()`, `BleService.java:822-829`) и по колбэку `onMtuChanged` уходит в `O()` (основной канал,
класс `d`, `BleService.java:250-269`). `w(String)` (`BleService.java:1012-1019`) идёт по колбэку
`c` (`BleService.java:178-248`), который **вообще не запрашивает MTU** и сразу вызывает `P()`
(второй канал, `BleService.java:216-222`). Между `v`/`w` переключается класс `i`
(`BleService.java:449-464`) по значению `il2.a(getApplicationContext())` сравнением с
`MainFragmentAty.N4`/`O4`.

### 1.2.1 Раскрыто отдельным запросом владельца — что за канал и не наследие ли это

**Капкан «объявлено, но не используется» проверен — канал живой, не мёртвый код.** Нашёл конкретные
рабочие вызовы: `CarManagerOneFrgm.java:1354,2650` шлют команды именно через `X4.q(...)` — метод
`BleService.q(byte[])`, тот, что кладёт кадр в очередь секондари-канала (`R()`,
`BleService.java:869-877`), а не в основную (`p()`→`Q()`). Не наследие — реальный, достижимый из
живого экрана путь.

**1. Чем отличается от `ffe0/ffe1`.** Не только паросочетание характеристик (см. таблицу выше —
раздельные запись/уведомление против одной общей `ffe1`), но и **сам формат кадра — другой протокол
целиком**, не тот же `AA 55…5A 5A` по другому проводу. Билдер — `gv1.a(byte, byte[4])`
(`gv1.java:11-28`):
```
0xCC(-52) | opcode(1 байт) | data[0..3] (4 байта) | XOR-чексумма(1 байт, gv1.b — цикл eor) | 0xFE(-2)
```
**7 байт всего**, заголовок `CC`, хвост `FE`, чексумма — один байт XOR (не CRC32, не CRC16, не
`AA 55`-парность из основного протокола InMotion/KingSong-колёс). Ничего общего по форме с 20-байтным
кадром, который разбирают `KingsongDecoder.cs`/`fw.java`/`MainFragmentAty.X1`.

**2. Для чего используется.** Не телеметрия и не настройки колеса — короткие дискретные команды.
Найдено два вызова: `opcode=8` — блокировка/разблокировка (`bArr7[0]` = инверсия текущего
`btlock`, `CarManagerOneFrgm.java:1344-1354`), `opcode=9` — свет вкл/выкл
(`CarManagerOneFrgm.java:2640-2650`, с той же проверкой имени модели рядом, см. ниже). Обратной
телеметрии (уведомлений с `ad02`) в прочитанных файлах не разбирал — не входило в счёт этой части,
речь только о том, что уходит наружу.

**3. Когда выбирается — условие из кода, дословно.** `BleService.java:449-464`, класс `i`:
```java
String a = il2.a(getApplicationContext());  // сохранённое имя устройства из SharedPreferences,
                                              // ключ "connected_device_name" (il2.java:10-13)
if (a.equals(MainFragmentAty.N4) || a.equals(MainFragmentAty.O4)) {
    bleService.w(bleService.r);   // → секондари-канал (ad00/ad01/ad02)
} else {
    bleService.v(bleService.r);   // → основной канал (ffe0/ffe1)
}
```
где `MainFragmentAty.N4 = "KS-E1/E3 KSE"`, `MainFragmentAty.O4 = "KS-E1KSE/E3"`
(`MainFragmentAty.java:171-172`) — **не универсальный запасной путь при неудаче на основном канале
и не выбор «для всех новых моделей»**, а точное сравнение с рекламным именем **конкретно двух
устройств КингСонг серии E1/E3**. Тот же признак модели используется и во втором найденном вызове
(`CarManagerOneFrgm.java:2641`: `if (a2.equals(N4) || a2.equals(O4)) { … X4.q(gv1.a(...)) }`) —
команда света для этой линейки строится и шлётся *только* если модель распознана как E1/E3, иначе
её не собирают вовсе (ветка `else`, если есть, в моём окне чтения не просматривалась — не
утверждаю, что для прочих моделей свет недоступен в принципе, только что здесь, в этом коде,
собирается именно кадр `gv1` под E1/E3).

Названия `E1`/`E3` не встречались мне ни в `bean/`, ни в шести экранах командного разбора как
явно подписанные «моноколесо» или «самокат» — по формату имени (`KS-E…`, короткий числовой индекс,
не буквенная модель вроде `KS-16X`/`KS-S20`) они не похожи на остальную линейку колёс, но
продуктовую линейку KingSong не сверял — **не утверждаю, что это самокат, только что это не
типичное для моноколёс имя**, и что протокол под него — заведомо другой.

**4. Что это значит для нас.** Два разных вопроса, ответ на них разный:
- **опознание**: `WheelProfiles.cs` не знает `ad00/ad01/ad02` вовсе (§1.2 выше) — устройство,
  поднимающее только этот сервис, мы не найдём на этапе сканирования;
- **даже если бы опознали — говорить с ним всё равно не сможем нынешним декодером**: протокол на
  этом канале не `AA 55…5A 5A`, а 7-байтный `CC…FE` с однобайтовым XOR — `KingsongDecoder.cs`
  такой кадр не построит и не разберёт ни при каких условиях, это не дыра в существующем
  декодере, а необходимость нового, отдельного от текущего.

**Итог: не дефект и не забытая возможность нашей стороны, а осознанно нерелевантный на сегодня
случай** — узкий, по имени модели, охват (два конкретных литерала), другой протокол целиком.
Стоило бы заводить поддержку, только если у владельца или пользователей появится реальное
устройство этой линейки — до тех пор это не пробел порта, а неопознанная (и неразбираемая
нынешним кодом) периферия вне текущей продуктовой границы.

**У нас в `WheelProfiles.cs` для KingSong — три отпечатка GATT-дерева
([`WheelProfiles.cs:71-94`](../WheelTalk.Core/Detection/WheelProfiles.cs)), и все три построены
вокруг `ffe0`/`ffe1` (плюс вариации `ffe2`/`fff3`/`fff5` и нестандартный `02f00000-…`) — `ad00`/
`ad01`/`ad02` не встречается в этом файле вовсе (проверено `grep`-ом по всему файлу). Разбор,
что это за канал и стоит ли о нём беспокоиться, — см. §1.2.1 ниже (закрыто отдельным запросом).

## 2. BMS: у них — отдельный, куда более грубый механизм, чем разбор полей

### 2.1 `BmsService` — своя нумерация типов, не совпадающая с нашей

`BmsService` регистрируется как второй подписчик на тот же поток кадров через `BleService.J(gc)`
(`BmsService.java:634-639`, `BleService.java:814-816`) и маршрутизирует по `bArr[16]` (тип) и
`bArr[17]` (подтип/номер страницы):

| `bArr[16]` (тип) | Значение | Диапазон `bArr[17]` | Что происходит |
|---|---|---|---|
| `116` (`0x74`) | пакет 1 | `1` (спец.) | подтверждение начала опроса — сброс счётчика повторов (`BmsService.java:57-65`) |
| `116` (`0x74`) | пакет 1 | `{160,175,182,209,211,213,215,217,219,221,223,225,227,229,231}` | 15 страниц данных пакета 1, `g` = 0..14 (`BmsService.java:78-155`) |
| `117` (`0x75`) | пакет 2 | `1` (спец.) | то же, плюс `MainFragmentAty.K4 = true` — флаг «BMS готов» (`BmsService.java:66-76`) |
| `117` (`0x75`) | пакет 2 | те же 15 значений | 15 страниц данных пакета 2, `g` = 15..29 (`BmsService.java:157-234`) |
| `118` (`0x76`) | — | `166` (`0xA6`) | ещё одна страница, `g` = 30 (`BmsService.java:236-244`) |
| `119` (`0x77`) | — | — | завершающая страница, `g` = 31, запускает выгрузку (`BmsService.java:246-258`) |

Это **другая нумерация**, чем та, что у нас в комментарии декодера (`0xF1`/`0xF2`/`0xD0`/`0xE1`/
`0xE2`/`0xE5`/`0xE6` = 241/242/208/225/226/229/230, [`KingsongDecoder.cs:42-45`](../WheelTalk.Core/Decoding/KingsongDecoder.cs),
источник — `KingsongAdapter.java`, WheelLog). Ни одно значение не совпадает построчно с диапазоном
`116..119`(`0x74..0x77`), который использует `BmsService`. **Открытый вопрос, не решаю его
догадкой** (капкан 3): возможно, это два разных поколения BMS-протокола (одиночный пак —
раскладка WheelLog `0xF1`/`0xF2`, двойной пак больших колёс вроде `KS-S22`/`KS-F22P` — раскладка
`BmsService` `0x74`/`0x75` с явным делением на «пакет 1»/«пакет 2»), возможно — оба существуют
параллельно на одном колесе для разных нужд (эта — диагностический снимок, та — что-то другое).
Файлов, которые связывали бы обе нумерации, в моём периметре нет.

### 2.2 Что делает `BmsService` с данными — не разбор полей, а сырой снимок для сервера

**Ключевая находка.** `BmsService` **не декодирует ни одного поля** внутри страницы — метод `m()`
(`BmsService.java:581-591`) просто кладёт **hex-строку всего 20-байтного кадра** (`qr.f(bArr)`) в
список `h` по индексу `g`, без интерпретации содержимого. Когда набирается всех 32 страниц
(индексы 0..31, `bArr[16]==119` — последняя), обработчик `case 32`
(`BmsService.java:523-541`) чистит пустые записи и отправляет весь список **как есть** на сервер
изготовителя: `HttpClient.getInstance().postBatteryConfig(strArr)` (`BmsService.java:530`).

Это не телеметрия для райдера — это **диагностический снимок**, целиком уходящий в облако
KingSong (видимо, для гарантийного разбора), и **ни разу не превращается в именованное значение**
(«напряжение ячейки N», «температура ячейки M») нигде в этом файле. Обратная сторона того же
механизма — `n()` (`BmsService.java:593-613`): приложение может **скачать** ранее сохранённый снимок
с сервера (`BmsConfig`, список hex-строк) и **воспроизвести его обратно колесу**
(`fw.N(...)` → `BleService.p(...)`, три раза с разной задержкой) — судя по всему, механизм
восстановления/калибровки BMS с сервера, а не что-то, что видит райдер в реальном времени. Смысл
конкретных байт внутри страницы (что кодируется в `fw.N`/куда пишется результат) вне периметра
задания — только транспорт-обёртка в моих файлах.

**Вывод для сравнения с нами.** У нас `KingsongDecoder` вообще не трогает ни одну BMS-страницу
(WheelLog-раскладка `0xF1`/`0xF2`/`0xD0`/`0xE1`/`0xE2`/`0xE5`/`0xE6` распознаётся и падает в `false`,
[`KingsongDecoder.cs:145-147`](../WheelTalk.Core/Decoding/KingsongDecoder.cs)) — но и **само
официальное приложение**, по крайней мере в части `BmsService`, тоже не разбирает свою собственную
BMS-раскладку (`0x74..0x77`) на поля для показа райдеру — только копит и грузит на сервер. Разница
не в «они умеют больше», а в цели: у них это диагностика для гарантии, не элемент экрана поездки.
**Не решает вопрос**, показывает ли официальное приложение хоть что-то из BMS в реальном времени —
если показывает, то через отдельный путь вне `BmsService` (не в моём периметре).

### 2.3 Что мы вообще не берём из BMS

- Раздельные ячейки/паки: ни та, ни другая нумерация (`0xF1..0xE6` или `0x74..0x77`) у нас не
  порождает ни одного значения в `WheelState`/`SmartBms`. Инфраструктура `SmartBms`/`CellVoltage`
  ([`WheelTalk.Core/Contracts/SmartBms.cs`](../WheelTalk.Core/Contracts/SmartBms.cs),
  [`WheelTalk.Core/Battery/CellVoltage.cs`](../WheelTalk.Core/Battery/CellVoltage.cs)) в кодовой базе
  есть и используется другими протоколами, но не наполняется для KingSong вовсе.
- `CellInputs()` ([`KingsongDecoder.cs:371-380`](../WheelTalk.Core/Decoding/KingsongDecoder.cs))
  берёт число ячеек из таблицы модели (`CellsFromModel`, по имени/напряжению класса), не с провода —
  число ячеек **вычислено**, не измерено, ни у нас, ни (насколько показывает `BmsService`) у
  официального приложения через этот путь.
- Два независимых пака (`бArr[16]==116` — пак1, `==117` — пак2) — у нас нет понятия «два пака» для
  KingSong вовсе; `WheelState`/`SmartBms` рассчитаны на один набор ячеек.

## 3. Аварии: доходят ли до райдера

**Смешанная картина, не такая однозначная, как «ни одна», найденная у InMotion P6.**

### 3.1 Наш декодер — ни одного `SetAlert`

`grep` по `SetAlert`/`Alert` в `KingsongDecoder.cs` не находит ни одного вызова — единственные
декодеры, которые вообще пишут в `WheelState.SetAlert`, это `GotwayDecoder`, `InMotionDecoder`,
`InMotionDecoderV2` (`grep` по всему `Decoding/`). Ни одно из семи разбираемых нами полей KingSong
(`0xA9/0xB9/0xBB/0xB3/0xF5/0xF6/0xA4-0xB5`) не превращается в именованный флаг тревоги. **По этому
конкретному механизму — то же самое, что нашлось у InMotion P6: ноль.**

### 3.2 Но у нас есть общий, кросс-протокольный канал — ШИМ доходит

Кадр `0xF5` (`DecodeCpuLoad`) кладёт значение output в `_state.SetOutput(...)`, дальше
`_state.UpdatePwm()` ([`KingsongDecoder.cs:236-243`](../WheelTalk.Core/Decoding/KingsongDecoder.cs))
считает `CalculatedPwm = Output / 10000.0` ([`WheelState.cs:224-229`](../WheelTalk.Core/Decoding/WheelState.cs)).
Это тот же `Pwm`, который читает общий (не завязанный на конкретный протокол) движок тревог
`AlertEvaluator` (`window.Max(s => Math.Abs(s.Pwm))`, [`AlertEvaluator.cs:88`](../WheelTalk.Core/Alerts/AlertEvaluator.cs),
пороги `PwmWarning`/`PwmCritical`, `AlertEvaluator.cs:109-115`). **Значит хотя бы предупреждение по
перегрузке (ШИМ) у KingSong в нашем приложении реально доходит до райдера** — через общий механизм,
не через декодер-специфичный `SetAlert`. Это заметно отличает KingSong от InMotion P6, где даже
общий путь не работал (P6 не пишет `Pwm` вовсе, см. `inmotion-loeuc-comparison.md` §1.5).

### 3.3 У официального приложения — архитектура для показа ошибок есть, конкретный кадр не установлен

`bean/DeviceBleBean.java` (в периметре задания) держит поля `errorCode`/`errorMsg`
(`DeviceBleBean.java:47-48`, геттеры/сеттеры `216-222`/`577-583`). Рядом с этим в `bean/` — целое
семейство HTTP-справочников кодов неисправностей: `TroubleCodeBean`/`TroubleCodeTwoBean`/
`BmsTroubleCodeBean` (все три — обычные REST-DTO с пагинацией `code/data/msg/page/pagenum/status/
total`, скачиваются с сервера) с полями `code`/`en`/`zh_cn`/`trouble_url` на каждую запись
(`TroubleCodeBean.java:10-17`, `TroubleCodeTwoBean.java:32-59`) — то есть код ошибки, пришедший с
колеса, приложение резолвит в человекочитаемый текст **через облачный словарь**, с ссылкой на
статью помощи.

**Это архитектурное доказательство, не побайтовое.** Я вижу, что у официального приложения есть
место, куда кладётся код ошибки (`DeviceBleBean.errorCode`), и механизм превращения кода в текст —
но **какой именно входящий кадр заполняет `errorCode`/`errorMsg`, в моих четырёх файлах не
установлено**: ни `BleService` (чистый транспорт), ни `BmsService` (диагностический дамп, не поля),
ни остальной `bean/` этого не показывают — разбор, видимо, идёт в классе вне периметра (капкан 2).
**Вывод, с честной границей факта**: у KingSong, в отличие от доказанного «ноль аварий» на InMotion
P6, официальное приложение как минимум **способно** показать код ошибки колеса пользователю
(инфраструктура существует и не пустая заглушка) — считать ли это «доходит» без знания байта-триггера
нельзя, честно фиксирую как частично подтверждённое, не полное «да».

**Закрыто во второй части (раздел «Добавление», кадр `0xF6`).** Байт-триггер найден: смещение 14-15
кадра `0xF6` (того же, что несёт лимит скорости) — 16-битный код ошибки, безусловно записываемый в
`errorCode`/`errorMsg` и резолвящийся через `TroubleCodeTwoBean`. Наш декодер этот кадр уже читает
(ради лимита скорости) и полностью игнорирует смещение 14-15 — см. раздел «Добавление» ниже.

## 4. Температура: формула

**У KingSong протокол устроен иначе, чем у InMotion, и в этом виде ту же ошибку (`+80-256`) сделать
негде.**

Наш разбор кадра `0xA9` читает температуру как **полный знаковый 16-битный** формат:
```csharp
_state.SetTemperature(MathsUtil.GetInt2R(buff, 12));
```
(`KingsongDecoder.cs:171`) — `GetInt2R` ([`MathsUtil.cs:56-68`](../WheelTalk.Core/Decoding/MathsUtil.cs))
делает знаковое чтение `(sbyte)bytes[starting+1] << 8 | bytes[starting] & 0xFF` — то есть **два
байта, знак берётся из старшего байта честным сдвигом**, без какой-либо ручной прибавки константы.
`TelemetrySnapshot.TemperatureC => TemperatureRaw / 100` ([`TelemetrySnapshot.cs:56`](../WheelTalk.Core/Contracts/TelemetrySnapshot.cs))
— то есть на проводе температура KingSong идёт в сотых долях градуса, тем же способом, что и
напряжение (центивольты). Диапазон значения — весь `-32768..32767` в сотых, никакого сжатия в один
байт с переносом через `+80` нет вовсе.

Формула InMotion, дающая расхождение на 256 (`(b & 0xff) + 80 - 256`, документировано в
[`AGENTS.md`](../../loeuc/AGENTS.md) §8 и разобрано подробно в
[`inmotion-loeuc-comparison.md`](inmotion-loeuc-comparison.md)), **структурно про другой формат**:
там температура — один байт, интерпретируемый то как знаковый, то как беззнаковый в зависимости от
диапазона, и порт эту развилку теряет. У KingSong такой развилки в принципе нет — читается сразу
двухбайтовое знаковое поле, `MathsUtil.GetInt2R` не содержит ручной арифметики со смещением/
переполнением, которую можно было бы перепутать со знаком. **Не вижу класса той же ошибки** в этом
месте нашего кода.

**Чего не хватает для полного ответа**: формулы/масштаба по стороне производителя — ни в
`DeviceBleBean` (поле `temperature`/`electricalTemperature`/`batteryTemperature` — просто `String`,
без видимой арифметики, `DeviceBleBean.java:79,45,29`), ни где-либо ещё в моих четырёх файлах не
видно, как байты кадра превращаются в эти строки — тот шаг вне периметра. Сравнение ограничено:
**наш метод чтения (сигнатура и разрядность) не совпадает по конструкции с известным классом ошибки
InMotion**, но byte-в-byte сверки с первоисточником здесь нет.

## 5. BMS — сведено с Вопросом 2

Отдельная служба `BmsService` у KingSong действительно есть (как и просил вопрос задания), но, в
отличие от ожидания «отдельная служба = более глубокий разбор», здесь она **менее** детальна, чем
наш общий (пока не наполненный) контракт `SmartBms`: она не превращает ни одного байта в
именованное значение, а копит кадры как непрозрачный HTTP-груз (§2.2). Что мы из неё не берём —
буквально всё, но и в самой службе взять особо нечего без класса-парсера вне периметра.

Коротко, что у нас отсутствует и не могло бы взяться даже при портировании `BmsService` 1:1:
- напряжение/температура отдельных ячеек — не видны на этом уровне вообще, только сырые кадры;
- деление на два пака (`0x74`/`0x75`) — механическое (по типу байта), не по смыслу поля;
- цикл готовности (`MainFragmentAty.K4`, ретраи по 500 мс, до 5 попыток, `BmsService.java:37,394-426`) —
  чисто протокольная механика опроса, не про данные.

## Добавление: побайтовая раскладка живой телеметрии — по коду официального приложения

Вторая часть разбора: держатель настоящей раскладки — не `fw.java` (это только каталог исходящих
команд, см. запись выше) и не `defpackage/i73.java` (это мост на часы через Wearable Data API,
исходящий, проверено и отклонено отдельно). Цепочка приёма живой телеметрии:

1. `BleService` шлёт широковещательный `Intent("bluetooth_data")` на **каждый** кадр, безусловно, в
   обход `gc`/`r` (`BleService.java:317-319`) — уже описано выше;
2. `MainFragmentAty` держит на него ресивер (`MainFragmentAty.java:1754,637-676`) и на каждый кадр
   зовёт **диспетчер** `X1(byteArrayExtra)` (`MainFragmentAty.java:675`);
3. `X1(byte[])` — метод на **17880 байткод-инструкций**. Обычный jadx и `--show-bad-code` дают
   заглушку (`MainFragmentAty.java:2070-2076`, `Method not decompiled`) — **капкан 2 сработал
   ровно по книге**: тело не пустое, а потерянное декомпилятором. Вскрыто только `-m fallback`
   (сырые инструкции, регистры переиспользуются, порядок строк ≠ порядку исполнения — читал по
   меткам `goto`/`Lxxxx` и по вызовам хелперов `Y1`/`a2`/`h2`, не сверху вниз, как предупреждал
   капкан 3).

**Источник и его ограничения.** Ссылки ниже — `MainFragmentAty.java:N` внутри
`...\scratchpad\ks-raw\MainFragmentAty.java` (fallback-дамп, 16137 строк, путь временный, не
репозиторный — нумерация своя, не совпадает ни с обычным jadx-дампом, ни с исходным `.java` из
`src_kingsong`). **Смещение и константа сравнения — факт** (прочитаны прямо из инструкции чтения
массива и `if`). **Имя поля и его физический смысл — факт, когда прослежен до `DeviceBleBean.setXxx(...)`
в том же куске кода** (регистр r2 — это `this`, поля вроде `U2`/`c3`/`b3` — обфусцированные instance-поля
`MainFragmentAty`, промежуточные перед записью в `DeviceBleBean`). Где такой цепочки нет — помечено
отдельно как невыведенное, не домысливаю.

### Конверт до диспетчера — второй, отдельный от `AA 55`

Прежде чем дойти до `AA 55`-ветки, `X1` сначала проверяет **другой заголовок**:

метка `L33a`), код входит в знакомую нам ветку — и уже внутри неё проверяет `bArr[16]`.

### Кадр `0xF6` (246) — здесь и живёт код ошибки, отвечающий на Вопрос 3

(`MainFragmentAty.java:8877-9054`, метка входа `L1d48`)

| Смещение | Хелпер | Множитель | Поле | Строка |
|---|---|---|---|---|
| 2-3 | `Y1` | `/100` | `nowMaxSpeedNum` (лимит скорости) | `8903-8911,8918-8925` |
| 6-9 | `a2` | без деления (Вт·ч) | `totalEnergy`; `avgEnergy` = то же / пробег | `8926-8965` |
| 12-13 | `Y1` | без деления (сек) | `allTime` (общее время в сети) | `8966-8972` |
| **14-15** | **`Y1`** | **без деления** | **`errorCode`/`errorMsg`** | **`8973-9053`** |

Смещение 2-3 совпадает с нашим `DecodeSpeedLimit`
([`KingsongDecoder.cs:246-252`](../WheelTalk.Core/Decoding/KingsongDecoder.cs): `MathsUtil.GetInt2R(buff,2)
/ 100.0`) дословно — тот же кадр, та же формула.

**Ответ на Вопрос 3 (аварии).** Смещение 14-15 того же самого кадра 0xF6, который наш декодер уже
разбирает (только ради лимита скорости), содержит **код ошибки колеса**. Официальное приложение:
1. читает `Y1(bArr[14], bArr[15])` как есть (без деления);
2. сравнивает с четырьмя «пустыми» значениями — `128(0x80)`, `228(0xE4)`, `2225(0x8B1)`, и `213(0xD5)`
   при дополнительном условии (`MainFragmentAty.java:8978-8988`) — похоже на «нет ошибки»/сигнальные
   заглушки, не проверено, что именно каждое означает;
3. **безусловно** пишет `DeviceBleBean.setErrorCode(String.valueOf(код))`
   (`MainFragmentAty.java:9001`);
4. ищет код в заранее скачанном словаре `MainFragmentAty.o4` (тип `List<TroubleCodeTwoBean.DataDTO>`
   — тот самый класс, что я уже нашёл в первой части через `bean/TroubleCodeTwoBean.java`) и кладёт
   локализованный текст (`getZhCn()`/`getEn()`, по языку интерфейса) в `setErrorMsg(...)`
   (`MainFragmentAty.java:9004-9049`).

**Это закрывает открытый вопрос из первой части: код ошибки приходит по проводу в кадре 0xF6,
смещение 14-15, тем же самым кадром, что несёт лимит скорости.** Наш `DecodeSpeedLimit` читает
только смещение 2-3 и полностью игнорирует 14-15
([`KingsongDecoder.cs:246-252`](../WheelTalk.Core/Decoding/KingsongDecoder.cs) — метод кончается на
`_state.SetSpeedLimit(speedLimit); return false;`, к смещению 14 не обращается). **Значит: у
KingSong авария на проводе есть, приходит регулярно (кадр 0xF6 — обычная телеметрия, не отдельный
редкий кадр по запросу), и мы её прямо сейчас отбрасываем на той же строке, что уже читаем ради
лимита скорости** — не «функции нет», а «читаем не до конца тот же кадр». Это заметно отличается от
InMotion P6, где авария не приходит вообще ни по одному пути, и от первой версии этого документа, где
я честно писал «архитектура есть, кадр не установлен» — **теперь кадр установлен**.

Значения кодов (что означает, например, `213`) — в `TroubleCodeTwoBean`, серверный словарь, я его не
скачивал и не сверял; сам факт «код есть, лежит на смещении 14-15» — из кода, не из словаря.

### Кадры `0xA4`(164) и `0xB5`(181) — не одна раскладка, вопреки нашему комментарию

(`0xA4`: `MainFragmentAty.java:8658-8687`, метка `L1b8e`; `0xB5`: `MainFragmentAty.java:8688-8747+`,
метка `L1bbc`)

Наш декодер обрабатывает оба этих типа **одним и тем же методом**
(`0xA4 or 0xB5 => DecodeAlarmAndMaxSpeed`, [`KingsongDecoder.cs:144`](../WheelTalk.Core/Decoding/KingsongDecoder.cs)),
как и написано в комментарии — порт `KingsongAdapter.java:228-242`. **В официальном приложении это
не так**:

- `0xA4` (`8658-8687`) — читает только `bArr[2]`/`bArr[3]` как флаги (0/1, битовые проверки) и шлёт
  сообщения хендлеру (`sendEmptyMessage(4)`/`(5)`) — **это подтверждение калибровки/настройки, не
  скоростные пороги вовсе**, значений выше смещения 3 не читает;
- `0xB5` (`8688-8747+`) — читает **четыре 16-битных поля** (`Y1`, не отдельные байты):

  | Смещение | Поле |
  |---|---|
  | 4-5 | `speedLevel1` |
  | 6-7 | `speedLevel2` |
  | 8-9 | `speedLevel3` |
  | 10-11 | `waneSpeed` |

Наш `DecodeAlarmAndMaxSpeed` читает **по одному байту** на тех же смещениях 4,6,8,10 (без младшего
байта у 5,7,9,11) и называет их `_ksAlarm1Speed.._ksAlarm3Speed`+`_wheelMaxSpeed`:
```csharp
_wheelMaxSpeed = buff[10] & 0xFF;
_ksAlarm3Speed = buff[8] & 0xFF;
_ksAlarm2Speed = buff[6] & 0xFF;
_ksAlarm1Speed = buff[4] & 0xFF;
```
(`KingsongDecoder.cs:265-268`). Три вещи расходятся разом:
1. **`0xA4` в официальном приложении не несёт скоростных порогов вообще** — наш декодер применяет к
   нему ту же раскладку, что и к `0xB5`, а должен бы (если верить этому источнику) не применять её
   вовсе;
2. **ширина поля**: у них 16 бит (`Y1`), у нас — 8 бит (только чётный байт смещения). На типичных
   значениях (скорости до 255 км/ч) старший байт наверняка нулевой и разницы нет, но это не то же
   самое чтение;
3. **имя смещения 10-11**: у нас это `_wheelMaxSpeed` (макс. скорость колеса), у официального
   приложения то же смещение называется `waneSpeed` — **другое поле по имени**, не «максимальная
   скорость». `DeviceBleBean.maxSpeed` (строковое поле) в `MainFragmentAty.java` вообще не
   присваивается ни разу (`grep` по `setMaxSpeed(` — ноль совпадений) — то есть «максимальная
   скорость» в этом приложении, похоже, берётся не из живого кадра, а из настроек/профиля модели, не
   из `0xB5` вовсе. **Не выведено до конца** — куда идёт `waneSpeed`, что это физически (кандидат по
   переводу — порог входа в режим ослабленного поля/спада мощности, не проверено) — фиксирую как
   открытое.

**Это не WheelLog-совпадение и не наша ошибка порта** — это независимое расхождение между
реверс-инженерным `KingsongAdapter.java` (общий предок и нашего порта, и, видимо, самого допущения
«0xA4 похож на 0xB5») и настоящим протоколом производителя. Капкан 3 в чистом виде: **раскладка
одного типа кадра не переносится на другой без проверки**, и здесь она перенесена ошибочно —
кем изначально, WheelLog или составителем нашего декодера, не устанавливаю, только фиксирую разницу.

### Кадр `0xBB`(187) — имя, версия иначе, чем мы думали

(`MainFragmentAty.java:9814-9847`, метка входа не найдена в окне чтения, до `L264c`)

Строка имени (смещения 2-15, до первого нулевого байта либо 14 байт) читается тем же приёмом, что и
у нас — посимвольно до нуля, дальше делится по `-` на модель/версию. Но **до этого** код читает
`Y1(bArr[18], bArr[19]) & 0xFFFF` (`MainFragmentAty.java:9816-9822`) — **16-битное число на
смещениях 18-19**, которое **не встречается в тексте имени**. Куда оно кладётся дальше — **не
проследил в пределах прочитанного окна** (регистр `r1` не встречается в оставшейся части ветки как
получатель `setXxx`); возможно, используется раньше по потоку инструкций (fallback-дамп не
гарантирует, что использование стоит текстуально после вычисления — капкан 3). **Помечаю как
невыведенное, не домысливаю**, чему равно это число — версия платы отдельно от той, что "зашита" в
текст имени, серийный номер платы, что-то ещё. Наш декодер смещения 18-19 для кадра `0xBB` не
читает вовсе ([`KingsongDecoder.cs:195-218`](../WheelTalk.Core/Decoding/KingsongDecoder.cs),
`DecodeName` — весь метод укладывается в 14 байт имени плюс парсинг текста). **Не могу сказать,
упущение это или нет — смысл поля не установлен**, это открытый вопрос, не находка.

### Развилки по модели (Вопрос 4)

Прямых `if (carType == …)`-ветвлений внутри разобранных полей X1 в прочитанном окне немного, но
есть два конкретных места:

- **`KS-S20`/`KS-S22` — сравнение по имени модели** (`MainFragmentAty.java:9893-9911`): если
  распознанная из кадра `0xBB` модель (переменная `k4`) равна `"KS-S20"` или `"KS-S22"`, флаг `X2`
  ставится в `false` (и второй флаг `y1` — тоже); для всех остальных моделей `X2 = true`. Этот же
  флаг `X2` используется в разборе кадра `0xA9` (`MainFragmentAty.java:9171`) — **вибрация при
  превышении скоростного порога включена не для этих двух моделей**. Значит хотя бы одно наблюдаемое
  поведение (виброотклик на пороге скорости) у `KS-S20`/`KS-S22` устроено иначе, чем у всей
  остальной линейки — **не проверял, что именно отличается физически на этих колёсах**, только что
  код различает их по имени явно;
- **`"car_type"` из `SharedPreferences`** (`MainFragmentAty.java:8881-8891`): в кадре `0xF6` расчёт
  оставшегося процента заряда (`kwh`, диапазон 1..101 при определённых условиях) применяется только
  если сохранённый `car_type` **не равен** текущему языковому идентификатору по умолчанию — то есть
  ветка привязана к тому, было ли распознавание типа машины успешным, не к конкретной модели
  напрямую. Слабее первого примера, но тоже завязано на распознанный тип машины.

Оба случая — **разные модели, разные ветки поведения в том же самом диспетчере `X1`, не в отдельном
классе на модель** (не как у InMotion, где `carType` расходится по методам `RealTimeVXX`). У KingSong
это плоский `if`/`else` внутри одного гигантского метода — соответствует находке о размазанности
разбора по экранам, но здесь размазанность **внутри одного метода**, не по разным `.java`-файлам.

### Итог по второй части

1. **Раскладка живой телеметрии для 0xA9 подтверждена дословно** — наш порт `KingsongAdapter.java`
   не разошёлся с официальным приложением ни на одно смещение, ни на один множитель.
2. **0xB9**: смещения вентилятора/заряда/пробега/температуры совпадают, но мы не читаем время
   поездки (6-7) и два флага режима (10/11) — реальный, некритичный пробел.
3. **0xF6 несёт код ошибки на смещении 14-15 — райдер у KingSong получает аварию, если приложение
   работает штатно, а наш декодер её отбрасывает** на той же строке, что уже читает лимит скорости.
   Это главная находка второй части и прямой ответ на Вопрос 3.
4. **0xA4 и 0xB5 — разные кадры с разной раскладкой**, наш общий обработчик для обоих (унаследованный
   от `KingsongAdapter.java`) в лучшем случае не различает их, в худшем — читает мусор для 0xA4 как
   если бы это были скоростные пороги.
5. **0xBB несёт дополнительное 16-битное поле на смещении 18-19**, назначение которого не установлено
   ни у нас, ни (в пределах прочитанного) у них.
6. Развилки по модели внутри `X1` — плоские `if`, привязанные к строке модели/типу машины, не
   отдельные методы на семейство.

## Добавление 2: облачный словарь кодов ошибок — можно ли запросить его нашим приложением

Третья часть, отдельный запрос владельца. Раздел «Аварии» выше нашёл, что код ошибки колеса
(смещение 14-15 кадра `0xF6`) официальное приложение резолвит в текст **через HTTP**, не из
собственных ресурсов — значит расшифровать код на своей стороне мы не можем без того же запроса.
Вопрос: устроен ли этот запрос так, что мы можем повторить его сами. **Только чтение кода, к серверу
не обращался ни разу.**

**Капкан по дороге, важный сам по себе**: в приложении **два независимых клиента на один и тот же
контракт**. Старый — `HttpParameterUtil`/`OkHttpUtil` (ручная сборка `OkHttp`-запроса), там же метод
`postTroubleCodes()` с **нулём параметров** сверх подписи. Новый, живой — `HttpClient`/`CommonRequest`
поверх Retrofit-интерфейса `ApiService`, и вызывается он из `MainFragmentAty.java` — то есть это и
есть то, что реально уходит с телефона. Ответ ниже — по **живому** пути; версия из
`HttpParameterUtil` упомянута только там, где расходится, как предостережение против чтения
не того клиента (тот же принцип, что капкан 1 предыдущей части: имя метода — не доказательство,
доказательство — кто его действительно зовёт).

### 1. Авторизация — не нужна ни для одного из двух словарей

Оба метода `ApiService` размечены Retrofit-аннотациями `@nv1("api/equipment/troublecode")`/
`@rk0`/`@re0` (`ApiService.java:298-300` — POST, форма, карта полей) и
`@nv1("api/equipment/bmstroublecode")`/`@rk0`/`@re0` (`:163-165`) — ни один заголовок авторизации
аннотацией не объявлен.

- **`equipment/bmstroublecode`** (`HttpClient.getBmstroublecode(String carModel)`,
  `HttpClient.java:444-449`): в тело идёт `carModel` и стандартный набор `ew1.n().j(...)`
  (см. вопрос 2) — **`sid` (токен входа) не добавляется вовсе**, ни условно, ни безусловно;
- **`equipment/troublecode`** (`HttpClient.postTroubleCodes()`, `HttpClient.java:796-803`): `sid`
  добавляется, **только если он уже есть** (`if (pr2.b(a02.k("token", ""))) …` — `pr2.b` это
  проверка «непусто», `pr2.java:11-13`) — анонимный вызов просто не кладёт это поле в форму, отказа
  на этом не построено нигде в прочитанном коде.

**Единственное, что похоже на «токен», в обоих запросах, — не токен входа, а подпись без секрета
пользователя.** `ew1.n().j(treeMap)` (`ew1.java:199-217`, зовётся в обоих методах) добавляет
`apiversions`/`lang`/`temptime`/`mobiletype`/`appbiaoshi`(литерал)/`apptype`/`phone_type`, затем
**вычисляет** поле `token`: сортирует все параметры по ключу, склеивает `key=value&…`, добавляет
**фиксированную строку из кода приложения** `a02.h0 = "$2a$10$Xw68Ojbxd5FWB1r5qQxDZu"`
(`a02.java:70`) и берёт MD5 от результата (`ew1.java:90-121`, метод `a`). Это подпись запроса общим
для всех клиентов приложения секретом, зашитым в APK, — не логин и не персональная авторизация.
**Прямое подтверждение из соседних констант того же файла**: пары `equipment/decode`/
`equipment/nologindecode`, `equipment/pass`/`equipment/nologinpass`, `equipment/check`/
`equipment/nologincheck` (`iw.java:118-123`) — у производителя есть явный, штатный класс
«no-login»-эндпоинтов; `troublecode`/`bmstroublecode` по фактическому коду ведут себя так же, просто
без отдельного «nologin»-имени в пути.

**Вывод: словарь можно запросить без учётной записи.** Понадобится только: путь, форма из §2 и
пересчитанная подпись `token` по алгоритму выше (соль `a02.h0` — открытый текст в декомпиляте,
не секрет сервера).

### 2. Полный вид запроса

Оба — **`POST`**, тело — **`application/x-www-form-urlencoded`** (`qk0.a` — построитель тела в
`OkHttpUtil.getRequestBody`, `OkHttpUtil.java:1214-1227`, тот же вывод независимо подтверждён
аннотацией `@rk0`=`FormUrlEncoded` у Retrofit-версии). Заголовков сверх обычных для формы — ни
одного: `getHeaders(map)` строится из карты, которую оба вызова передают **пустой**
(`new TreeMap()`, `HttpParameterUtil.java:189,480`).

**Базовый адрес по коду** — `https://www.kingsong.site/index.php/api/` (`iw.java:37`, `C`). Голый
IP `120.77.146.212` из задания в этом файле не встречается нигде, кроме одного не относящегося к
делу места (`postReportlockstatus`, `HttpParameterUtil.java:435`, сравнение строки ради выбора
запасного `sid` для другого метода) — **вероятно, это тот же адрес, к которому резолвится домен**,
но по коду это не проверить, а обращаться к серверу, чтобы проверить, запрещено заданием. Фиксирую
как несовпадение форм записи, не как расхождение по сути.

| Эндпоинт | Путь | Обязательные поля | Необязательные поля |
|---|---|---|---|
| Общий справочник (`TroubleCodeTwoBean`) | `api/equipment/troublecode` | `apiversions`, `lang`, `temptime`, `mobiletype`, `appbiaoshi`, `apptype`, `phone_type`, `token` (подпись, см. §1) | `sid` — только если уже вошёл в аккаунт |
| Справочник BMS (`BmsTroubleCodeBean`) | `api/equipment/bmstroublecode` | то же плюс **`carModel`** | — |

`lang` — не языковой выбор в обычном смысле: метод, который должен переводить код языка
(`ew1.o(String)`, `ew1.java:81-88`) устроен как `switch` **без единого `case`** — при любом входе
возвращает один и тот же `hw.u1 = "zh_CN"` (`hw.java:159`). **По факту `lang` всегда равен `zh_CN`,
что бы ни было выставлено на телефоне** — это либо намеренно нерабочая ветка, либо остаток после
вырезанной локализации; в любом случае для читателя запроса это означает: **параметром `lang`
языковой выбор в ответе не управляет** (ответ не завязан на него так, как можно было бы подумать —
см. §3).

### 3. Что возвращается

Оба бина — `code/data/msg/page/pagenum/status/total` на верхнем уровне
(`bean/TroubleCodeTwoBean.java:9-30`, `bean/BmsTroubleCodeBean.java:6-13`) — форма пагинации есть в
структуре, но **ни один из двух запросов не передаёт `page`/`size`/`pagenum` в теле** — значит
если постраничность и работает, она работает на значениях по умолчанию сервера, не выбирается
клиентом; сколько записей приходит за раз, из кода не видно (ответ не читал, задание запрещает
обращаться к серверу).

Одна запись справочника (`TroubleCodeTwoBean.DataDTO`, `:32-59`): `id`, `code`, `en`, `zh_cn` — **и
только эти два языка**, поля `ru`/русской локали нет вовсе на уровне структуры — добавить её иначе
как на нашей стороне (переводом по коду, раз коды у нас те же) нельзя, сервер её не пришлёт ни при
каком `lang`. Плюс `troubleUrl` (ссылка на статью помощи), `createtime`/`updatetime`/`isdel`
(служебные). У `BmsTroubleCodeBean.Data` (`:15-24`) — тот же набор `code`/`en`/`zh_cn`, плюс
`carModel` — **прямое подтверждение, что этот словарь размечен по модели** (сервер явно возвращает
поле `carModel` в каждой записи, значит одна и та же таблица кодов может отличаться по колёсам).

**Привязан ли словарь к модели колеса — по-разному для двух эндпоинтов**:
- `equipment/troublecode` (общий) — **нет**, запрос не несёт ни `carModel`, ни `serialNumber`,
  ни что-либо колесо-специфичное — один и тот же словарь для всех;
- `equipment/bmstroublecode` (BMS) — **да**, `carModel` обязателен в запросе и есть в каждой записи
  ответа — это подтверждённый факт (капкан задания: не путать эти два эндпоинта местами — они ведут
  себя по-разному именно в этом).

### 4. Когда приложение его запрашивает

- **Общий справочник** — `postTroubleCodes()` зовётся из `K2()`, а `K2()` — из блока, похожего на
  инициализацию активности (`MainFragmentAty.java:2895-2900`, соседние вызовы —
  `b2.c(getApplicationContext())`, проверка разрешений, `q2()`) — **похоже на «один раз при
  открытии приложения»**, не привязано к подключению к колесу;
- **Словарь BMS** — `CommonRequest.getBmstroublecode(model)` зовётся сразу после того, как в
  `MainFragmentAty` становится известна модель подключённого колеса
  (`MainFragmentAty.java:1393,1397` — в одном блоке с `P4.setModel(...)`) — **привязано к событию
  «модель определена», то есть примерно к каждому новому подключению**, не к самому запуску
  приложения и не к моменту получения кода ошибки.

Ни тот ни другой вызов не встретился мне рядом с разбором кадра `0xF6` (там, где реально
всплывает код ошибки, `MainFragmentAty.java:8973-9053` — см. раздел «Добавление» выше, §«Кадр
`0xF6`»). Список `MainFragmentAty.o4` (тип `List<TroubleCodeTwoBean.DataDTO>`, тот же раздел) там
только читается, не запрашивается — то есть **словарь запрашивается заранее и кэшируется**, до
того, как код ошибки понадобится для перевода, не в момент самой аварии. Значит и обновляется он
не чаще, чем происходят эти два события (запуск приложения / новое подключение), а не при каждой
ошибке.

Не разбирал ни один из них дальше названия и сигнатуры — не входило в запрос, отмечаю как наводку.

### Итог

**Да, можно** — ни один из двух словарей не требует входа в аккаунт по коду, который реально
выполняется (`HttpClient`/`ApiService`, не устаревший `HttpParameterUtil`). Нужны: `POST` с
form-телом на `api/equipment/troublecode` (общий) или `api/equipment/bmstroublecode` (BMS, плюс
`carModel`), обязательные поля из таблицы §2, и подпись `token` = `MD5(отсортированные_пары
"key=value&" + "$2a$10$Xw68Ojbxd5FWB1r5qQxDZu")`. Ответ несёт английский и китайский тексты (не
русский) на каждый код, привязку к модели — только у BMS-версии. **Решение, обращаться ли к серверу
владельца, и сам запрос (один, не перебором) — не мои, отдано владельцу, как и было сказано.**
