> **Статус: ✅ выполнен 10.08.2026** — этап 0 и лечение §3.2 + §3.1а в один день.
> **Этап 0 назвал виновника числом:** `SetPoints` работал **115–370 мс на главном потоке каждые
> ~1,5 с** — стройка данных графика (по Java-точке через JNI) осталась в `chart.Post`, хотя чтение
> истории давно вне кадра; вдобавок точек приходило **1334 при ширине 720 px** — кап считал

> **Лечение:** стройка уехала в `FillAsync` за `ConfigureAwait(false)`, главному потоку остался
> `ShowData` 3–4 мс; корзин просится вдвое меньше точек (точек стало ≤ ширины); в прокрутке
> (`ScrollWatch`) графики не поллятся и снимок по плиткам не разносится (§3.1а одной стражей).
> **Числа:** p90 53→25 мс, p95 69→28, p99 **200→46**, janky 65→53 % (медиана 17 мс — базовая
> цена отрисовки, §4 «за идеальными 60 fps не гнаться»). Гейт глазами — за владельцем.
>
> Предыстория: лаг переходов и ANR закрыты
> `6699f84` (горячий цикл подбора кегля), после чего владелец: «всё ещё есть лаги при прокрутке
> экрана вверх-вниз». Это другой класс беды: не разовый пересчёт, а цена каждого кадра прокрутки.

**Цель:** fling по «Цифрам» на BV6600Pro идёт без видимых рывков при живом реплее.

**Границы.** Подбор кегля не трогается (закрыт замком `TileTypographyCostTests` и не зовётся в

просмотр. Вид плиток не меняется ни на пиксель.

## 1. Что известно и чего не знаем

Устройство экрана: `RecyclerView` (`_list`), кадры идут через `MainScreenDriver.PostOnAnimation`
— `Show()` зовётся на каждом кадре (60/с), но настоящая работа отсечена: снимок телеметрии
приходит 5 раз в секунду, и `TileAdapter.Render` выходит по `ReferenceEquals` на повторном.

**Чего не знаем: какая стадия кадра горит.** Прокрутка на аппаратной отрисовке сама по себе
дёшева — готовые узлы отрисовки просто сдвигаются; дорогим кадр делает то, что в него *вклинилось*:
перекладка, привязка новой плитки, стройка данных графика, GC. Пока стадия не названа замером,
любая правка — гадание. Урок пересчёта кеглей ровно об этом: мастер нашёл корень счётом
(3095 обращений), а не подозрением.

## 2. Этап 0 — замер. Обязателен до любой правки

Один инструментированный прогон (проверочные циклы ограничены — слово владельца):

1. `adb shell dumpsys gfxinfo com.wheeltalk.lab.droid reset`, затем fling сверху вниз и обратно
   по реплею, затем `dumpsys gfxinfo com.wheeltalk.lab.droid framestats`: доля janky-кадров
   (это число «до» для гейта) и разбивка худших кадров по стадиям — measure/layout, draw, sync.
2. `logcat`: паузы GC (`background concurrent copying`); строки `WheelTalk.Tiles: Remeasure` —
   убедиться, что пересчёт в прокрутке **не** зовётся (если зовётся — это находка №1).
3. Временные счётчики под `#if DEBUG` (снять после замера): сколько `requestLayout` в секунду
   при прокрутке; попадает ли `SetPoints` графиков в прокрутку; зовётся ли `OnCreateViewHolder`
   посреди fling.

Выход этапа — **имя горящей стадии и числа**, не догадка.

## 3. Подозреваемые — в порядке вероятности

### 3.1 `SetText` на кадре телеметрии → `requestLayout` → перекладка всего списка

Каждый пятый-в-секунду снимок переставляет текст изменившимся плиткам
(`MetricTileView.Render` → `TextView.TextFormatted`), а `SetText` у `TextView` тянет за собой
`requestLayout`. Дитя `RecyclerView`, попросившее перекладку, поднимает measure/layout всего
списка — и каждые 200 мс кадр прокрутки получает эту работу поверх своей. По построению она не
нужна вовсе: кегль и бокс числа уже посчитаны подбором и от смены «21,8» на «21,9» не меняются.

Лечение, по нарастающей цене:

- **а) Не переставлять текст, пока список в прокрутке.** `OnScrollListener`: состояние не
  `Idle` — последний снимок копится, применяется по остановке. Дёшево и честно: на летящем
  экране смену десятой доли глаз всё равно не читает. Плитки, въезжающие в экран, привязываются
  свежим снимком как привязывались.
- **б) Вью числа без перекладки.** Своя лёгкая вью: готовая строка рисуется `DrawText` в готовом
  боксе, смена текста — `Invalidate` без `requestLayout`. Геометрия вся уже есть у
  `TileTypography`. Убирает класс проблем целиком, но это новая вью и новые тесты — делать,
  только если (а) не взяло гейт.

### 3.2 Графики: данные строятся на главном потоке сотнями Java-точек

`FillAsync` читает историю вне потока отрисовки (это сделано планом 23), но **готовит данные —
на нём**: `SetPoints` → `ChartLine.Build` — по `Entry` на точку, точек до ширины плитки в
пикселях (~700), каждая — объект за JNI-швом. Раз в 1–2 секунды на каждую плитку-график; попав
в кадр прокрутки — гарантированный пропуск.

Лечение: не поллить в прокрутке (тот же scroll state, что в 3.1а — «окно едет» и подождёт
секунду); стройку `ChartLine.Build` унести в `FillAsync` за `await`, главному потоку оставить
вручение готового `Data` и `Invalidate`.

### 3.3 Плитка-график рождается при въезде в экран

`OnCreateViewHolder` для графика создаёт `LineChart` — дорогой платформенный объект с осями и
рисовальщиками. Первый проезд мимо графиков дёргается об это по разу на плитку, дальше держатели
переиспользуются. Лечение — если замер покажет create посреди fling: прогреть пул
(`RecycledViewPool`) после первой раскладки, вне кадра.

### 3.4 Плашка связи перерисовывает корень покадрово

Пока фаза связи не `Live`, `TilesScreen.Show` зовёт `_root.Invalidate()` на каждом кадре — весь
корень, а не прямоугольник плашки. На реплее фазу показать замером; лечение — инвалидация
областью (`Invalidate(rect)`) и только при смене того, что нарисовано (фаза/секунды/имя).

### 3.5 Мелочь: аллокации кадра

`MainScreenFrame`-запись строится 60 раз в секунду, `MetricNumber.Compose` рождает
`SpannableString` на смену числа. Трогать **только** если этап 0 покажет паузы GC: чинить
аллокации без улик — это опять чинить симптомы.

## 4. Чего не делать

| Что | Почему |
|---|---|
| Чинить всё скопом | Одна правка — один контрольный замер тем же жестом; иначе неизвестно, что помогло |
| Свой рисовальщик графика | Решение владельца 04.08.2026: одна библиотека на плитку и полноэкранный просмотр |
| Трогать подбор кегля | Закрыт `6699f84` и замком цены; в прокрутке не зовётся |
| Гнаться за идеальными 60 fps | Телефон бюджетный; гейт — «без видимых рывков», числом ниже |
| Держать счётчики в Release | Инструментовка этапа 0 живёт под `#if DEBUG` и снимается после |

## 5. Гейты

1. **Числом.** Тот же fling по тому же реплею: доля janky-кадров в `framestats` заметно ниже
   числа «до» с этапа 0 (ориентир — единицы процентов); худший кадр вне рождения вью ≤ ~32 мс.
2. **Глазами.** Fling без видимых рывков; вход и выход правки не регрессировали (лог
   `Remeasure` — пересборок в прокрутке ноль).
3. **Замками.** 468 тестов зелёные; вид плиток не изменился ни на пиксель.

**Порядок:** этап 0 → чинить только то, что замер назвал по имени (ожидаемо 3.1а + 3.2) →
контрольный замер → остальное лишь если гейт не взят.
