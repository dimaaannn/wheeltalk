# KingSong: каталог исходящих команд — сверка с нашим декодером

Третья часть разбора родного приложения `com.kingsong.dlc` (декомпилят —
`C:\Work\repos\loeuc\src_kingsong`, **не обфусцирован в Java-слое**, но метки методов —
машинные, R8). Первые две части — приём телеметрии
([`kingsong-telemetry-comparison.md`](kingsong-telemetry-comparison.md)). Здесь — **исходящие
команды**: каталог `defpackage/fw.java` (2778 строк, около сотни билдеров кадров, **прочитан
целиком** в прошлой сессии) плюс шесть экранов, где часть команд собирается прямо на месте, в
обход `fw`: `SpeedSettingActivity`, `RideModeActivityNew`, `GearAdjustmentActivity`,
`WeakMagneticSpeedActivity`, `AuxiliaryAccelerationActivity`, `LightSelectColorFragment`. Прошивка
и часы — не эта часть, не трогал.

**Наша сторона**: [`KingsongDecoder.cs`](../WheelTalk.Core/Decoding/KingsongDecoder.cs) (билдеры в
конце файла), [`WheelCommand.cs`](../WheelTalk.Core/Contracts/WheelCommand.cs),
[`IWheelDecoder.cs`](../WheelTalk.Core/Decoding/IWheelDecoder.cs). Формат и подход к рискам — по
образцу [`veteran-commands-import-plan.md`](veteran-commands-import-plan.md) (тот же класс
находок: коллизия опкода, генерационные развилки, список запрещённого).

**Метод.** `fw.java` обфусцирован — имена методов (`A0`, `H0`, `k1`…) ничего не говорят. Смысл
даёт **место вызова**: шесть названных экранов зовут конкретные методы `fw.*` с говорящим
контекстом рядом (подписи полей, диапазоны seekbar'ов, единицы измерения). Где вызов найден —
назначение задокументировано с ссылкой на экран. Где не найден (подавляющее большинство из ~100
билдеров `fw.java` вызывается из экранов вне заданного списка, либо только из `FirmwareUpdateActivity`
— прошивка, не эта часть) — **байты приведены, назначение помечено неустановленным**, не
домысливается по имени метода.

**Формат ссылок.** Их сторона — `файл:строка` внутри `src_kingsong/sources/…`. Наша — обычные
`файл:строка` внутри `WheelTalk.Core`.

## 2. Что умеем мы

Пять билдеров в [`KingsongDecoder.cs`](../WheelTalk.Core/Decoding/KingsongDecoder.cs) (`405-452`):
`BuildWheelBeep`(0x88), `BuildSetLightState`/`BuildSwitchFlashlight`(0x73, через
`BuildLightModeCommand`), `BuildUpdatePedalsMode`(0x87), `BuildCalibrate`(0x89),
`BuildResetTrip` → всегда `null` (нет аналога у `KingsongAdapter.java`, как и в
`veteran-commands-import-plan.md` для Veteran). `WheelCommand.cs` — тот же закрытый список из
шести вариантов на все протоколы разом (`Beep`/`SetLight`/`SwitchFlashlight`/`SetPedalsMode`/
`ResetTrip`/`Calibrate`), реализован только срез Veteran+KingSong.

**Чего у нас нет вовсе — из найденного в этой части:**

- запись скоростных порогов тревоги (0x85) — **осознанно исключено** уже на этапе первой части
  (класс-комментарий `KingsongDecoder.cs:46-49`: «wheel beeps on its own thresholds… command 0x85
  is never built at all»). Теперь известна точная раскладка (см. §1) — если решение когда-нибудь
  пересмотрят, байты для этого уже есть;
- запись порога мощности/ШИМ (0x8A, страница 13) — не было известно вовсе, не упомянуто и в
  комментарии декодера;
- вспомогательное ускорение (0x8A, страница 17) — то же, полностью новое для нас;
- выбор пресета езды (0x1B, оба варианта) — новое;
- запись PIN/пароля колеса (0x44) — новое, и по образцу LeaperKim это **опасная** категория (§4).

**Разбор режима педалей — единственная команда с прямым 1:1-аналогом, и в ней найдено
расхождение.** Наш `BuildUpdatePedalsMode` ([`KingsongDecoder.cs:439-446`](../WheelTalk.Core/Decoding/KingsongDecoder.cs)):
```csharp
byte[] data = EmptyRequest(0x87);
data[2] = (byte)pedalsMode;
data[3] = 0xE0;
data[17] = 0x15;   // ← не совпадает с оригиналом
```
Официальное приложение, тот же смысл (`GearAdjustmentActivity.java:279` → `fw.H0(int)`,
`fw.java:439-450`):
```java
bArr[2] = (byte) i;
bArr[3] = -32;      // = 0xE0, совпадает
bArr[17] = 20;      // = 0x14, ОБЫЧНЫЙ заполнитель — не 0x15
```
**Смещения 2 и 3 совпадают дословно**, но наш порт (унаследованный от `KingsongAdapter.java`,
WheelLog) ставит на байте 17 значение `0x15`, тогда как официальное приложение везде на этом же
байте держит константу `0x14` — здесь она **не заменяется**. Не проверял, влияет ли байт 17 на то,
принимает ли колесо команду (частым явлением у KingSong он выглядит просто заполнителем, но нигде
это не доказано ни у нас, ни у них) — **фиксирую расхождение как факт, не как доказанный баг**:
если когда-нибудь колесо будет молча игнорировать `BuildUpdatePedalsMode`, это первое место для
проверки.

## 3. Коллизии — тип `[16]` делят несколько разных команд

### 3.1 `0x1B`(27) — два вызова, разное значение параметра, потенциальное совпадение

`fw.k1(byte b2)`: `[2] = b2` (в наблюдаемых вызовах — литерал `2`).
`fw.O2(int i)`: `[2] = 3` (константа), `[4] = i` (ID пресета из `SelectModeBean`).

Если `k1` когда-нибудь вызывается со значением `b2 == 3` (диапазон возможных значений `k1` в моём
окне чтения не установлен — видел только литерал `2` дважды, `RideModeActivityNew.java:247,261`),
кадр `k1(3)` и кадр `O2(любой ID)` с `[4]==0` **совпадут по байтам 0-4** и разойдутся только на
`[4]`, если `i≠0`, либо не разойдутся вовсе, если `i==0`. **Не доказанная коллизия** (не видел
вызова `k1` с параметром 3), но структурно та же форма риска, что и коллизия `0x16` у LeaperKim —
**два разных смысла на одном опкоде, различаемых только дальним байтом, и раздельного контроля за
диапазоном первого параметра в коде не видно**. Стоит считать `0x1B` небезопасным для сборки
«с нуля» без проверки всех вызовов `k1` по всему приложению — вне периметра этой части.

### 3.2 `0x8A`(138) — не коллизия, а осознанная общая точка записи «страница настроек»

`SpeedSettingActivity` (страница 13 — порог мощности) и `AuxiliaryAccelerationActivity` (страница
16 — запрос, страница 17 — запись) используют один и тот же тип `[16]=0x8A`, различаясь байтом
`[2]` (номер страницы) — это **дизайн, не коллизия**: байт-селектор явно присутствует и не
пересекается в двух известных мне вызовах (13 ≠ 16 ≠ 17). Отмечаю здесь только потому, что форма
(общий тип + байт-селектор в постоянной позиции `[2]`) — это тот самый механизм, которым, видимо,
устроена значительная часть каталога `fw.java`: **не отдельная команда на каждый тип `[16]`, а
семейство «читать/писать страницу N» на нескольких общих типах** (`0x87` с `[2]=101` — тоже похоже
на это, см. §1). Сколько всего страниц и что каждая значит — не выведено, кроме трёх найденных
(13, 16, 17).

### 3.3 `0x87`(135) — тип делят пример из §2 (запись режима педалей) и запрос настроек

`fw.H0(int)` (запись режима педалей, `[2]`=значение, `[3]`=0xE0) и **три места**, зовущие
byte-идентичный запрос-триггер с `[2]=101` константой без `[3]` (`SpeedSettingActivity.B0()`,
`WeakMagneticSpeedActivity.p0()`, и, вероятно, ещё где-то за пределами шести названных экранов).
Различаются байтом `[3]` (0xE0 у записи, `0`/не задан у запроса) — **разводится чисто по значению
байта 3, не структурная коллизия**, но тот же тип `[16]`, что стоит знать, если когда-нибудь
понадобится опознавать исходящую команду KingSong по одному байту 16 (тем же уроком, что и
`veteran-commands-import-plan.md` §3: **опкод/тип сам по себе не идентификатор команды**).

## 4. Опасное — перечислить и исключить, не предлагать

- **Запись PIN/пароля колеса (`0x44`, §1, `PasswordActivity.java:180-217`).** По образцу LeaperKim
  (`veteran-commands-import-plan.md` §8: «пароль… установка PIN без найденного пути программного
  восстановления… забытый пароль потенциально блокирует владельца от собственного колеса») — того
  же рода риск: не нашёл в прочитанных файлах пути программного сброса пароля колеса. **Не включать
  в каталог для реализации.**
- **Запись скоростных порогов/лимита с паролем (`0x85`, §1, `SpeedSettingActivity.D0()`).** Само по
  себе обратимо (можно записать другое значение), но: (а) уже осознанно исключено решением владельца
  (класс-комментарий декодера, см. §2); (б) на части моделей запись вообще заблокирована паролем
  лимита скорости (`limitPsd`, тот же экран) — если когда-то решат портировать, обязательно нести
  пароль как часть команды, а не как отдельную настройку, иначе запись будет тихо игнорироваться
  колесом (или, хуже, приниматься на моделях без пароля и путаться с моделями, где он есть).
- **Исключения по модели на этом же экране** (`SpeedSettingActivity.java:657,687,704,726`):
  `KS-N8`, `KS-N10`, `KS-N1-B`, `KS-X1` — официальное приложение **не проверяет** плавность
  диапазонов (`A0()`) и **не отправляет** команду порога мощности (`E0()`) вовсе для этих моделей.
  Если раскладка §1 когда-нибудь будет портирована, для этих четырёх моделей отправка данных команд
  должна быть заблокирована так же, как в оригинале — не «предположительно сработает», а прямое
  указание источника, что для них эта форма команды не подразумевается.
- **Вход в режим прошивки и передача образа** — не встречал в шести названных экранах (там их и не
  может быть, `FirmwareUpdateActivity` — отдельный экран), но `fw.A2(String)` (кодирование пароля
  цифрами) вызывается именно оттуда
  (`FirmwareUpdateActivity.java:3288`) — **не разбирал**, прошивка не эта часть задания, упомянуто
  только чтобы не спутать с паролем колеса из `PasswordActivity` (§1) — это два разных экрана, два
  разных пароля, `fw.A2` и запись `0x44` не одно и то же.

## 5. Развилки по модели/поколению — где видно условие

- **`SpeedSettingActivity`** — модели `KS-N8`/`KS-N10`/`KS-N1-B`/`KS-X1` исключены из
  клампов/отправки команды мощности (см. §4) — приведено дословно, четыре строковых литерала,
  `contains()` по названию модели, не таблица версий;
- **`0x1B` (§3.1)** — `RideModeActivityNew` шлёт `k1((byte)2)` при одних условиях и `O2(ID)` при
  выборе из пользовательского списка пресетов — это не различие по модели колеса, а по **типу
  действия пользователя** (переключить встроенный пресет против выбрать сохранённый пользователем) —
  не путать со генерационной разницей, это разные функции на одном типе кадра;
- **Прочих `if (модель == …)` вокруг команд шести названных экранов не нашёл** — большинство
  команд (педали, вспомогательное ускорение, порог мощности) шлются безусловно, разница по
  моделям, если она есть на уровне прошивки колеса (принимает/игнорирует определённые страницы),
  в этих файлах не видна — там, где она есть, колесо, видимо, решает сама, не приложение.

## 6. Что осталось непокрытым — честно, не по умолчанию

`fw.java` — около **сотни** билдеров кадров (полный список типов `[16]`, встреченных в файле,
занял бы отдельную таблицу на полторы сотни строк; не привожу её целиком, чтобы не создавать
видимость систематизации там, где смысл не установлен). Прочитанного в этой части хватило на
уверенное назначение **пятнадцати** команд (§1) — все остальные:

- либо вызываются только из `FirmwareUpdateActivity`/`FirmwareUpdateActivity2` (прошивка, не эта
  часть — не проверял, сколько именно);
- либо вызываются из экранов и фрагментов **вне** шести названных (`RgbSetActivity`,
  `RgbLightSelectColorFragment`, множество экранов социальной части приложения, найденных ранее
  через `bean/`) — не искал по всему дереву специально, это была бы отдельная, гораздо более
  крупная работа;
- либо не нашёл вызова вовсе в пределах доступного мне поиска.

**Не домысливаю их назначение по именам методов** (капкан 1 задания) — там, где имя метода похоже
на что-то («`J2`», «`K`», билдеры с параметром `i==1?...:...`, замеченные в BMS-контексте по
типам 116/117 ещё в первой части) это совпадение с уже установленными смыслами первой части
(BMS-страницы пакетов 1/2), а не новая находка этой части.

## 7. Режим глубокой диагностики (UART/factory/engineer) — искал, не нашёл

Владелец назвал прецедент LeaperKim: команда переключает колесо в режим, где по проводу вместо
обычной телеметрии идёт **сырой** вывод отладочного UART (токи фаз, IMU, АЦП, температуры, ячейки,
частоты циклов управления, журнал флеша), два режима — 2 Гц и 500 Гц, выход из быстрого — только
перезагрузкой колеса. Искал у KingSong аналог теми же пятью признаками, что задал владелец. **Не
нашёл ни по одному.**

**Что проверено и не дало результата:**

1. **Переключатель режима потока (не запрос данных).** Просмотрен `fw.java` целиком ещё в §1 —
   абсолютно все ~160 билдеров кадров дают массив **ровно 16, 20 или 0 байт**
   (`grep -o 'new byte\[\d+\]' fw.java` — три размера на весь файл, без исключений). Ни одного
   кадра переменной длины, ни одного, который выглядел бы как «включить поток» в отличие от
   «запросить страницу N» (см. §1, §3.2 — вся семья команд построена по одному и тому же
   16/20-байтному конверту, включая уже найденные команды записи настроек);
2. **Поток сырого текста вместо кадров.** Единственный известный случай, когда колесо KingSong
   вообще отдаёт что-то, кроме `AA 55…5A 5A`-кадра, — уже задокументированное поведение живого
   KS-16S (`KingsongDecoder.cs:34-35`: девять байт `AT+ULKTE` каждые 2,4 с). Проверил: **ни одной
   строки `"AT+"` нигде в `com.kingsong.dlc` или `defpackage.fw`** (`grep` по всему дереву обоих
   пакетов) — приложение не строит и не ожидает AT-команд, это чистое поведение прошивки на
   некорректно опрошенном колесе, не то, что приложение умеет вызывать сознательно;
3. **Слова-маркеры в именах/строках/ресурсах.** Проверил `debug`/`factory`/`engineer`/`test`/
   `log`/`raw`/`uart`/`verbose` (англ.) и `调试`/`工程`/`出厂`/`服务模式`/`波形`/`示波`/`频率`/
   `采样`/`自检` (кит., по смыслу «отладка/инженерный/заводской/сервисный/осциллограф/частота/
   выборка/самопроверка») по всему `com.kingsong.dlc` (Java) и по `resources/res/values/strings.xml`
   (единственному найденному файлу строковых ресурсов в этом декомпиляте) — совпадения либо не
   найдены вовсе, либо оказались однозначными ложными следами (`JPushInterface.setDebugMode` —
   чужой SDK пуш-уведомлений, `ServiceProblemAty`/`ServiceQaAty`/… — раздел «служба поддержки»
   социальной части приложения, не колесо);
4. **Скрытый вход.** Проверены обработчики долгого нажатия на главном экране
   (`CarManagerOneFrgm.java` — все найденные `onLongClick`/`onItemLongClick` относятся к разделу
   «Moving»/ленте активности, не к панели телеметрии) и общий поиск по «длинное нажатие»/«скрытый»/
   «секретный»/«внутренний» (кит. `长按`/`隐藏`/`秘密`/`研发`) — все 22 найденных файла с
   `onLongClick` целиком относятся к социальной ленте (лайк/меню поста), ни один — к экрану колеса;
5. **Необычно высокая частота.** Самое частое из найденного — heartbeat `0x5E` раз в 2,5 с
   (уже описан в первой части) и повторы `BmsService` раз в 500 мс с ограниченным числом попыток
   (тоже первая часть) — оба на два-три порядка медленнее заявленных 500 Гц LeaperKim, и оба —
   обычные keep-alive/ретраи, не переключение состояния протокола.

**Второй GATT-канал (`ad00/ad01/ad02`, разобран отдельно в
[`kingsong-telemetry-comparison.md`](kingsong-telemetry-comparison.md) §1.2.1) — тоже не он.** Это
не диагностика, а отдельный, всегда 7-байтный (`CC…FE`) протокол для конкретно двух устройств
линейки `KS-E1/E3`, с ровно двумя найденными командами (свет, блокировка) — не поток данных,
не переключение режима основного колеса.

**Вывод.** Искал по всем пяти признакам, которые дал владелец, в пределах доступных мне файлов
(`fw.java` целиком, `com.kingsong.dlc` — Java-исходники и `resources/res/values/strings.xml`).
**Ни разу не нашёл переключателя режима, при котором характер потока с колеса меняется** — ни
командного, ни строкового признака, ни скрытого входа в UI. Это не значит, что такого режима не
существует физически на плате (UART для заводской настройки почти наверняка есть — иначе колесо
невозможно откалибровать на конвейере), значит только, что **это приложение** (клиентское,
`com.kingsong.dlc` версии 4.9.82) его не открывает ни одним найденным мной путём. Если такой режим
есть, вход в него — не через это приложение, а либо через отдельный, не входящий в этот
декомпилят инструмент производителя, либо физически (сервисный разъём/джампер на плате), что
целиком вне досягаемости разбора APK.

## Спорное / решения по ходу разбора

1. **Глубина проверки коллизии `0x1B` (§3.1)** — не искал все вызовы `fw.k1` по всему дереву
   (вне шести названных экранов), только два в `RideModeActivityNew`. Возможно, `k1` вызывается
   и с другими значениями где-то ещё, что подтвердило бы или сняло подозрение на коллизию с `O2`.
   Решил не расширять поиск за пределы заданных экранов — задание просило именно их как источник
   смысла, а не исчерпывающий обход всего приложения;
2. **Байт `[17]=0x15` у `BuildUpdatePedalsMode` (§2)** — фиксирую как расхождение, не как баг:
   не проверял на живом колесе, важен ли этот байт вообще (во всех виденных мной кадрах он всегда
   `0x14`, кроме этого единственного места в нашем порте — не в `fw.java`, значит расхождение
   пришло из `KingsongAdapter.java`/WheelLog, не из этой сессии её порта);
3. **Полнота каталога (§6)** — сознательно не пытался закрыть все ~100 методов `fw.java`
   догадками по именам; решил, что пятнадцать проверенных по месту вызова команд полезнее длинной
   таблицы с байтами без назначения. Если нужен полный список типов `[16]` без назначений —
   это отдельный, чисто механический проход, могу сделать по отдельному запросу.
