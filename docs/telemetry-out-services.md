# Телеметрия наружу: внешние ресурсы и треки поездок

Снимок анализа оригинала (`C:\Work\repos\Wheellog.Android`) на 28.07.2026. Здесь — что WheelLog
отдаёт **в сеть и в другие приложения телефона**: треки поездок, их формат, API сервиса и способы
поделиться. Парная записка про часы и браслеты — [telemetry-out-devices.md](telemetry-out-devices.md).
План адаптации — [android-plan-10-telemetry-out.md](android-plan-10-telemetry-out.md).

---

## 0. Главное в одном абзаце

Сетевой сервис у WheelLog **ровно один — electro.club**. Ни своего бэкенда, ни Strava, ни EUC
World, ни GPX/TCX-экспорта в коде нет: единственный формат трека — **тот самый CSV, который пишет
`LoggingService`**, и он же уходит на сервер как есть, файлом. Из этого следует главное для нас:
**формат журнала и есть сетевой контракт**, а «загрузка трека» — это `multipart/form-data` с этим
файлом. Всё остальное (список поездок, картинка трека, гараж) — метаданные, которые сервер
возвращает и приложение складывает в свою локальную таблицу.

## 1. CSV поездки — формат, который является контрактом

Пишет `LoggingService.kt`, разбирает `data/TripParser.kt`, имена колонок — `utils/LogHeaderEnum.kt`.

### 1.1. Заголовок

Без GPS:

```
date,time,speed,voltage,phase_current,current,power,torque,pwm,battery_level,distance,totaldistance,system_temp,temp2,tilt,roll,mode,alert
```

С GPS — шесть колонок вставляются **после `time`**:

```
date,time,latitude,longitude,gps_speed,gps_alt,gps_heading,gps_distance,speed,...
```

### 1.2. Строка

`LoggingService.kt:285-307`, формат `Locale.US`:

| Колонка | Формат | Источник |
|---|---|---|
| `date` | `yyyy-MM-dd` | `WheelData.timeStamp` |
| `time` | `HH:mm:ss.SSS` | там же |
| `latitude`, `longitude` | `toString()` двойного, **пусто если фикса ещё нет** | `Location` |
| `gps_speed` | м/с × 3.6 | `location.speed` |
| `gps_alt`, `gps_heading` | `toString()` | `Location` |
| `gps_distance` | `%.0f`, накопительная сумма `distanceTo` | считается на телефоне |
| `speed` … `pwm` | `%.2f` | км/ч, В, А, А, Вт, Н·м, % |
| `battery_level`, `distance`, `totaldistance`, `system_temp`, `temp2` | `%d` | %, м, м, °C, °C |
| `tilt`, `roll` | `%.2f` | градусы |
| `mode`, `alert` | `%s` | свободный текст |

Перевод строки — **CRLF** (`FileUtil.writeLine`).

### 1.3. Нюансы, которые ломают наивного читателя

- **GPS-блок опционален.** Читатель обязан разбирать заголовок, а не считать колонки по позиции.
  `TripParser` именно так и делает — строит `HashMap<LogHeaderEnum, Int>` по заголовку.
- **`TripParser` отказывается открывать файл без `latitude`/`longitude`** — экран карты и статистики
  у оригинала недоступен для журналов без GPS. То есть **своя же программа читает свой же файл не
  целиком**: часть функций доступна только с включённым логированием координат.
- **Первые строки содержат `totaldistance = 0`** — одометр ещё не пришёл от колеса. Все читатели
  обязаны это обходить (`firstTotalDistance` берётся с первого ненулевого).
- **Конец пробега берётся как максимум по последним десяти строкам**, а не по последней: одно
  битое значение в хвосте иначе задаёт весь пробег.
- **Простои вычитаются при чтении, а не при записи.** Промежуток между отсчётами больше секунды
  считается стоянкой и не входит в длительность, по которой считается расход. Запись при этом идёт
  всегда, пока есть соединение, — стоянку и зарядку включительно.
- **`mode` пустой после `reset()`** и `"Unknown"`, если сброса не было. Пустая строка в середине
  CSV — это то, к чему чужие парсеры не готовы, но так есть.

### 1.4. Файл на диске

- Имя: `yyyy_MM_dd_HH_mm_ss.csv` (`SimpleDateFormat`, `Locale.US`).
- Папка: `Download/WheelLog/<mac с ':' → '_'>/` (`Constants.LOG_FOLDER_NAME`, старое имя
  `WheelLog Logs` поддерживается для миграции).
- **Дозапись в вчерашний файл**: `continueThisDayLog` — если последний журнал того же MAC, он
  открывается на дозапись, а прошлые значения `WheelData` восстанавливаются
  `ParserLogToWheelData`, чтобы пробег не начался с нуля. Исключение по MAC —
  `continueThisDayLogMacException`.
- Старт записи: `autoLog` (по умолчанию **выключен**) + `startAutoLoggingWhenIsMovingMore`
  (по умолчанию 7 км/ч; ноль = писать с момента подключения).

## 2. electro.club — единственный сетевой сервис

Файл: `ElectroClub.kt`. Клиент — OkHttp, таймауты 60 с на соединение и на чтение.

### 2.1. Общее

- **База**: `https://electro.club/api/v1`
- **Метод передаётся параметром `method`**, а не путём. Один URL, три метода.
- **Две токен-сущности**:
  - `access_token` — ключ **приложения**, вшит в сборку через `BuildConfig.ec_accessToken`
    (подставляется gradle из локального свойства, в репозитории его нет);
  - `user_token` — токен **пользователя**, получается логином и хранится в настройках.
- **Ошибки**: тело ответа — JSON, текст ошибки в `data.error`. Коды 500–599 обрабатываются
  отдельно, без разбора тела (`"500 exception"`). Ошибки разбора JSON тоже попадают в `lastError`.
- Результаты уходят в два колбэка-слушателя (`errorListener`, `successListener`) с именем метода
  первым аргументом — так UI показывает, что именно не удалось.

### 2.2. `login`

```
GET /api/v1?method=login&access_token=<app>&email=<email>&password=<plain>
```

Ответ: `data.user.{user_token, user_id, nickname}`.

**Пароль уходит в query-строке открытым текстом.** HTTPS его закрывает от сети, но он попадает в
любые логи прокси и в историю URL-объектов. Токен и `user_id` складываются в `SharedPreferences`
в открытом виде.

### 2.3. `uploadTrack`

```
POST /api/v1
Content-Type: multipart/form-data
```

| Часть | Значение |
|---|---|
| `method` | `uploadTrack` |
| `access_token` | ключ приложения |
| `user_token` | токен пользователя |
| `file` | **содержимое CSV**, имя части = имя файла, MIME `text/csv` |
| `time_zone` | смещение вида `+03:00` — берётся `SimpleDateFormat("Z")` и в него **вручную вставляется двоеточие** перед двумя последними цифрами |
| `garage_id` | опционально, если выбран и не `"0"` |
| `verified` | `"1"`, если загрузка автоматическая по окончании записи |

Ответ: `data.track.{id, start_time, garage_id, image, duration}`.

Ограничения и поведение:

- **Лимит 50 000 000 байт** проверяется на клиенте до отправки.
- Перед отправкой в локальную таблицу вставляется пустая запись поездки с этим именем файла —
  чтобы связь «файл ↔ трек на сервере» существовала даже если загрузка не дойдёт.
- После успеха в ту же запись дописываются `ecId`, `ecStartTime`, `ecTransportId`, `ecUrlImage`,
  `ecDuration`.
- **Автозагрузка происходит в `LoggingService.onDestroy()`** — то есть в момент остановки записи,
  и сервис не завершается, пока загрузка не отдаст результат. Включается `autoUploadEc`
  (по умолчанию выключено).

### 2.4. `getUserGarage`

```
GET /api/v1?method=getUserGarage&access_token=<app>&user_token=<user>&user_id=<id>
```

Ответ: `data.transport_list[]`, элементы `{ id, name, MAC }`.

Смысл: у пользователя на сервисе может быть несколько аппаратов («гараж»), и трек надо привязать
к нужному. Приложение **сопоставляет по MAC подключённого колеса**; если совпадения нет — показывает
диалог выбора. Отказ от выбора записывает `"0"` — «этому колесу гараж не нужен», и диалог больше не
всплывает.

### 2.5. Ссылка на трек

`getUrlFromTrackId` возвращает `https:/electro.club/track/$trackId` — **с одной косой чертой**.
Дефект; ссылка нерабочая.

## 3. Локальная таблица поездок

`data/TripDataDbEntry.kt` (Room, таблица `trip_database`, уникальный индекс по `fileName`).

| Группа | Поля |
|---|---|
| Идентификация | `id`, `fileName` (ключ связи со всем остальным), `mac`, `profileName` |
| Время | `start`, `duration` (минуты) |
| electro.club | `ecId`, `ecStartTime`, `ecDuration`, `ecUrl`, `ecUrlImage`, `ecTransportId` |
| Итоги | `maxSpeed`, `maxSpeedGps`, `avgSpeed`, `maxPwm`, `maxCurrent`, `maxPower`, `distance`, `consumptionTotal`, `consumptionByKm` |
| Запас | `additionalJson` |

Нюансы:

- **Ключ — имя файла, а не идентификатор поездки.** Сущности «поездка» в оригинале нет; есть файл,
  и таблица — его карточка. Переименование или удаление файла рвёт связь.
- **Итоги считаются заново при каждом открытии файла** (`TripParser` пересчитывает и обновляет
  запись). Это и есть причина медленного списка поездок.
- `avgSpeed` в таблице считается **по всем отсчётам, включая нулевые**, а «средняя скорость» в
  живых показаниях — только по секундам со скоростью выше 2 км/ч (`RIDING_SPEED = 200`). Две разные
  средние, и это осознанно.
- `profileName` — свободная строка пользователя, уезжает вместе с записью, но **не уезжает на
  сервер**: в `uploadTrack` его нет.

## 4. Поделиться файлом

`views/TripAdapter.kt:123-130` — стандартный `Intent.ACTION_SEND` с `createChooser`, URI выдаёт
`FileProvider` (`${applicationId}.fileprovider`, пути в `res/xml/file_paths.xml`).

Это второй и последний способ отдать поездку наружу: файл целиком, чужому приложению, руками
пользователя. Никакой конвертации — тот же CSV.

## 5. Чего нет

Перечислено намеренно — при планировании легко ожидать обратного:

- **Нет GPX, TCX, FIT, KML.** Ни экспорта, ни импорта.
- **Нет Strava, Garmin Connect (как сервиса), Komoot, EUC World, wheellog.net.**
- **Нет своего бэкенда и синхронизации между устройствами.**
- **Нет выгрузки телеметрии в реальном времени в сеть** — ни MQTT, ни WebSocket, ни вебхуков.
  Всё сетевое происходит **после** поездки, одним файлом.
- **Нет очереди отложенной загрузки.** Если сети нет в момент остановки записи — трек просто не
  уйдёт, и повторить можно только вручную из списка поездок.
- **Нет обезличивания.** В CSV уходят точные координаты, включая точку старта, то есть обычно дом.

## 6. Что здесь контракт

- **Заголовок CSV, порядок колонок и точность каждой.** На них завязаны сторонние сервисы —
  ровно поэтому в нашем `RideLog` формат скопирован посимвольно.
- **Имя файла `yyyy_MM_dd_HH_mm_ss.csv`** — по нему сервер и локальная таблица склеивают поездку.
- **Метод, набор частей и имена полей electro.club.** Внешний API, менять не нам.
- `time_zone` в виде `+03:00` — сервер восстанавливает по нему локальное время поездки, потому что
  в CSV время локальное, а зоны в нём нет.
