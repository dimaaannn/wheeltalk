# UI оригинального WheelLog — справочник

Разбор интерфейса Android-приложения WheelLog (`C:\Work\repos\Wheellog.Android`) как исходника
для проектирования нашего UI. Ссылки вида `файл:строка` — на пути внутри того репозитория,
относительно `app/src/main/java/com/cooper/wheellog/` (для разметок — `app/src/main/res/layout/`).

Составлен по [Плану 2](android-plan-2-ui-analysis.md). Код не портировался — только описание.

---

## 0. Какой UI живой: XML, не Compose

В проекте сосуществуют два слоя, и переключает их **настройка, выключенная по умолчанию**:

```kotlin
// MainActivity.kt:661
if (appConfig.useComposeUI) { setContent { AppTheme { MainScreen() } } }
else { setContentView(binding.root) }         // <- сюда попадает обычный запуск
```

`AppConfig.kt:57` — `var useComposeUI: Boolean = false`, причём это простое поле, а не настройка
в SharedPreferences: включить её из интерфейса нельзя, только правкой кода. Значит **живой слой —
классические Android Views** (`activity_main.xml` + кастомный `WheelView`), а `compose/*Screen.kt` —
незавершённый параллельный вариант. Описываю дальше XML-слой.

Единственное исключение: **экран настроек всегда на Compose** — он вставлен в разметку как
`ComposeView` (`activity_main.xml:20`, наполняется в `MainActivity.kt:729`). То же и с PiP-видом
(`pip_view`).

## 2. Приборка (`WheelView`)

Самодельный `View` на 1220 строк, рисует всё на канве. Два варианта отрисовки — «оригинальный»
(`drawOriginal`, `WheelView.kt:692`) и AJDM-тема (`drawAJDM`, `WheelView.kt:826`); различаются компоновкой дуг,
логика значений общая.

### 2.1. Что нарисовано

| Элемент | Что показывает | Как считается | Где |
|---|---|---|---|
| Внешняя дуга (144°…396°, 112 делений) | Скорость, а при `swapSpeedPwm` — ШИМ | `targetSpeed = |speed| / maxSpeed * 112` | `WheelView.kt:342, 718` |
| Цвет внешней дуги | Уровень ШИМ | градиент по порогам, см. §2.2 | `WheelView.kt:674, 720` |
| Внутренняя дуга, левый сектор (144°, 90°) | Заряд, 40 делений | `targetBattery = 40 * battery / 100` | `WheelView.kt:349, 741` |
| Внутренняя дуга, правый сектор (306°, 90°) | Температура, 40 делений, шкала 0…80 °C | `targetTemperature = 112 − 40 * clamp(t,0,80)/80` | `WheelView.kt:363, 742` |
| Отдельная отметка на дуге заряда | Минимальный заряд за поездку | `targetBatteryLowest` | `WheelView.kt:350, 745` |
| Средняя дуга (AJDM) | Максимальная и средняя скорость | — | `WheelView.kt:883` |
| Крупный текст в центре | Скорость (или ШИМ при `swapSpeedPwm`) | — | `WheelView.kt:764` |
| Строка под ним | ШИМ или скорость — то, чего нет в центре | — | `WheelView.kt:772` |
| Текст по дуге | Модель колеса | — | `modelTextPath` |
| Мелкий текст | Версия приложения и дата сборки | — | `WheelView.kt:76` |
| Прямоугольные «плитки» | Настраиваемый набор значений, см. §2.3 | — | `mViewBlocks` |

### 2.2. Цвет по ШИМ — то, что стоит перенять

`WheelView.getPwmColor` (`WheelView.kt:674`):

- ниже `colorPwmStart` — полупрозрачный белый `0xAAFFFFFF`;
- выше `colorPwmEnd` — насыщенный красный `0xFFFF0000`;
- между ними — **линейная интерполяция** от бледно-жёлтого `0xAAFFFFAA` к красному.

Дефолты (`AppConfig.kt:325`): `colorPwmStart = 78`, `colorPwmEnd = 92`. То есть визуальная тревога
начинается заметно раньше звуковой (80 %) и достигает максимума раньше порога срыва (95 %).

### 2.3. Плитки значений — настраиваемый набор

Плитки описываются `ViewBlockInfo` (`views/ViewBlockInfo.kt`): заголовок, лямбда-значение, флаг
`enabled` и `index` для порядка. Полный список — `WheelView.kt:121…290`, около тридцати штук:

ШИМ · макс. ШИМ · напряжение · средняя скорость в движении · время в поездке · скорость ·
макс. скорость · дистанция · одометр · заряд · ток · фазный ток · макс. ток · макс. фазный ток ·
мощность · температура · температура 2 · макс. температура · средняя скорость · пробег GPS ·
скорость GPS · время · остаток заряда · и т. д.

Пользователь включает нужные и задаёт порядок в настройках. Значения форматируются на месте
(`"%.2f%%"`, `"%.1f А"` и т. п.), единицы переключаются км/ч ↔ mph.

## 3. Подключение к колесу

### 3.1. Экран поиска (`ScanActivity.kt`, 256 строк)

Отдельная активность, открывается из меню (`R.id.miSearch`). Список — `binding.list` с
`DeviceListAdapter`; строка (`scan_list_item.xml`) состоит ровно из двух полей: `device_name` и
`device_address`. Тап возвращает адрес в `MainActivity` через `setResult(RESULT_OK, intent)`.

Особенности:

- скан **автоматически останавливается по таймауту** `scanPeriod` (`ScanActivity.kt:224`);
- перед сканом проверяются разрешения и **включена ли геолокация** (`isLocationEnabled`,
  `ScanActivity.kt:242`) — та же ловушка Android ≤ 11, что и у нас;
- из рекламного пакета вытаскиваются **manufacturer data** (`findManufacturerData`,
  `ScanActivity.kt:197`) — по ним отличают семейства колёс ещё до подключения.

### 3.2. Автоподключение и состояние

`MainActivity` хранит `appConfig.lastMac` (`MainActivity.kt:690`) и при старте поднимает
`BluetoothService`. Проверка «поддерживается ли BLE» и «включён ли Bluetooth» — там же, с
системным запросом на включение через `enableBleLauncher`. Состояние соединения приходит
broadcast-ами (`mCoreBroadcastReceiver`), отображается в тулбаре и в уведомлении.

Отдельно: при старте вызывается `checkBatteryOptimizationsAndShowAlert` (`MainActivity.kt:737`) —
приложение само просит исключить себя из оптимизации батареи. Ровно то, что нам понадобится
в [Плане 4](android-plan-4-alerts-and-background.md).

## 6. Тревоги — самое ценное для плана 4

`utils/Alarms.kt` (343 строки). Два режима, переключаются `appConfig.pwmBasedAlarms`.

### 6.1. Режим по ШИМ (актуальный)

`alertedAlarms` (`Alarms.kt:116`):

- порог включения — `alarmFactor1`, **дефолт 80 %**;
- «сила» тревоги считается линейно между факторами:
  `200 * (pwm − factor1) / (factor2 − factor1)`, где `alarmFactor2` — **дефолт 90 %**;
  результат управляет интенсивностью сигнала;
- `alarmFactor3` — **дефолт 95 %**, крайний порог;
- отдельно есть «предупреждение» с периодом повтора: если `pwm ≥ warningPwm` и с прошлого раза
  прошло больше `warningSpeedPeriod` мс — играется `R.raw.warning_pwm`. По умолчанию оба нули,
  то есть выключено;
- аналогичное предупреждение по скорости (`warningSpeed`, звук `sound_warning_speed`).

### 6.2. Прочие тревоги

Скорость (три уровня, каждый со своим порогом заряда), ток и фазный ток, температура и температура
мотора, заряд, и тревога, о которой сообщило само колесо (`wheelAlarms`). Все — с порогами из
настроек, ноль означает «выключено».

### 6.3. Антидребезг

Вместо гистерезиса — «залипающие» флаги `TempBoolean` с временем сброса (`Alarms.kt:29`):

| Тревога | Удержание |
|---|---|
| Скорость / ШИМ | 170 мс |
| Температура | 570 мс |
| Заряд | 970 мс |

Пока флаг взведён, повторная тревога того же типа не поднимается. Разные времена разведены
специально, чтобы сигналы не сливались.

### 6.4. Как звучит и трясётся

`raiseAlarm` (`Alarms.kt:255`) шлёт broadcast `ACTION_ALARM_TRIGGERED` и параллельно:

| Тип | Вибрация (мс) |
|---|---|
| Скорость 1/2/3, ШИМ | `0, 100, 100` |
| Ток | `0, 50, 50, 50, 50` |
| Температура | `0, 500, 500` |
| Заряд | `0, 100, 500` |
| Тревога колеса | `0, 50, 50` |

Звук и вибрация отключаются раздельно (`disablePhoneBeep`, `disablePhoneVibrate`). Звуки — готовые
файлы в ресурсах (`R.raw.warning_pwm`, `R.raw.sound_warning_speed`, `R.raw.lowbat`), не синтез.

## 7. Формат файла логов — соблюдать точно

Пишет `LoggingService.kt`. На этот формат завязаны сторонние сервисы, поэтому колонки, порядок и
точность менять нельзя.

- **Имя файла**: `yyyy_MM_dd_HH_mm_ss.csv` (`LoggingService.kt:122`), локаль `US`; каталог
  привязан к MAC колеса.
- **Заголовок** (`LoggingService.kt:169`), запятая-разделитель, без пробелов:

```
date,time,latitude,longitude,gps_speed,gps_alt,gps_heading,gps_distance,speed,voltage,phase_current,current,power,torque,pwm,battery_level,distance,totaldistance,system_temp,temp2,tilt,roll,mode,alert
```

Блок `latitude…gps_distance` присутствует, **только если включена запись геоданных** — иначе
шесть колонок просто отсутствуют и в заголовке, и в строках.

- **Строка** (`LoggingService.kt:285`), формат `Locale.US` (точка как десятичный разделитель):

| Колонка | Источник | Формат |
|---|---|---|
| date, time | `SimpleDateFormat("yyyy-MM-dd,HH:mm:ss.SSS")` от `WheelData.timeStamp` | две колонки одной строкой |
| latitude, longitude, gps_speed, gps_alt, gps_heading | из `Location`, скорость × 3.6 (км/ч) | `%s` |
| gps_distance | накопленная дистанция по GPS | `%.0f` |
| speed, voltage, phase_current, current, power, torque, pwm | `wd.speedDouble` … `wd.calculatedPwm` | `%.2f` |
| battery_level, distance, totaldistance, system_temp, temp2 | целые | `%d` |
| tilt, roll | `wd.angle`, `wd.roll` | `%.2f` |
| mode, alert | строки | `%s` |

Заголовок перечислен и в `utils/LogHeaderEnum.kt` — там же порядок, которого держится парсер
обратного чтения (`ParserLogToWheelData.kt`).

Чего у нас нет для полной совместимости: `torque`, `roll`, `mode` и весь блок GPS — эти величины
`TelemetrySnapshot` не содержит. **Вопрос совместимости решён кодом:** заголовок зафиксирован в
`WheelTalk.Core/Logging/RideLog.cs:22-24` — без блока GPS, а `torque`/`roll` пишутся `0.00` и
`mode` пустым: ровно то, что сам оригинал пишет для наших колёс (разбор — план 8 §2.2).

| WheelLog | Наш `TelemetrySnapshot` |
|---|---|
| `speedDouble` | `SpeedKmh` |
| `calculatedPwm` | `Pwm` |
| максимум ШИМ | `MaxPwm` |
| `voltageDouble` | `VoltageV` |
| `currentDouble` | `CurrentA` |
| `phaseCurrentDouble` | `PhaseCurrentA` |
| `powerDouble` | `PowerW` |
| `batteryLevel` | `Battery` |
| `temperature` / `temperature2` | `TemperatureC` / `Temperature2C` |
| `topSpeed` | `TopSpeedKmh` |
| `distance` / `totalDistance` | `WheelDistance` / `TotalDistance` |
| `angle` | `Angle` |
| `wheelAlarm`, `alert` | `WheelAlarm`, `Alert` |
| модель, версия прошивки | `Model`, `Version` |
| данные BMS | `Bms1`, `Bms2` |

Оговорка к таблице: с тех пор снимок хранит сырые значения полями `*Raw`
(`VoltageRaw`, `CurrentRaw`…), а `VoltageV`/`CurrentA` и прочие — derived-свойства поверх них
(`Contracts/TelemetrySnapshot.cs`); соответствие по смыслу не изменилось.

**Чего у нас нет** (список усох — большая часть с тех пор появилась): `roll` (крен), `torque`,
`modeStr` и всё, что связано с GPS. Появились и живут в `RideTotals`/`RideTrace`: максимумы тока,
мощности, скорости и температуры за поездку, средняя скорость, время в движении, просадка пака.
Это подтвердило исходную догадку: производные восстановились в нашем ядре без правки декодеров.

## 9. Что стоит перенять, а что нет

**Стоит:**

- **Цветовую шкалу по ШИМ** с интерполяцией между двумя порогами (§2.2) — она сообщает не только
  «тревога/нет», но и насколько близко к пределу; наша тревожная рамка из плана 4 устроена так же.
- **Разнесение звуков по типам тревог** и раздельное отключение звука и вибрации.
- **Разное время удержания** для разных тревог (§6.3) — чтобы сигналы не сливались в кашу.
- **Запрос на исключение из оптимизации батареи при старте** — без него фон на многих прошивках
  не живёт.
- **Скорость и ШИМ как две главные величины**, причём взаимозаменяемые (`swapSpeedPwm`): кто-то
  смотрит на ШИМ, кто-то на скорость.

**Не стоит в первой версии:**

- Самодельная канва на 1200 строк с двумя темами отрисовки — под наши задачи это неоправданная
  сложность.
- Тридцать настраиваемых плиток: набор нужных выясняется в поездках, а не проектированием.
- Пять страниц пейджера, часы в тулбаре, интеграции с часами и браслетами.
- Три уровня тревог по скорости с привязкой к заряду — усложняет настройку без явной пользы.

## 10. Вопросы — все три закрыты практикой

1. **Совместимость файла логов.** ~~Писать колонки пустыми или отказаться от формата?~~ Решено:
   формат соблюдается точно, `torque`/`roll` — `0.00`, `mode` — пусто, GPS-блока нет — как пишет
   сам оригинал для наших колёс (`RideLog.cs`, план 8 §2.2).
2. **Единицы.** ~~WheelLog умеет mph; нам это нужно вообще?~~ Не делалось: в ядре только км/ч
   (derived-свойства с суффиксом `Kmh`), запроса на mph не появилось.
3. **`swapSpeedPwm`.** ~~Обмен местами скорости и ШИМ?~~ Снят панелью: на главном экране скорость —
   цифра в центре, ШИМ — лента у края (план 7, [dashboard-help.md](dashboard-help.md)); меняться
   местами им больше негде.
