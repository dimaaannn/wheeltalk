# Готовые библиотеки для нативного интерфейса: что брать, что не брать

> **Решения владельца 29.07.2026 по итогам этого документа:**
> - **RecyclerView** — брать (список поездок).
> - **Material Components** — брать: системный вид и виджеты варианта B перевешивают цену темы.
>   *(В сборку фактически взят **1.13.0**, а не 1.14.0.5 из обзора ниже —
>   `WheelTalk.Droid.csproj`.)*
> - **MPAndroidChart** — брать своим биндингом `AndroidMavenLibrary`, когда дойдёт до графиков.
> - **Карты — osmdroid, зафиксировано** (офлайн, без ключей, ноль зависимостей); реализация — с
>   GPS-планом. Mapsui отвергнут (второй движок отрисовки).
> - Остальные отказы (Preference, Vico, Google Maps, MapLibre, SkiaSharp/LiveCharts,
>   ConstraintLayout, чужие View для панели) — приняты как записано ниже.

> **Тип документа:** исследование, а не решение. Код не тронут, зависимостей не добавлено.
> Вопрос владельца: .NET для Android умеет биндить Java/Kotlin-библиотеки — есть ли в экосистеме
> готовое, что улучшит и оптимизирует интерфейс, прежде чем всё писать руками.
> **Решение о принятии любой зависимости — за владельцем.** Здесь только честная картина, включая
> вариант «ничего не брать».
>
> **Даты и версии проверены по NuGet, Maven Central, JitPack и GitHub 29.07.2026.** Ничего не
> взято по памяти: у каждого кандидата ниже стоит номер версии и дата публикации.
>
> **Разбор ведётся по нашим экранам** — [опись миграции](archive/native-rewrite-inventory.md) и
> [редизайн настроек](archive/settings-redesign.md) (принят вариант B, без поиска).

## Правила, по которым здесь судят

Три взяты из уже принятых решений проекта, четвёртое следует из них:

1. **Зависимость лечит конкретную боль, а не «на всякий случай»** ([AGENTS.md](../AGENTS.md)).
   Библиотека, которая «пригодится», — это библиотека, которая протухнет.
2. **Внешних сервисов нет** ([план 11 §7](android-plan-11-field-robustness.md#7-рассмотрено-и-сознательно-не-делается)).
   Правило написано про Sentry/Firebase/Crashlytics, но его дух — «ни аккаунтов, ни ключей, ни
   чужих серверов» — прямо касается карт: вариант без регистрации предпочтительнее.
3. **Считаем как WheelLog** — это про **формулы и значения**, не про библиотеки. Выбор оригинала
   ниже используется как источник требований (что именно рисуется, какие взаимодействия нужны),
   а не как ограничение: рекомендация может разойтись с оригиналом, если она лучше по нашим
   критериям.
4. **Собирает один человек.** Значит цена зависимости — не только килобайты, но и «кто починит
   биндинг, когда он сломается». Отсюда главный критерий по каждому пакету — **кто его
   поддерживает и когда он последний раз обновлялся**.

## Как вообще устроен биндинг в .NET 9/10 для Android — и почему это меняет ответ

Это важно прочитать до всех разделов ниже, потому что здравый смысл «нет NuGet-пакета — значит
нельзя» с .NET 9 больше не верен.

Раньше биндинг чужой Java-библиотеки означал «найти чужой NuGet-пакет или руками собирать
проект вокруг скачанного `.aar`». Начиная с **.NET 9** есть `AndroidMavenLibrary`: артефакт
скачивается из Maven-репозитория и биндится самой сборкой
([docs](https://learn.microsoft.com/en-us/dotnet/android/binding-libs/binding-java-libs/binding-java-maven-library)):

```xml
<!-- проект, созданный через: dotnet new android-bindinglib -->
<ItemGroup>
  <AndroidMavenLibrary Include="org.osmdroid:osmdroid-android" Version="6.1.20" />
</ItemGroup>
```

Существенные детали:

- `Repository` принимает `Central` (по умолчанию), `Google` или **любой https-адрес Maven-репозитория**
  — то есть `https://jitpack.io` тоже (там лежит MPAndroidChart).
- **Java Dependency Verification** (.NET 9+) проверяет зависимости по `.pom` и выдаёт внятные
  ошибки: `XA4241: Java dependency '…' is not satisfied` и `XA4242: … Microsoft maintains the NuGet
  package 'Xamarin.Kotlin.StdLib' that could fulfill this dependency`. То есть «чего не хватает»
  говорит сборка, а не эксперимент на устройстве.
- Формально между приложением и биндингом в .NET для Android разницы нет (`.aar` можно положить
  прямо в проект приложения), но документация настоятельно рекомендует отдельный проект — и это
  правильно: биндинг пересобирается редко, а приложение постоянно.

**Практический вывод, который переворачивает половину этого документа:** мёртвый комьюнити-NuGet
больше не приговор. Для Java-библиотеки **без зависимостей** (а обе главные кандидатуры ниже —
ровно такие) свой биндинг стоит пять строк в `csproj`, и владелец этих строк — мы, а не незнакомый
человек, который забросил репозиторий в 2020 году.

## 1. Настройки — AndroidX Preference против списка своими руками

### Что предлагается

`Xamarin.AndroidX.Preference` — официальный биндинг `androidx.preference:preference`, то, чем
построены системные «Настройки» Android. `PreferenceFragmentCompat` + дерево `Preference`,
`PreferenceCategory`, `SwitchPreferenceCompat`, `ListPreference`, `SeekBarPreference`, и
`PreferenceDataStore` — точка, через которую значения читаются и пишутся не в `SharedPreferences`,
а куда мы скажем.

**Состояние биндинга.** `Xamarin.AndroidX.Preference` **1.2.1.18**, опубликован **27.06.2026**,
TFM `net10.0-android36.0` и `net9.0-android35.0`, владельцы — Microsoft и Xamarin, 8,4 млн загрузок
всего. Обновляется регулярно (1.2.1.15 — 16.08.2025, .16 — 08.01.2026, .17 — 06.03.2026, .18 —
27.06.2026). Риск протухания — практически нулевой.
Зависимости: `Activity.Ktx`, `AppCompat`, `Core`, `Fragment.Ktx`, `RecyclerView`, `SlidingPaneLayout`.

### Как это ложится на нашу модель — по частям, честно

Наша модель: [`LayeredSettings`](../WheelTalk.Core/Settings/LayeredSettings.cs) (заводское →
общее → колесо, плюс `ClearOverride`/`ClearGlobal`/`PromoteToGlobal`),
[`SettingDescriptor`](../WheelTalk.Core/Settings/SettingDescriptor.cs) (**50 описаний**, сверено
08.08.2026; на момент исследования было 45, потом добавился `Wheel:Name` и далее по мелочи; каждое
со своим `Apply`/`Current`, `IsVisible`, `GlobalOnly`, `ReportedByWheel`, у одного —
`AfterEdit`) и вариант B редизайна
(сегментный переключатель слоя, сводки, подпись слоя под значением).

| Часть нашей модели | Ложится на Preference? | Подробно |
|---|---|---|
| Хранилище значений | **Да, хорошо** | `PreferenceDataStore` — ровно та абстракция: `GetString(key, default)` / `PutString(key, value)`. Поверх `LayeredSettings.Get(key).Value` и `Set(key, value, globalOnly)` пишется в двадцать строк |
| Строка «переключатель / число / выбор» | **Да** | `SwitchPreferenceCompat`, `ListPreference`, `EditTextPreference` — прямые аналоги `SettingKind` |
| Подпись под заголовком (наш «80 % · общее») | **Да** | `Preference.SummaryProvider` / `Summary` — механика ровно под это и заведена |
| Каскады «выключено — скрыто» (`IsVisible`) | **Да** | `Preference.Visible = false` |
| Динамический каталог из 45 дескрипторов | **Скорее да, но против шерсти** | `PreferenceManager.CreatePreferenceScreen(context)` позволяет строить дерево кодом. Но весь API, вся документация и все примеры — вокруг XML `preferences.xml`; кодовая ветка малохоженая. Мы же строим строки из описаний, и XML нам противопоказан: он был бы 46-м местом, где живёт правда о настройке |
| **Слой и его смена** (`Scope`) | **Нет прямой поддержки** | `PreferenceDataStore` — плоский `key → value`, идеи «то же значение, но из другого слоя» в нём нет. Смена колеса означает, что **все** строки должны перечитать значение и подпись: у Preference нет «инвалидировать экран», надо либо звать `NotifyChanged()` на каждой строке, либо пересобирать `PreferenceScreen`. Работает, но это наш код поверх чужого, а не их механика |
| **Сегментный переключатель «Общее / это колесо»** (главное в варианте B) | **Нет** | `PreferenceFragmentCompat` — фрагмент со своим `RecyclerView` на весь экран. Закреплённая панель сверху делается своей разметкой, в которую фрагмент вкладывается. Возможно, но это уже наша разметка вокруг чужого списка |
| **Меню слоя на строке** («вернуть общее» / «сделать общим») | **Нет** | Долгое нажатие и своё меню требуют наследника `Preference` с переопределённым `OnBindViewHolder` — то есть ровно того же кода, что и своя строка `RecyclerView`, только внутри чужой иерархии |
| Индикатор переопределения (рамка/подпись) | **Через свой layout строки** | `Preference.SetLayoutResource(...)` + свой `OnBindViewHolder` |
| `ReportedByWheel` (показываем, не храним) | **Через свой Preference** | В модели Preference «строка, которая не пишет» — это `Preference` без ключа; работает, но снова свой класс |

### Цена

- **Тема обязательна.** `PreferenceFragmentCompat` требует `AppCompat`-темы и выставленного
  атрибута `preferenceTheme` — иначе разметка не надувается и приложение падает при открытии
  экрана. Это классическая мина, и она заставляет тянуть тему `AppCompat` на весь проект (что мы
  и так, вероятно, сделаем ради `AppCompatActivity`, но это связывание, а не подарок).
- **Kotlin-рантайм.** Зависимости `Activity.Ktx`/`Fragment.Ktx` тянут `Xamarin.Kotlin.StdLib`.
  Для приложения, где сегодня Kotlin-кода нет ни байта, это первое место, где он появляется.
- **`Fragment`-архитектура.** У нас в описи миграции экраны — `Activity`. Preference втягивает
  фрагменты как минимум на страницу настроек.

### Вердикт

**Не брать — но это решение владельца, и цена отказа тоже названа.**

Причина: из десяти пунктов таблицы Preference закрывает шесть — и все шесть у нас **уже написаны**
и работают (`SettingsListPage.Show()` строит строки из дескрипторов). А четыре, которые он не
закрывает, — это ровно то, что редизайн варианта B добавляет: слой, его переключатель, меню строки
и подпись происхождения. То есть библиотека берёт на себя решённое и не берёт нерешённое.

Что мы теряем отказом (честно): системный вид строк «как в настройках Android» без ручной работы,
готовую механику `summary`, и `SeekBarPreference` для узких шкал. Первое достигается стилем
строки (одна разметка на 45 строк), второе у нас уже есть в виде подписи, третье вариантом B
сознательно не берётся (диалог, план 6 §10).

**Что брать вместо:** `RecyclerView` — то же самое, что Preference использует внутри, минус
дерево, тема, фрагменты и Kotlin. Наш `Show()` превращается в адаптер с 4–5 типами строк
(`SettingKind`), и вся слоёность остаётся там, где она сейчас — в нашем коде.

*Как решилось в порте (30.07.2026): без Preference, как и рекомендовано, но и без адаптера —
настройки собраны `ScrollView` + `LinearLayout`, все строки живые сразу: их десятки, а не сотни,
и переиспользование ничего не окупает. RecyclerView взят только для списков, которые растут, —
поездки и скан.*

## 2. Списки — поездки, скан, телеметрия

Наши списки: поездки (десятки строк, растёт), найденные при скане устройства (единицы),
телеметрия (около тридцати **фиксированных** полей снэпшота + банки BMS).

### RecyclerView

**Пакет:** `Xamarin.AndroidX.RecyclerView` **1.4.0.6**, **27.06.2026**, `net10.0-android36.0` /
`net9.0-android35.0`, Microsoft и Xamarin, 36,1 млн загрузок. Риск нулевой.

**Что даёт:** переиспользование строк (без него длинный список — это N надутых разметок в памяти),
`ItemTouchHelper` (свайп по строке поездки), `ListAdapter`/`DiffUtil`, `LinearLayoutManager`.

**Чем лучше ручного варианта:** ручной вариант — либо `LinearLayout` в `ScrollView` (все строки
живые сразу), либо `android.widget.ListView` с `ArrayAdapter` (переиспользование есть, зависимостей
ноль, но виджет из framework образца 2009 года, без `DiffUtil` и без `ItemTouchHelper`).

**Вердикт: брать.** Это единственная позиция в документе, которая ближе к «база платформы», чем к
«зависимость»: список поездок будет расти всю жизнь приложения, а `ScrollView` с полусотней живых
строк — конкретный правдоподобный сбой (рывки на прокрутке), а не гипотеза.

**Оговорка про `ListAdapter`/`DiffUtil`.** Брать RecyclerView — да; начинать с `DiffUtil` — нет.
`DiffUtil` окупается там, где список меняется точечно и часто (пришла строка, изменилась одна).
Список поездок открывается разом и целиком, скан добавляет строки по одной (`NotifyItemInserted` —
и без диффа точен), а телеметрия вообще не список, а **фиксированный набор полей**: ей место в
статической разметке, где каждое поле — свой `TextView` с именем, и правило «писать только при
изменении» (план 11 §0) применяется напрямую. Заводить `DiffUtil` на неё — это заводить сравнение
списков там, где список не меняет длину никогда.

### ConstraintLayout

**Пакет:** `Xamarin.AndroidX.ConstraintLayout` **2.2.1.6**, **27.06.2026**, `net10.0-android36.0` /
`net9.0-android35.0`, Microsoft. Зависимости: `AppCompat`, `ConstraintLayout.Core`, `Core`,
`ProfileInstaller`.

**Что даёт:** плоская разметка вместо вложенных `LinearLayout` — меньше проходов измерения.

**Чем лучше ручного варианта:** для **глубоких** разметок — заметно. Наши экраны глубокими не
являются: строка настройки — это «подпись слева, значение справа, подпись слоя снизу», строка
поездки — то же самое. Два уровня `LinearLayout` измеряются быстрее, чем решается граф ограничений
на той же разметке.

**Вердикт: не брать сейчас.** Боли нет: измерения разметки у нас нигде не были узким местом (узким
местом была отрисовка панели, и она решена своим `Canvas`). Вернуться, если появится экран с
десятком выровненных по сетке элементов.

### Material Components

**Пакет:** `Xamarin.Google.Android.Material` **1.14.0.5**, **06.07.2026**, .NET 9 и .NET 10 Android,
Microsoft и Xamarin, 32,4 млн загрузок, **20 транзитивных зависимостей** (включая AppCompat,
RecyclerView и, через них, Kotlin-рантайм).

**Что даёт применительно к нашим экранам:**

| Виджет | Наш экран | Ручной эквивалент |
|---|---|---|
| `MaterialButtonToggleGroup` | **Сегментный переключатель «Общее / Sherman L»** — ядро варианта B | Две `Button` с `selector`-фоном и своим состоянием — порядка 30 строк и один XML `selector` |
| `Chip` / `ChipGroup` в `HorizontalScrollView` | **Чипы разделов** на странице «Отображение» — вторая половина варианта B | `TextView` с фоном-`shape` в `HorizontalScrollView` — примерно столько же |
| `MaterialAlertDialogBuilder` | Диалоги правки числа, подтверждения удаления, меню слоя | `AlertDialog.Builder` из framework — есть всегда, выглядит по теме устройства |
| `Slider` | Только если решим вернуть ползунки | `SeekBar` из framework |
| `MaterialCardView` | Строки поездок | `CardView` (отдельный пакет) или `shape`-фон |
| `BottomSheetDialog` | Меню строки настройки | `AlertDialog` со списком (так и сделано сейчас) |

**Цена:** тема `Theme.Material3.*` становится обязательной (иначе инфляция Material-виджета падает
на этапе разбора атрибутов), 20 пакетов в графе, Kotlin-рантайм, самый заметный вклад в dex из
всего документа. Наша приборная панель при этом не выигрывает ничего — она рисуется своим
`Canvas` и о темах не знает.

**Вердикт: решение владельца, с уклоном в «не брать».** Материал берут ради вида «как всё
остальное на телефоне» и ради двух конкретных виджетов варианта B. Оба виджета воспроизводятся
парой десятков строк каждый, а тему всё равно придётся настраивать под наш тёмный экран. Если
владелец хочет системный вид без возни — брать, боль настоящая (шесть-семь мест: диалоги, чипы,
сегмент, карточки). Если приоритет — минимальный граф зависимостей, `AlertDialog` + свои `selector`
закрывают то же самое.

### Вариант «ничего не брать»

Он реален и его надо назвать: `android.widget.ListView` + `ArrayAdapter`, `AlertDialog.Builder`,
`LinearLayout` — всё это в framework, доступно без единого NuGet-пакета, и покрывает наши экраны
целиком. Проигрыш — прокрутка длинного списка поездок и отсутствие свайпа по строке. Это
единственное место, где «ничего» реально хуже.

## 3. Главный экран и панель — анти-рекомендации

Коротко, как и просили: **менять нечего и незачем.**

- **Замер уже сделан и он однозначен** ([dashboard-fps.md](dashboard-fps.md)): 62 кадра/с и худший
  кадр 17,4 мс на своём `Canvas` против 13 кадров/с и 91 мс на MAUI, на одном телефоне и одних
  данных. Ни одна библиотека здесь не решает задачу, которая уже решена.
- **Ни одна чужая библиотека не знает наших приборов.** Лента с barber pole, след поездки
  «мин/макс», стрелка тренда, окно значения, сглаживание хода по реальному времени
  (`TapeRenderer.Scroll()` на `NanoTime()`) — это не «график» и не «прогресс-бар», это набор
  приёмов, отобранный на стенде ([dashboard-feedback.md](dashboard-feedback.md)).
- **Кадровый источник должен остаться один.** Опись миграции
  ([§7](archive/native-rewrite-inventory.md#7-риски-и-неочевидное)) прямо предупреждает: если полосы
  тревоги и ленты начнут перерисовываться от двух источников, их частоты разойдутся и на записи
  экрана будет видно биение. Любой чужой `View` со своей анимацией — это второй источник по
  определению.
- **Единственная причина, по которой сюда что-то могло бы прийти, — это графики**, и они разобраны
  ниже как **отдельный экран**, а не как элемент панели.

Что действительно осталось сделать на панели — не библиотеки, а перенос `DashboardOptions` с
литералов на runtime плюс две поведенческие детали (мигание критического окна, мягкая тревога по
скорости); список — в [описи §4.3](archive/native-rewrite-inventory.md#43-сверка-с-wheeltalknative--что-уже-портировано).

## 4. Графики поездок — подтверждённая потребность

Владелец 29.07.2026: «графики нам точно понадобятся — в оригинальном проекте они играют большую
роль». Значит вопрос не «стоит ли», а «чем именно». В [плане 8 §3.3](android-plan-8-ride-database.md)
экран поездки сознательно сделан без графиков — «делать их дважды дороже, чем подождать»; это и
есть та точка, к которой мы вернулись.

### 4.1. Что именно рисует оригинал — требования, снятые с кода

Проверено по `C:\Work\repos\Wheellog.Android`. Зависимость: `com.github.PhilJay:MPAndroidChart:v3.1.0`.

**Живой график на главном экране** (`MainPageAdapter.kt`): один `LineChart`, два набора —
скорость (левая ось) и ток (правая), режим `CUBIC_BEZIER`, точки добавляются по мере прихода
телеметрии.
*У нас этой роли нет и не планируется*: ход величин на главном экране показывают ленты, и это
осознанное отклонение (AGENTS.md, «две ленты по краям вместо сетки плиток»). Требованием это не
становится, но объясняет, почему в оригинале график живёт ещё и в реальном времени.

**Экран поездки** (`map/StatsFragment.kt`, `map/MapActivity.kt`) — вот отсюда требования:

- **Два графика один под другим.** Первый: заряд, скорость (левая ось) + температура (правая).
  Второй: ШИМ, напряжение (левая) + мощность и далее (правая).
- **Ось X — время**, со своим `ValueFormatter` (`HH:mm:ss`).
- **Две независимые оси Y** на каждом графике (`AxisDependency.LEFT`/`RIGHT`) — иначе проценты,
  вольты и градусы на одном полотне несопоставимы.
- **Маркер по касанию** (`ChartMarkerView`): всплывающая карточка со **всеми** величинами в этой
  точке времени, каждая своим цветом, с автопозиционированием сверху/снизу от точки.
- **Синхронизация выделения между двумя графиками** — тап по первому подсвечивает ту же точку во
  втором (`OnChartValueSelectedListener`).
- **Зум и панорамирование жестами** — базовое поведение `LineChart`, отдельного кода в оригинале
  нет, потому что оно из коробки.
- Легенда, отключаемая сетка, текст «нет данных».

**Наш собственный заказ** ([ui-notes.md](ui-notes.md)): «нажатие на заряд открывает график разряда
за 12 часов» — это **не** график поездки: запрос идёт по времени и пересекает границы поездок.
План 8 это предусмотрел (`wheel_id` в каждой строке; индекс по нему заводится вместе с графиком).

### 4.2. Кандидат — MPAndroidChart

**Что даёт:** ровно перечисленное выше, без единой строки нашего кода на зум, маркеры,
форматтеры осей и синхронизацию выделения.

**Чем лучше ручного варианта:** ручной график поездки — это не «ещё один виджет вроде ленты».
Наш опыт с `TapeRenderer` переносится на отрисовку линий, но **не** на жесты: зум двумя пальцами с
инерцией, панорамирование с границами, попадание пальцем в ближайшую точку из тысяч, маркер,
который не уезжает за край экрана. Это недели, и каждая из этих недель — про то, что у чужой
библиотеки работает по умолчанию.

**Состояние библиотеки (Java):**
- Последний релиз — **v3.1.0** (2019). Репозиторий не архивирован, последний push — **05.06.2025**,
  38,2 тыс. звёзд, **2191 открытый issue**. Читать это надо так: библиотека **заморожена**, а не
  мертва. Для рисования на `Canvas` заморозка почти не страшна — она не зависит от новых API
  платформы; но и багов, которые кто-то починит, ждать не стоит.
- **AAR: 356 115 байт (≈348 КБ)** (JitPack, проверено).
- **Зависимости по POM: только `androidx.annotation:annotation:1.0.0` (runtime)** — то есть
  фактически ничего. **Kotlin не используется вовсе.** Это самый лёгкий класс биндинга, какой
  бывает.

**Состояние биндингов — и это главная развилка:**

| Путь | Пакет / способ | Версия | Дата | Кто поддерживает | Годится? |
|---|---|---|---|---|---|
| Чужой NuGet | `MPAndroidChart` (Flash3001) | 3.1.0 | **14.09.2020** | Комьюнити; репозиторий биндинга — последний коммит **30.09.2022**, 59 звёзд, привязан к 3.0.1 | **Нет.** TFM `MonoAndroid`; формально .NET для Android такие пакеты потребляет, но это шестилетний артефакт классического Xamarin |
| Чужой NuGet | `Karamunting.Android.PhilJay.MPAndroidChart` | 3.1.0.1 | **01.12.2020** | Один человек, 3 тыс. загрузок всего | **Нет.** `MonoAndroid 9.0`, заброшен |
| **Свой биндинг** | `AndroidMavenLibrary Include="com.github.PhilJay:MPAndroidChart" Version="v3.1.0" Repository="https://jitpack.io"` | v3.1.0 | — | **Мы** | **Да** |

**Цена:** ≈348 КБ AAR (до r8), один маленький проект-биндинг в солюшене, и **наша** ответственность
за то, что генератор биндингов переварит публичный API MPAndroidChart. API у него большой; вероятны
точечные правки метаданных биндинга (переименования, скрытие проблемных членов). Это разовая
работа, но её надо заложить: «пять строк в csproj» — это старт, а не гарантия, что всё соберётся с
первого раза.

**Вердикт: брать — но своим биндингом из Maven/JitPack, не чужим NuGet-пакетом.** Это тот редкий
случай, где зависимость лечит конкретную боль (жесты и маркеры на графике поездки), стоит меньше
мегабайта, не тянет ни Kotlin, ни AndroidX сверх аннотаций, и совпадает с оригиналом — но
совпадает по нашим критериям, а не потому что так у оригинала.

> **Уточнено 03.08.2026 (§4.6):** способ остался прежним — свой биндинг с JitPack, — но берётся
> **не эта библиотека, а её живой форк** `AppDevNext/AndroidChart` 3.1.0.31. Всё сказанное ниже
> про цену биндинга и метаданные к нему относится в той же мере.

### 4.3. Кандидат — Vico

**Что даёт:** современный, живой (v3.2.3, **20.06.2026**), Compose Multiplatform, поддерживается
Software Mansion.

**Почему не годится:**
- Kotlin + Compose. `@Composable`-функции в байткоде — не обычные функции: компилятор Compose
  добавляет `Composer`, ключи групп и логику пропуска рекомпозиции. Из C# их не вызвать никак.
  **Compose-библиотеки практически не биндятся**, и это не «сложно», а «нет пути».
- View-модуль у Vico формально есть, но **проект объявил Android «Compose-first»: views-модуль
  получает только критические исправления, а версионирование отвязано и относится к compose.**
  То есть даже если побороть Kotlin-специфику view-модуля, мы прицепимся к части, которую сам автор
  считает устаревшей.

**Вердикт: не брать.** Не по цене, а по невозможности.

### 4.4. Кандидат — рисовать самим

**Что даёт:** ноль зависимостей, полный контроль, тот же `Canvas`/`Paint`, который у нас уже
освоен, и палитра, уже согласованная с панелью.

**Где ломается:** см. 4.2 — не в линиях, а в жестах, попадании в точку и маркере. Плюс то, что
владелец назвал «графики играют большую роль»: если их будет несколько видов (поездка, разряд за
12 часов, будущие прогнозы плана 9), стоимость своего движка платится один раз, но она большая, и
она конкурирует не с MPAndroidChart, а с оставшимися пунктами roadmap.

**Вердикт: не как первый шаг.** Разумная позиция — взять MPAndroidChart на экран поездки; если
окажется, что нам нужны две-три статичные линии без зума (как раз «разряд за 12 часов»), их можно
нарисовать самим тем же кодом, что и ленты, — и это не будет противоречием: библиотека нужна там,
где нужны жесты.

### 4.5. Кандидат — SkiaSharp / LiveCharts

**Состояние:** `SkiaSharp.Views` **4.150.1**, **14.07.2026**, включает `net10.0-android36.0`,
Microsoft — то есть `SKCanvasView` для чистого Android доступен и живой. Но **готовых графиков в
нём нет**, а LiveCharts2 таргетов под чистый `net-android` не имеет (MAUI, WPF, Avalonia, Uno,
Blazor, WinForms).

**Вердикт: не брать.** Второй движок отрисовки рядом с уже работающим `Android.Graphics.Canvas` —
это нативная библиотека на каждый ABI ради полотна, которое у нас уже есть.

### 4.6. Живой форк MPAndroidChart — найден 03.08.2026

Раздел 4.2 писался, **не зная о нём**, и выбирал между замороженным оригиналом и мёртвыми
NuGet-биндингами. Форк `AppDevNext/AndroidChart` — единственный по-настоящему живой кандидат на
View-графики; последний push на день проверки.

| | Оригинал | Форк 3.1.0.x | Форк 5.x |
|---|---|---|---|
| Координаты | `com.github.PhilJay:MPAndroidChart:v3.1.0` | `com.github.AppDevNext:AndroidChart:3.1.0.31` (JitPack) | `com.github.AppDevNext.AndroidChart:chartLib:5.2.4` |
| Версия / дата | v3.1.0, **20.03.2019** | **3.1.0.31, 14.09.2025** | 5.2.4, 28.07.2026 |
| AAR | 356 115 Б | 444 523 Б | 628 622 Б |
| Пакеты классов | `com.github.mikephil.charting` | **те же** — совместим | `info.appdev.charting` — переименованы |
| Язык | Java | почти Java, следы Kotlin | **Kotlin целиком** |
| Зависимости POM | `androidx.annotation` — и всё | + `kotlin-stdlib`, `androidx.core`, `activity-ktx` | + `AppDevNext.Logcat:LogcatCoreLib`, тянущий **timber, korutiny, lifecycle** |

**Пятая ветка дисквалифицирована:** библиотека рисования графиков требует чужой логгер с
корутинами и lifecycle, и `LogcatCoreLib` живёт только на JitPack — его пришлось бы биндить
отдельно, чтобы удовлетворить Java Dependency Verification (`XA4241`). Корневой артефакт `5.2.4` —
агрегатор, тянущий заодно `chartLibCompose`; ссылаться можно только на `chartLib`.

Четыре зависимости третьей ветки — обычные AndroidX, все закрываются пакетами
`Xamarin.AndroidX.*` / `Xamarin.Kotlin.StdLib`.

**Решение владельца 03.08.2026: берём форк, ветку 3.1.0.x**, своим биндингом
(`AndroidMavenLibrary` с `Repository="https://jitpack.io"`, как и планировалось для оригинала).
Причина: шесть лет чужих багфиксов дороже трёх лишних AndroidX-пакетов, а имена классов совпадают
с оригиналом — отход обратно ничего не стоит.

Что при этом принято сознательно: **неопределённость биндинга у форка не меньше, чем у оригинала,
а чуть больше** — Kotlin там уже есть, пусть и следами, и генератор биндингов на нём может
споткнуться. Это разовая работа, но её надо заложить.

### 4.7. Мелкие графики без жестов — библиотека не нужна

Спарклайн 40×20 dp в плитке — это `Path` по точкам на `Canvas`, тем же кодом, что ленты. Полный
движок осей, легенд и жестов ради него — та самая лишняя сущность. **Библиотека нужна только там,
где нужны жесты**: зум, попадание пальцем в точку из тысяч, маркер, не уезжающий за край.

Проверено и отвергнуто заодно: `williamchart` (3.11.0, 15.07.2021 — красив, но **без зума и без
маркеров**), `robinhood/spark` (релизов нет вовсе; как идея — это и есть наш спарклайн на триста
строк), `GraphView` (последний релиз 2013), `HelloCharts`, `AnyChart`/`AAChartCore` (обёртки над
**WebView + JS**), `Microcharts` (Android-таргет тянет **MAUI**; чистый `Microcharts.Android` —
preview от 27.04.2021), `LiveCharts2` и `ScottPlot` (пакетов под чистый `net-android` не
существует), Syncfusion и SciChart (Xamarin-эра, коммерческая лицензия с регистрацией).

## 5. Карты — маршрут поездки

Раздел добавлен по запросу владельца («как и карты»). **Важно:** GPS-записи у нас нет вовсе —
[roadmap](roadmap.md) держит «GPS-блок в CSV» в разделе «чего в очереди нет намеренно», а
[план 8 §3.3](android-plan-8-ride-database.md) прямо отмечает, что экран поездки нарочно не
требует GPS (у оригинала без координат весь экран падает в «Failed to open map», унося с собой и
графики по ШИМ/току, к геоданным отношения не имеющие). **Карты потянут за собой GPS-подсистему —
это отдельная работа.** Ниже — выбор библиотеки и то, что имеет смысл решить сейчас.

### 5.1. Что использует оригинал

`org.osmdroid:osmdroid-android:6.1.20`. По коду `map/MapFragment.kt`:

- Тайлы `TileSourceFactory.MAPNIK` (обычные растровые тайлы OpenStreetMap), зум 8…20,
  мультитач.
- `Polyline` маршрута; точки — свой `LogGeoPoint` (координата + скорость, напряжение, заряд,
  температура, пробег, время), то есть **точка маршрута несёт телеметрию**.
- Маркеры «Старт», «Финиш» и «Максимальная скорость» (последний — только если точек больше 100 и
  скорость выше 20).
- Тап по линии находит ближайшую точку в радиусе 24 dp и открывает окно с телеметрией этой точки.
- `ScaleBarOverlay`, `CompassOverlay` со своим провайдером ориентации, свой `RotationOverlay`
  (поворот карты), автозум по `boundingBox` маршрута.

**GPS в оригинале** (`LoggingService.kt`) — платформенный `LocationManager`, `NETWORK_PROVIDER`
или `GPS_PROVIDER` по настройке, `requestLocationUpdates(provider, 250 мс, 0 м, listener)`.
**Никаких Google Play Services location.** Колонки в CSV:
`latitude,longitude,gps_speed,gps_alt,gps_heading,gps_distance`.

Это хорошая новость: сама GPS-подсистема зависимостей не требует вообще — она в framework.

### 5.2. Кандидаты

#### osmdroid

**Что даёт:** ровно то, что перечислено в 5.1, — карта, полилиния, маркеры, оверлеи, офлайн.

**Состояние библиотеки:** **6.1.20**, релиз **18.08.2024** (Maven Central), 44 версии всего.
Развивается медленно — но карта на растровых тайлах и не должна развиваться быстро.
**AAR: 861 704 байта (≈842 КБ)** — проверено на Maven Central.
**Зависимостей в POM нет ни одной** (проверено; в `build.gradle` самой библиотеки — только
тестовые). Чистая Java, без Kotlin, без AndroidX.

**Состояние биндинга:**

| Путь | Что это | Состояние | Годится? |
|---|---|---|---|
| `OsmdroidXamarin` (репозиторий самой osmdroid) | Биндинг для классического Xamarin | Застрял на osmdroid **5.0.1**, авторы сами пишут, что не поддерживается и нужны добровольцы | **Нет** |
| NuGet по запросу «osmdroid» | Находится только `BruTile.Osmdroid` 6.0.0 (27.10.2025, pauldendulk) | Это **не биндинг**: расширение BruTile для чтения офлайн-тайлов формата osmdroid | Не тот зверь |
| **Свой биндинг** | `AndroidMavenLibrary Include="org.osmdroid:osmdroid-android" Version="6.1.20"` (репозиторий Central по умолчанию) | **Мы** | **Да** |

**Офлайн:** osmdroid умеет офлайн-архивы тайлов (sqlite/mbtiles/zip/gemf) и кэширует скачанные
тайлы на устройстве — то есть уже проеханный маршрут открывается без сети. Онлайн-тайлы
OpenStreetMap бесплатны и не требуют ключа, но требуют корректного `User-Agent` и соблюдения
tile usage policy OSM (не качать массово). **Ни аккаунта, ни регистрации, ни ключа.**

**Цена:** ≈842 КБ AAR; свой биндинг-проект (класс сложности минимальный — Java без зависимостей);
осторожность с политикой тайлов OSM.

**Вердикт: брать, когда дойдёт до карт.** Совпадает с оригиналом, но выигрывает и по нашим
критериям: ноль зависимостей, ноль ключей, штатный офлайн.

#### MapLibre GL Native

**Что даёт:** векторные тайлы, плавный зум и поворот, штатное скачивание офлайн-регионов —
технически это лучшая карта из трёх.

**Состояние биндинга:** **биндинга нет.** Ни официального, ни живого комьюнити-пакета в NuGet;
в репозитории maplibre-native висит открытый запрос на .NET MAUI-биндинги, а публикации на эту тему
описывают самодельные биндинги, собранные под конкретный проект.

**Цена:** нативные `.so` под каждый ABI (самая тяжёлая позиция в документе после SkiaSharp),
Kotlin/Java поверх JNI, и биндинг, который придётся делать и чинить нам. Плюс векторным тайлам
нужен источник стиля и тайлов — а это, как правило, снова чужой сервис с ключом.

**Вердикт: не брать.** Для одного разработчика цена несопоставима с выигрышем.

#### Google Maps SDK

**Состояние биндинга — лучшее из всех:** `Xamarin.GooglePlayServices.Maps` **120.0.0.2**,
**27.06.2026**, `net10.0-android36.0` / `net9.0-android35.0`, владельцы Microsoft и Xamarin,
9,6 млн загрузок. Тут протухать нечему.

**Цена, и она решающая:** нужен **API-ключ**, проект в Google Cloud с включённым биллингом,
принятие Google Maps Platform Terms, наличие Play Services на устройстве, лицензия Android SDK
вместо открытой. **Офлайна для SDK нет** — скачанные области живут в приложении Google Maps, а не
в чужом. Для райдера за городом без сети это означает пустой серый прямоугольник вместо маршрута.

**Вердикт: не брать.** Это ровно то, против чего написано правило «внешних зависимостей нет»: ключ,
аккаунт и чужие условия ради картинки. Плюс отсутствие офлайна убивает основной сценарий.

#### Mapsui — вариант «вообще без биндинга»

**Что это:** карта, написанная на C#. `Mapsui` **5.1.0** (**27.05.2026**) + `Mapsui.Android`
**5.1.0** (**27.05.2026**), автор pauldendulk, MIT. `Mapsui.Android` — `MapControl` именно для
.NET для Android (проект прямо перечисляет «.NET for Android» среди поддерживаемых платформ).
Тайлы через BruTile (в том числе офлайн MBTiles), рендер — SkiaSharp.

**Чем лучше:** биндинга нет вообще — значит нечему протухать со стороны Java, а отладка идёт по
нашему же стеку. Ключей и аккаунтов не требует (источник тайлов выбираем мы).

**Цена и оговорки:**
- TFM пакета — `net8.0-android34.0` и `net9.0-android35.0`; **`net10.0-android36.0` в списке нет**.
  По правилам совместимости NuGet более новый TFM потребляет более старый, так что это должно
  собраться, — но **это надо проверить сборкой, а не поверить документу**.
- Тянет **SkiaSharp** (нативная библиотека на каждый ABI — самая дорогая по размеру позиция во
  всём документе), `NetTopologySuite`, `BruTile`.
- Экосистема маленькая: 32,1 тыс. загрузок у `Mapsui.Android` всего. Проект старый и живой, но
  вопросы «как сделать X» гуглятся хуже, чем по osmdroid.

**Вердикт: держать как альтернативу osmdroid — решение владельца.** Выбор между ними — это выбор
«свой биндинг чистой Java на 842 КБ» против «ноль биндингов, но SkiaSharp в APK». Если владельца
пугает именно перспектива поддерживать биндинг — Mapsui честно снимает эту заботу.

### 5.3. Что имеет смысл решить сейчас, а что можно отложить

Владелец просил выбрать библиотеку сейчас, чтобы не переделывать хранение точек. Проверив оба
кандидата, скажу честнее: **хранение от выбора почти не зависит.**

- И osmdroid (`GeoPoint`), и Mapsui, и любая другая карта принимают **широту и долготу в градусах
  WGS84** — это не библиотечное соглашение, а формат, в котором координату отдаёт сам Android
  (`Location.Latitude`/`Longitude`, `double`). Хранить надо именно так; ни проекция (osmdroid и
  Mapsui считают её сами), ни внутреннее представление библиотеки на схему не влияют.
- Значит риск «переделать хранение из-за смены библиотеки» **низкий**, и выбор карты можно
  спокойно отложить до момента, когда карты будут делаться.

**А вот что действительно стоит решить до первой миграции схемы** — потому что
[уже написанную миграцию не правят](../AGENTS.md) (на телефоне в этом файле лежат поездки,
которых нет больше нигде):

1. **Состав полей точки.** Оригинал пишет `latitude, longitude, gps_speed, gps_alt, gps_heading,
   gps_distance`. Из кода карты видно, зачем: `LogGeoPoint` несёт ещё и телеметрию (скорость,
   напряжение, заряд, температуру, пробег) — чтобы тап по линии показал состояние колеса в этой
   точке. У нас телеметрия **уже** лежит в базе построчно с временем, поэтому дублировать её в
   точке не нужно: достаточно, чтобы точка имела то же время, что и строка телеметрии.
2. **Куда писать.** Либо колонки в существующей таблице телеметрии (координата приходит реже, чем
   кадры, — будет много NULL), либо отдельная таблица точек со своим временем. Второе честнее:
   GPS даёт точку раз в 250 мс–секунду и **независимо** от кадров с колеса, а склеивать два потока
   по времени база умеет.
3. **Источник координат — платформенный `LocationManager`**, как в оригинале. `play-services-location`
   (Fused) точнее и экономнее по батарее, но это Google Play Services: аккаунт не нужен, зато
   зависимость от сервисов Google на устройстве — нужна. Для нашего правила это лишнее.
4. **Точность и её хранение.** Оригинал пишет высоту и курс, но не точность. Точка с погрешностью
   50 м на маршруте выглядит так же, как точка с погрешностью 5 м, и рисует зигзаг там, где ехали
   прямо. Одна колонка `accuracy` стоит ничего и позволяет потом отфильтровать мусор **при чтении**
   — ровно так же, как план 11 §5.6 чинит три другие болячки чтения.

Всё перечисленное — вопросы к отдельному плану GPS, здесь они только зафиксированы, чтобы решение
о картах не пришло раньше решения о том, что мы вообще пишем.

## 6. Kotlin-специфика — коротко и практично

Пакет-фундамент: **`Xamarin.Kotlin.StdLib` 2.4.0.1, 27.06.2026**, `net10.0-android36.0` /
`net9.0-android35.0`, Microsoft и Xamarin, 61,6 млн загрузок. Он нужен всегда, когда биндуемая
библиотека написана на Kotlin. Java Dependency Verification .NET 9+ сам об этом скажет:
`XA4242: … Microsoft maintains the NuGet package 'Xamarin.Kotlin.StdLib' that could fulfill this
dependency`.

Что стоит знать до того, как выбирать Kotlin-библиотеку:

| Особенность Kotlin | Что видит C# | Практический вывод |
|---|---|---|
| `@Composable`-функции | Ничего пригодного: компилятор Compose превращает их в функции с `Composer` и группами рекомпозиции | **Compose-библиотеки не биндятся.** Это отсекает Vico и весь современный Kotlin-UI разом |
| `suspend fun` | Метод с лишним параметром `Continuation` | Формально вызывается, практически бессмысленно без корутинного контекста. Библиотека с асинхронным API на корутинах — плохой кандидат |
| `companion object` | Вложенный класс `Companion` + статическое поле-экземпляр | Работает, но вызовы выглядят непривычно (`Foo.Companion.Bar()`) |
| Параметры по умолчанию | Синтетические перегрузки `…$default` с маской битов | Из C# надо передавать все параметры; синтетика засоряет биндинг |
| `internal`-члены | Публичные методы с искажёнными именами (`foo$module_name`) | Мусор в биндинге; лечится метаданными биндинга (скрыть) |
| `inline` / `reified` | В байткоде для внешнего вызова их нет | Часть API просто не существует для C# |
| `value` / `inline class` | Разворачивается в примитив, сигнатуры «уезжают» | Источник неочевидных несовпадений |
| `data class`, `sealed`, обычные классы | Биндится нормально | Kotlin сам по себе не приговор |

**Главный практический вывод:** предпочитать **Java-библиотеки без зависимостей**. Обе
рекомендации этого документа (MPAndroidChart, osmdroid) — ровно такие: чистая Java, ноль или почти
ноль зависимостей в POM, Kotlin не используется. Для них биндинг — это скачивание AAR и генерация
обёрток, а не проект по мотивам чужого байткода.

### Размер APK

Измеренные величины (не оценки):

| Что | Размер | Комментарий |
|---|---|---|
| `MPAndroidChart` v3.1.0 AAR | **348 КБ** | + `androidx.annotation` (крошечный) |
| `osmdroid-android` 6.1.20 AAR | **842 КБ** | зависимостей нет вовсе |
| `Xamarin.Google.Android.Material` | не измерено | **20 транзитивных пакетов**, включая Kotlin-рантайм — самая тяжёлая AndroidX-позиция |
| `Xamarin.AndroidX.Preference` | не измерено | 6 прямых зависимостей, тянет Kotlin через `*.Ktx` |
| SkiaSharp (через Mapsui) | не измерено | нативная `.so` **на каждый ABI** — обычно самая крупная статья в APK |

**Как это считать по-честному:** Release-сборка .NET для Android прогоняет и триммер .NET, и r8 по
Java-коду, поэтому номинал AAR — верхняя граница, а не факт. Единственный честный способ — собрать
Release до и после и сравнить размер APK. Спорить о килобайтах без этого замера — то же самое, что
спорить о FPS без `dashboard-fps.md`.

### AOT и трим

- **Наш обычный случай безопасен.** Мы вызываем Java из C#; такие вызовы триммер видит и не режет.
- **Опасен обратный случай** — когда Android создаёт наш тип по имени: типы, надуваемые из XML
  (свои `View`), `Activity`/`Service` из манифеста, и `PreferenceFragmentCompat`, который
  инстанцирует классы по строке из XML. Это ещё один довод против XML-ветки Preference: там
  рефлексия по имени класса встроена в саму механику.
- Дополнительный расход: `AndroidMavenLibrary` тянет AAR в сборку, а значит сборка перестаёт быть
  полностью офлайновой при чистом клоне — Maven-артефакт скачивается. Для CI это надо знать
  заранее; для одного разработчика с кэшем это незаметно.

### Риск протухания — единственная шкала, которая тут важна

| Класс | Примеры из этого документа | Риск |
|---|---|---|
| Поддерживается Microsoft | AndroidX (RecyclerView, Preference, ConstraintLayout), Material, GooglePlayServices.Maps, Kotlin.StdLib, SkiaSharp | **Почти ноль.** Обновления идут пачками ежемесячно (27.06.2026 — сразу пять пакетов из списка) |
| Живой сторонний .NET-проект | Mapsui | **Низкий**, но экосистема маленькая |
| Чужой комьюнити-биндинг | `MPAndroidChart` (2020), `Karamunting…` (2020), `OsmdroidXamarin` (osmdroid 5.0.1) | **Высокий и уже реализовавшийся.** Все три мертвы |
| **Свой биндинг из Maven** | MPAndroidChart, osmdroid | **Переносится на нас** — и для Java-библиотек без зависимостей это правильный обмен: обновление раз в год-два против чужой заброшенности |

Отсюда вывод, который стоит держать в голове всему проекту: **не «есть ли NuGet-пакет», а «кто его
чинит».** Для двух наших кандидатов ответ «никто» — и именно поэтому свой биндинг из Maven лучше
чужого пакета, а не хуже.

Поиск по GitHub с push после 01.01.2025 вернул на всю нишу **два** репозитория, оба нежилые.
Отдельно проверено `language:Kotlin` четырьмя запросами: **выше 300★ в мире Kotlin + View нет ни
одного неархивированного проекта.**

**Главное: ни одна из них не меняет ширину плитки.** Все умеют только переставлять. Ширина — это
`GridLayoutManager.SpanSizeLookup`, встроенный механизм; чужие библиотеки либо игнорируют его,
либо навязывают свой layout manager, спанов не знающий. Любая из них — треть задачи ценой мёртвой
зависимости.

### 9.2. Из чего складывается своя реализация

| Часть | Чем | Цена |
|---|---|---|
| Ширина 1/2/3 в ряд | `GridLayoutManager(ctx, 6)` + `SpanSizeLookup` (6 — НОК, спаны 6/3/2) | ~10 строк |
| Перетаскивание | `ItemTouchHelper.SimpleCallback`, флаги `UP\|DOWN\|LEFT\|RIGHT` — без горизонтали сетка не двигается | ~80 строк |
| Ручка | `StartDrag` из `OnTouch` по иконке | ~15 строк |
| Смена ширины | правка спана + `NotifyItemChanged` | ~20 строк |
| Добавить/убрать | список величин с галочками — **не** перетаскивание между двумя сетками, этого `ItemTouchHelper` не умеет | отдельный экран |

**Около 130 строк, новых зависимостей ноль** — `RecyclerView` уже одобрен §2.

**Камень:** тень перетаскиваемой плитки рисуется её собственным размером — узкая, брошенная на
место широкой, растянется только при отпускании. Лечится своим `OnChildDraw`.

### 9.3. Compose — дверь не заперта, но за ней вторая система сборки

Kotlin-мир ушёл в Compose целиком, и живое там есть: `sh.calvin.reorderable` **3.1.0, 20.04.2026**
(перетаскивание с автопрокруткой, анимацией соседей и откликом вибрацией), `compose-grid` 2.8.0,
плюс встроенные `LazyVerticalGrid` с `GridItemSpan` и `Modifier.animateItem()`. На Compose этот
экран — 30–40 строк вместо 130.

Технически путь существует, и это стоит зафиксировать точно, чтобы не открывать вопрос заново:

- Microsoft публикует **`Xamarin.AndroidX.Compose.*` 1.11.4 от 13.07.2026** под
  `net10.0-android36.0` — зависимости закрываются штатно, не ручным сбором AAR.
- Биндинг локального `.aar` тривиален: `dotnet new android-bindinglib`, файл в папку проекта.
- `@Composable` через границу **не ходит и ходить не может**. Единственная рабочая схема — свой
  Kotlin-модуль, отдающий наружу обычный `View`-фасад с `ComposeView` внутри. Забиндить
  Compose-библиотеку напрямую невозможно, обёртка обязательна.

**Цена — и из-за неё отвергнуто владельцем 03.08.2026:**

| Что | Цена |
|---|---|
| Тулчейн | JDK, Gradle, AGP, Kotlin с compose-плагином (версия жёстко привязана к Kotlin), Android Studio для отладки — **вторая система сборки** в проекте, который собирает один человек |
| Сборка | .NET Android SDK **Gradle не вызывает**: либо двоичник в гите, либо `Exec` на `gradlew` — и тогда `dotnet build` перестаёт быть достаточной проверкой. Тёплая пересборка — 10–40 с на каждую правку плитки |
| Условие запуска | Все наши одиннадцать активити — `Android.App.Activity`. `ComposeView` требует `ViewTreeLifecycleOwner`, который ставит только `ComponentActivity`; иначе `IllegalStateException`. Либо менять базовый класс всем, либо реализовывать самим |
| Размер | Compose UI 6,3 МБ + Foundation 5,9 МБ + Runtime 2,8 МБ до R8 — против 1,19 МБ у всего `RecyclerView` |
| Кадры | У Compose свои часы рекомпозиции — второй кадровый источник, ровно то, о чём предупреждает §3 |
| Прецеденты | Примеров Compose из .NET for Android **не найдено ни одного**; документация описывает биндинг **чужих** готовых `.aar` |

**Вердикт: не брать.** Сто строк экономии против второй системы сборки. Если эта дверь однажды
понадобится, открывать её надо не на плитках, а решением «часть интерфейса живёт в Compose» —
платить полную цену тулчейна за самую дешёвую задачу смысла нет.

Промежуточный вариант «свой Kotlin-модуль на View, без Compose» отброшен сразу: цена тулчейна та
же, выигрыш нулевой — живых Kotlin+View библиотек не существует (§9.1).
