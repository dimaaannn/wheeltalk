# Begode: сверка с родным приложением

Источник — родное приложение `com.zzcyi.monotroch` (Begode) 1.0.49, декомпилят
`C:\Work\repos\loeuc\src_begode`. Два класса (`HomeSettingActivity`, `BatteryInfoActivity`)
декомпилировались обычным jadx с потерянными телами веток — читаны из `showbad/`, это отмечено
в каждой ссылке отдельно. Остальные четыре протокольных класса — из `sources/`.

**Метод.** Разбор кадра скопирован независимо в шесть UI-классов (`HomeFragment`,
`HomeSettingActivity`, `BatteryPackActivity`, `ModeSetActivity`, `AmbientLightSettingActivity`,
`BatteryInfoActivity`, `MileageStatisticsActivity` — фактически семь). Все они прочитаны. Где поля
совпадают дословно между классами — упомянут один, репрезентативный. Где расходятся — указаны все.

Наша сторона — `WheelTalk.Core/Decoding/GotwayDecoder.cs`. Для проверки утверждений данными
переразобраны как 24-байтные кадры (`55 AA … 5A 5A 5A 5A`) все четыре replay-файла MTen3
(`replay/mten3-calm-ride.csv`, `mten3-parking.csv`, `mten3-alarm-spinup.csv`,
`mten3-slowing-to-stop.csv`) — так добыт факт, вынесенный в начало §2: **на реальном MTen3 по проводу
идут только кадры `type=0/page=24` и `type=4/page=24`, парами 1:1, ничего больше** (2074 кадра всего
по четырём файлам, ни одного `type∈{1,2,3,5,6,7}`). Это ограничивает, что вообще можно подтвердить
записью, а не только чтением кода — отмечено по тексту.

## 1. Раскладка кадров

Заголовок и 24-байтная рамка — уже установленный факт (см. поручение), не переоткрывается.
Внутри рамки: **тип в байте `[18]`, номер страницы в `[19]`** — подтверждено по всем семи классам.

### 1.1 `page=24` (0x18) — «ядро»: телеметрия и эхо настроек в одних и тех же полях

Внутри `page=24` тип `[18]` **не образует пяти независимых кадров, а один: 16 байт (`[2..17]`)
одной рамки, где нижняя половина (`[2..13]`) — телеметрия, верхняя (`[14..17]`) — эхо текущих
настроек.** Разные экраны читают разные подмножества одной и той же байтовой строки, а не разные
байтовые строки — установлено сравнением `HomeFragment` (телеметрия) и `HomeSettingActivity`
(настройки) на одинаковых `[18]`:

| `[18]` | `HomeFragment.java` (`[2..13]`, телеметрия) | `HomeSettingActivity.java` (showbad, `[14..17]`, настройки) |
|---|---|---|
| 0 | напряжение `[2:3]`, скорость `[4:5]` (raw·3.6/100 = км/ч), запас хода `[6:7]`, пробег сессии `[8:9]`, ток `[10:11]` (÷100 = А), температура `[12:13]` (raw/340+36.53) — `HomeFragment.java:950-1186` | громкость зуммера `[16:17]`; битовое слово `[14:15]` = angle10(6 бит)·angle5(5 бит)·power3(2 бита)·momm(3 бита) — `showbad/HomeSettingActivity.java:1686-1730` |
| 1 | напряжение пакета `[6:7]`, макс./мин. температура `[10:11]`/`[12:13]` (offsets `[2:5]`,`[8:9]`,`[14:15]` вычисляются, но не используются) — `HomeFragment.java:1201-1211` | порог сигнала о разряде, % `[2:3]` — `showbad/HomeSettingActivity.java:1660-1685` |
| 2 | не разбирается вовсе (ветка пустая) — `HomeFragment.java:1236` | статус калибровки: 0=идёт, 1=калибруется, 2=готово, `[2:3]` — `showbad/HomeSettingActivity.java:1798-1841` |
| 4 | суммарный пробег 32 бита `[2:5]` (÷1000 = км), единицы `[7]` бит0, режим `[6:7]>>13`, deviceType `[16:17]`, **биты тревог `[14]`** (см. §3) — `HomeFragment.java:1237-1260` | те же поля плюс лимит скорости `[10:11]`, режим подсветки `[12:13]`, наклон-отсечка `[6:7]` биты 7-8 — `showbad/HomeSettingActivity.java:1512-1650` (то же поле, шире прочитано) |
| 7 | ток `[2:3]` (÷100 = А), температура силовой части `[6:7]` (без формулы, целое °C), PWM/заряд % `[8:9]` — `HomeFragment.java:1441-1453` | слабый магнетизм (старший ниббл `[5]`) и наклон вбок (младший ниббл `[5]`) — `showbad/HomeSettingActivity.java:1842-1895` |

Вывод: это **один непрерывный поток из двух чередующихся типов** на реальном MTen3
(`type=0` и `type=4`, подтверждено данными, см. врезку метода) — `type=1,2,7` существуют в
протоколе (подтверждены чтением остальных пяти классов), но не наблюдались ни разу за четыре
поездки MTen3.

### 1.2 `page=0..6` — батарейные пакеты: тип `[18]` выбирает физический пакет, страница — окно ячеек

Установлено по `BatteryPackActivity.java` (полностью, страницы `0..6`) и `HomeFragment.java`
(частично, страницы `0..5`):

- `[18]==1` — «инфо»-кадр: ёмкость/ток `[8:9]`, второе число `[14:15]`, макс./мин. температура
  `[10:11]`/`[12:13]`, 16-битное битовое слово статуса `[16:17]` (реверсированное строкой,
  `HexUtil.toBinary`+`TextUtils.getReverse`). Разложение битов **из отдельного места**
  (`HomeFragment.java:1213-1234`, тот же формат встречается для *другого* поля тревог — см. §2.3):
  биты `[2:4)`=`00`перегрев/`01`недогрев, биты `[9:12)`=`001`ошибка связи/`010`обрыв
  батареи/`100`аномалия ячейки/`101`аномалия заряда;
- `[18]∈{2,3,5,6}` — 8 напряжений ячеек за страницу (`getShort` на смещениях `2,4,…,16`),
  накапливаются по страницам `0..6` в массив на пакет: `[18]=2`→пакет A, `3`→B, `5`→C, `6`→D,
  до 50 ячеек на пакет (страница 6 даёт только 2 ячейки, `48+2=50`) —
  `BatteryPackActivity.java:889-1249`.

«Инфо»-кадр (`[18]==1`) устроен ортогонально: страница здесь — **номер отдельного модуля/BMS**, а
не окно среза одного пакета (`HomeFragment.java` держит до шести таких структур — `info1..info6`,
`BatteryPackActivity.java` — до четырёх, `strings1..4`, `BatteryInfoActivity.java` (showbad) —
тоже четыре, `strings1..4`, `showbad/BatteryInfoActivity.java:176-236`). Число «инфо»-страниц (до
6-7) не обязано совпадать с числом пакетов ячеек (4, `[18]∈{2,3,5,6}`) — это два независимых
измерения одной решётки `(тип,страница)`.

## 2. Расхождения с нашим декодером

### 2.1 `hwPwm` читается из поля, которое на самом деле — эхо настроек, не телеметрия

`GotwayDecoder.cs:237`: `hwPwm = SignedShortFromBytesBE(buff, 14) * 10`, читает `type=0` смещение
`[14:15]`. По §1.1 это смещение на `page=24` — **не PWM**, а битовое слово angle10/angle5/power3/momm
(эхо настроек тряски/наклона), подтверждено `showbad/HomeSettingActivity.java:1719-1723`. Настоящего
PWM/выхода в `type=0` на этом месте нет вовсе — родное приложение получает PWM% из `type=7`
смещения `[8:9]` (`HomeFragment.java:1449-1452`), которого MTen3 **не присылает** (см. врезку метода).

**Смягчение, важное для вывода.** Для штатной прошивки (`HwPwm=false` после хендшейка `"GW"`,
`GotwayDecoder.cs:167`) отображаемый `CalculatedPwm` считается не из `Output`, а формулой от
скорости/напряжения (`WheelState.CalculatePwm()`, `WheelState.cs:232-238`) — подтверждено записью:
в `WheelTalk.Tests/Fixtures/mten3_recorded_20260719.csv` колонка `Pwm` растёт линейно со `Speed`
(коэффициент ≈1/44.4 на всех строках), что и даёт формула, а не сырое значение из `[14:15]`.
Значит **гейдж хода райдер видит верный**, а испорченное значение (`Output`/`OutputRaw`) остаётся
только во внутреннем состоянии — риск актуален для прошивок с `HwPwm=true` (Alexovik CF/BF), где
`UpdatePwm()` берёт `Output` напрямую (`WheelState.cs:225-229`); эти прошивки вне заявленного
охвата порта (`GotwayDecoder.cs:20-25`), но если пользователь на них окажется — гейдж покажет мусор.

### 2.2 Биты тревог `1` и `2` названы «Speed2»/«Speed1», в родном приложении — «mos»/«gyroscope»

`GotwayDecoder.cs:379-385` (кадр `0x04`, байт `[14]`, наш порядок бит от LSB):

| бит | у нас (`GotwayDecoder.cs:379-385`) | в приложении (`HomeFragment.java:1312-1369`, реверс строки — см. §1.2) |
|---|---|---|
| 0 | нет текста, только `SetWheelAlarm` | `alarm_power_h` — превышение мощности |
| 1 | **«Speed2»** | **«mos» — неисправность силового ключа** |
| 2 | **«Speed1»** | **«gyroscope» — неисправность гироскопа** (в приложении ещё и гасится, если `maxSpeed<15` — UI-эвристика, не свойство провода) |
| 3 | LowVoltage | volt_l — совпадает |
| 4 | OverVoltage | volt_h — совпадает |
| 5 | OverTemperature | temp_h — совпадает |
| 6 | errHallSensors | hall — совпадает |
| 7 | TransportMode | «lock/state» — требует **трёх кадров подряд** прежде чем показаться (`isLock>=3`, `HomeFragment.java:1369-1381`); у нас показывается с первого кадра — мы строже фильтра оригинала, не слабее |

Биты `3,4,5,6` подтверждены и кодом, и записью (`mten3-alarm-spinup.csv` даёт `[14]=0x11` =
биты `0`+`4`, т.е. `power_h`+`volt_h` одновременно — сценарий разгона). **Биты `1` и `2` в наших
четырёх поездках MTen3 ни разу не взводились** — сверить с записью нельзя, вывод только из чтения
кода (капкан 4: не выбираю красивое, отмечаю как код-код расхождение, не код-данные). Если источник
верен — неисправность силового ключа сегодня показывается райдеру как рядовое «Speed2», занижая
тяжесть события.

### 2.3 Отдельный канал ошибок BMS (`type=1`, смещение `[16:17]`) не разбирается вовсе

По §1.2: `type=1`-кадр (что на `page=24`, что на страницах `0..6`) несёт 16-битное слово статуса
(перегрев/недогрев конкретного модуля + 3-битный код связь/обрыв/ячейка/заряд). Наш
`DecodeFrame01` (`GotwayDecoder.cs:286-319`) читает из этого же кадра напряжение `[6:7]`, ток
`[8:9]`, температуры `[10:11]`/`[12:13]`, полу-напряжение `[14:15]` — **смещение `[16:17]` не
трогает совсем**. Эти шесть аварийных состояний конкретного модуля (не всей связки) сегодня нигде
не всплывают. Смягчение то же, что в §2.1: на MTen3 `type=1` не наблюдался ни разу за четыре
поездки — риск реален для других моделей Begode с активной BMS-телеметрией, не подтверждён для
MTen3 записью.

### 2.4 Пакеты C/D (`[18]=5,6`) не долетают до диспетчера вовсе

`GotwayDecoder.cs:126-129` разбирает `frameType==0x02||0x03` в `DecodeBmsCells` — `0x05`/`0x06`
там нет ни единой веткой. По §1.2 это два из четырёх физических пакетов напряжений ячеек
(`[18]=5`→пакет C, `6`→D, `BatteryPackActivity.java:995-1004,1211-1220,1243-1249` и параллельно).
Для колёс с 3-4 параллельными пакетами (крупные Begode — EX30, Msuper Pro, RS19) половина ячеек
не попадёт в `WheelState.Bms1/Bms2` вовсе. Не проверено записью — MTen3 таких кадров не шлёт (у
него меньше пакетов).

### 2.5 «Инфо»-страницы сворачиваются в два BMS-слота, `page=24` дополнительно путается с ними

`DecodeFrame01` берёт `bmsnum = buff[19] & 0xFF` и делит `bmsnum<2 ? Bms1 : Bms2`
(`GotwayDecoder.cs:299-300`). По §1.2 страница здесь — номер отдельного модуля (до 6-7 штук), т.е.
страницы `2..6` сворачиваются в один и тот же `Bms2`, взаимно перезаписывая друг друга. Отдельно:
на `page=24` тот же `[18]==1` — это агрегированная сводка «всего пакета» (§1.1), а не седьмой
модуль, но `bmsnum=24` по формуле выше тоже уходит в `Bms2` — агрегат смешивается с последним
увиденным реальным модулем. Не наблюдалось записью (см. §2.3) — тот же класс риска.

### 2.6 Статус калибровки (`type=2`/`page=24`) не разбирается — по всей видимости, осознанно

`GotwayDecoder.cs` не заводит ветку `frameType==0x02` для калибровочного статуса вовсе (диспетчер
`126-129` трактует `0x02` как страницу ячеек, что верно только когда `page≠24` — смешение осей
безобидно здесь, т.к. `page=24` для `type=2` на MTen3 не наблюдалась). Команда `BuildCalibrate()`
(`GotwayDecoder.cs:586-590`) шлёт `c`, затем `y` через 300 мс — приложение делает то же
(`showDialogSet`, `HomeSettingActivity.java:980-988`), но ждёт 1000 мс, а не 300. Раз статус
калибровки не читается назад ни у нас, ни (в телеметрическом смысле) не нужен — это, похоже,
сознательный вырез «эхо для UI-диалога», не потерянная авария; выношу как факт, не как дефект.

### 2.7 Побочный гудок после смены света/режима — поведения приложения нет

`BuildLightModeCommand` и `BuildUpdatePedalsMode` шлют `b` (гудок, `HomeFragment.java:2322`
подтверждает: `b` = свисток) с задержкой 100 мс после каждой смены (`GotwayDecoder.cs:571,579`).
В приложении смена света (`Q`/`T`/`E`, `HomeFragment.java:2219-2274`) и смена режима (`s`/`f`/`h`,
`ModeSetActivity.java:127-141`) — одиночные команды, без последующего гудка. Если это не осознанный
аудио-отклик WheelTalk, при каждом тапе по свету или режиму колесо у пользователя будет пикать —
поведения, которого нет у производителя.

### 2.8 `BuildUpdatePedalsMode(3)` шлёт `i` — команду уровня сигнализации, не режима езды

Числовая конвенция 0=жёсткий/1=средний/2=мягкий у нас и Veteran согласована
(`VeteranDecoder.cs:381-386`, `GotwayDecoder.cs:577`: `0→"h", 1→"f", 2→"s"` — совпадает с
`ModeSetActivity.java:127`: `s`=мягкий,`f`=комфорт,`h`=взрывной — **не перепутано**, числа просто
идут в обратном порядке от «мягкий→жёсткий»). Но `pedalsMode=3 → "i"` — по
`showbad/HomeSettingActivity.java:1175-1181` `i` — это выбор уровня идентификации тревоги
(«двойная тревога»), не режим педалей вообще. В самом WheelTalk `SetPedalsMode(3)` из UI сегодня
не вызывается нигде (проверено `grep`) — риск на сегодня не открыт для рядового пользователя, но
это ловушка на будущее, если в UI когда-нибудь добавят четвёртый пункт.

### 2.9 Команда `R` перегружена (аналог капкана LeaperKim с опкодом 22)

Голая `R` — свет-режим №3, только для `deviceType==205` (`HomeFragment.java:2231-2233`). Та же
буква после `W`+пауза — часть тройки `W`,`R`,`<0-9>` для тонкой настройки угла защиты от завала
(`showbad/HomeSettingActivity.java:685-696`, отличается от углового кадра `>`/`=`/`<`, см. §5).
Различить их можно только по контексту (что было послано перед этим), не по самому символу —
формально то же явление, что зафиксировано для LeaperKim (опкод 22 на три смысла). Мы `R` для
настроек не шлём вовсе (нет соответствующего `BuildXxx`), так что коллизии внутри WheelTalk нет —
фиксирую как свойство протокола, не как наш дефект.

## 3. Аварии: доходят ли до райдера

**В отличие от InMotion P6 (там не доходит ни одна) — у Begode базовый канал тревог доходит.**
`DecodeFrameB` (`GotwayDecoder.cs:367-407`) вызывает `_state.SetWheelAlarm(...)` и
`_state.SetAlert(...)` на каждый кадр `type=4`, что по памяти проекта (`alerts-on-every-screen.md`)
означает показ на всех экранах. Подтверждено записью: `mten3-alarm-spinup.csv` действительно
взводит `[14]=0x11` (биты `power_h`+`volt_h`) в момент имитации резкого разгона, и это доходит до
`SetAlert` неизменным по смещению (`GotwayDecoder.cs:375`).

Оговорки к «доходит»:
- метки бит `1`/`2` расходятся с источником (§2.2) — тревога **показывается**, но может быть
  подписана неверно (MOSFET-неисправность как «Speed2»);
- отдельный, более гранулярный канал ошибок конкретного модуля BMS (§2.3, `type=1[16:17]`) —
  **не доходит вовсе**, ни в каком виде, ни на одном экране;
- бит `7` (transport/lock) в приложении дебounсится тремя кадрами перед показом, у нас — нет
  (см. §2.2) — у нас **строже**, не слабее оригинала.

## 4. Температура

**У Begode формула совпадает у нас и в приложении дословно, ни в одной из двух температур бага
уровня InMotion V2 (±256) нет.**

- Основная (гиро) температура: приложение — `(getShort2(bArr5[13],bArr5[12]) / 340.0f) + 36.53`
  (`HomeFragment.java:1180`); мы — `(SignedShortFromBytesBE(buff,12) / 340.0 + 36.53) * 100`
  (`GotwayDecoder.cs:233-234`, `×100` — внутренняя конвенция сотых, не отдельная формула). Знаковый
  short с обеих сторон (`getShort2`/`SignedShortFromBytesBE`) — совпадает и по знаку, не только по
  множителю;
- Вторая (силовая часть/мотор) температура: приложение хранит `getShort2(bArr5[7],bArr5[6])`
  без всякого преобразования (`HomeFragment.java:1448`, значение нигде дальше не форматируется
  формулой); мы — `SignedShortFromBytesBE(buff,6) * 100` без преобразования (`GotwayDecoder.cs:417,427`)
  — тоже совпадает.

Оговорка: вторая температура идёт в кадре `type=7`, которого MTen3 не шлёт (см. врезку метода) —
совпадение формул подтверждено чтением обеих кодовых баз, не подтверждено записью для этого
конкретного колеса.

## 5. Команды

Список из поручения (`b, N, Q, R, W, E, T, C, X, Y, M, m, g, y, u, o, i, 0`) — подтверждённое
подмножество. При чтении шести классов нашлось заметно больше: `P, B, U, ", >, =, <, +, -, x, e,
s, f, h, c` — не было в исходном списке.

| Команда | Назначение | Источник |

## 6. Расшифровка канала ошибок BMS (`type=1`, смещение `[16:17]`)

Продолжение §2.3: там был зафиксирован факт (канал не разбирается), здесь — коды. Источник —
`showbad/BatteryInfoActivity.java` (единственный экран, который **показывает** это поле текстом,
`updateView()`) вместе с раскладкой битов из `BatteryPackActivity.java:899-913` (откуда берутся
сами значения `strings1..4`) и подписи полей — из `res/layout/activity_battery_info.xml` +
`res/values/strings.xml` (`string2..string17`).

**Капкан 3, отвечаю прямо: тексты лежат локально, не на сервере.** Это статические ресурсы
приложения — `C:\Work\repos\loeuc\src_begode\resources\res\values\strings.xml:646-665`
(китайский, язык по умолчанию) и `res\values-en\strings.xml:333-352` (английский; всего
переведено на ~70 языков, `res/values-XX/`). Ничего похожего на серверный словарь KingSong здесь
нет — сервер приложению для этого канала не нужен.

**Капкан 2, проверено: ловушки чужой библиотеки в этом месте нет.** Имена ресурсов (`string10` …
`string17`) — собственная, не заимствованная нумерация приложения; сравнивал не имя, а
текст ресурса и место, где он показан (`android:text="@string/stringN"` в самом layout, рядом с
конкретным `TextView`).

### 1. Байты `[16]`/`[17]` — один 16-битный код, восемь суб-полей

`Utils.getShort(bArr[17], bArr[16])` даёt значение `V = bArr[16]<<8 | bArr[17]` (`bArr[16]` —
старший байт). `BatteryPackActivity`/`BatteryInfoActivity` разворачивают его в двоичную строку и
**переворачивают** (`HexUtil.toBinary` + `TextUtils.getReverse`, `BatteryPackActivity.java:902-903`),
так что `charAt(k)` в их коде — это бит `k` значения `V` (бит `0` — младший). Ниже — биты в этой
системе отсчёта.

| Биты `V` | Поле-источник (`strings1[i]`) | Подпись экрана (`R.string.stringN`, RU/EN) | Значения | Что означает | К чему относится | Тяжесть |
|---|---|---|---|---|---|---|
| 0 | `[2]` | — (нигде не отображается) | 0/1 | неизвестно — записывается, но не читается ни одним из семи классов | ? | не определена — поле мёртвое для UI |
| 1–2 | — | — | — | не попадают ни в один `strings1..4[i]` вовсе (пропуск между индексами 2 и 3) | — | — |
| 3 | `[3]` | `string8` «电池组均衡»/«Battery pack balancing» | `1`=ON, иначе OFF | балансировка между пакетами активна/неактивна | пакет в целом | низкая — диагностика, не авария |
| 4–6 | `[4]` | `string9` «故障状态»/«Fault conditions» | 3-битный номер (`b4`=старший): `1`(`001`)=`string14` «通讯异常»/Abnormal communication; `2`(`010`)=`string15` «电池断线»/Battery disconnection; `4`(`100`)=`string16` «单电压异常»/Single voltage abnormality; `5`(`101`)=`string17` «充电异常»/Abnormal charging; `0`=норма (зелёная иконка) | связь с модулем потеряна / модуль физически отключён / аномалия одной ячейки / аномалия при зарядке | конкретный модуль (страница — его номер, §1.2) | `2`(отключён) и `4`(ячейка) — **высокая**; `1`(связь) и `5`(заряд) — средняя |

### 2. Что уже видит райдер, а что — нет

Общий канал тревог, который реально доходит до райдера — **другой кадр и другое смещение**
(`type=4`, байт `[14]`, §2.2/§3). Прямой связи между двумя каналами в коде приложения нет ни в
одном из семи классов — приложение никогда не читает оба поля в одном месте и не сопоставляет их.

| Код BMS-канала | Сопоставимый бит `type=4[14]` | Доходит ли до райдера сейчас |
|---|---|---|
| Перегрев модуля (биты 12-13=`"00"`) | бит5 `OverTemperature` — по смыслу близко | **вероятно частично**: если прошивка агрегирует «любой модуль перегрет» в общий бит — не проверено, вывод о поведении прошивки, не о коде приложения; при этом **какой именно модуль** — не доходит в любом случае |
| Недогрев модуля (биты 12-13=`"01"`) | нет соответствия вовсе | **не доходит никак** — в `type=4` нет бита «недогрев» |
| Перенапряжение модуля (биты 10-11=`"00"`) | бит4 `OverVoltage` — по смыслу близко | та же оговорка, что для перегрева — вероятно частично, номер модуля не доходит |
| Пониженное напряжение модуля (биты 10-11=`"01"`) | бит3 `LowVoltage` — по смыслу близко | та же оговорка |
| Связь с модулем потеряна (биты 4-6=`1`) | нет соответствия | **не доходит никак** |
| Модуль физически отключён (биты 4-6=`2`) | нет соответствия | **не доходит никак** — самое тяжёлое состояние из всех восьми, и оно же самое тихое |
| Аномалия ячейки (биты 4-6=`4`) | нет соответствия | **не доходит никак** |
| Аномалия при зарядке (биты 4-6=`5`) | нет соответствия | **не доходит никак** |
| МОП-ключ разомкнут (биты 8-9≠`"00"`) | нет соответствия | **не доходит никак** |
| Балансировка ячеек/пакетов, статус зарядки (биты 3,7,14-15) | нет соответствия — это статусы, не аварии | не доходит, но и не авария по смыслу |

Итог: даже в лучшем случае (если предположение про агрегацию перегрева/перенапряжения в прошивке
верно) райдер не узнаёт **какой из нескольких физических модулей** неисправен и **какого рода**
неисправность (связь/обрыв/ячейка/заряд/ключ) — WheelTalk сегодня даёт для Begode только
общий, ненумерованный сигнал «что-то с напряжением или температурой», а не диагностику по модулю.

## Открытые вопросы

- **Биты тревог `1`/`2`** (§2.2) — расхождение подтверждено только чтением обеих кодовых баз, ни
  разу не проверено записью (MTen3 их не взводил за четыре поездки). Нужен выезд, где
  провоцируется неисправность MOSFET или гироскопа (либо просто дождаться реальной поломки), чтобы
  подтвердить или опровергнуть.
- **Смещение `[14:15]` кадра `type=0`** — вывод «это эхо настроек, не PWM» опирается только на
  `HomeSettingActivity`; не исключено, что часть моделей Begode кладёт туда что-то ещё. Нет записи
  с открытым экраном настроек, где это можно было бы сверить по времени с действием пользователя.
- **Знак тока в `DecodeFrame07`** (`-1 * batteryCurrent`, `GotwayDecoder.cs:426`) — приложение не
  инвертирует знак при отображении `type=7` тока (`HomeFragment.java:1442-1447`). Не проверено ни
  записью (кадр `type=7` на MTen3 не наблюдался), ни понятно, совпадает ли знаковая конвенция
  `WheelState.Current` с конвенцией провода — не берусь утверждать ни бага, ни его отсутствия.
- **Источник команды `V`** — не найден в шести протокольных классах; возможно, в классе
  подключения/сканирования, не входившем в капкан поручения.
- **Полу-напряжения (`SemiVoltage1/2`, `GotwayDecoder.cs:311,317`)** — сопоставлены со смещением
  `[14:15]` кадра `type=1` по совпадению офсета с `info1[1]`/`i26` в `HomeFragment.java:1476,1483`,
  но само приложение это число нигде текстом не подписывает (просто выводит как есть) — совпадение
  смещения не доказывает совпадения смысла.
- **`HomeFragment`'овская урезанная версия того же 16-битного поля (§6) читает биты в другом
  порядке, чем `BatteryPackActivity`/`BatteryInfoActivity`.** `HomeFragment.java:1212` строит строку
  как `byteToBitString(bArr5[16]) + byteToBitString(bArr5[17])` (обычный порядок бит внутри байта,
  без переворота) — что при пересчёте даёт **обычную** двоичную запись значения `V` старшим битом
  вперёд. `BatteryPackActivity.java:902-903` явно **переворачивает** ту же запись
  (`TextUtils.getReverse`). Для 2-битного температурного кода (§6, биты 12-13) это не меняет
  смысла случая «оба бита в нуле», но для случая «один бит установлен» даёт **разное** сопоставление
  бита физическому смыслу (перегрев/недогрев) между двумя классами одного приложения. Не мой вывод
  «который из двух прав» — сам факт разногласия между двумя частями родного кода зафиксирован,
  разрешить его может только реальный кадр с зафиксированным перегревом/недогревом на проводе,
  которого нет ни в одной из четырёх записей MTen3.
